# Pubky Switch specification

**Status.** Review candidate, not frozen. This document and the Switch's wire format (`spec/wire-format.md`) specify the Pubky Switch on its own. The wire format is complete, with test vectors, and the reference prototype implements it. An independent implementation, shared separately, written from the wire format alone, reproduces every test vector on these documents. The spec is frozen once the team has decided the open questions (Section 19), and an independent human crypto review and the measurements on real infrastructure are done.

The Pubky Switch is an inbox and coordination service for Pubky identities. Each identity uses one switch at a time, which its signed `identity.json` names. Apps of other identities write sealed, signed messages to its inbox. The identity's own apps read them from one ordered feed, and coordinate through two generic primitives, claims and shared records. The switch also holds what the identity's apps need from each other and from their counterparties: app records, receive keys, key bundles and the allowlist. It reads no message and no shared data, and it knows nothing of what a protocol does with them.

A protocol uses the Switch through its scopes, the switch permissions they need, its message kinds and its collections; Section 1 says how, and describes `tasks`, the sample protocol of this spec's examples.

## Terms

| Term | Meaning |
|---|---|
| **Identity** | A Pubky identity, named by its Ed25519 public key. |
| **Signer** | The software holding the identity key: Ring, or Bitkit acting as signer. |
| **App** | One application acting for an identity, with its own keys and certificate. An app may run on several devices; the switch treats it as one app (Section 3.1). An app of a protocol, such as a tasks app, holds that protocol's scopes. |
| **App ID** | The identifier of an app, derived from its signing key. |
| **Current app** | An app listed in the identity's newest `identity.json` that the switch hasn't revoked or recorded as departed (Section 3.4). |
| **Own app** | A current app of the identity in question. |
| **App record** | An app's public, self-signed description: signing key, certificate, accepted message kinds, and what its protocols add, such as the boards of a tasks app. |
| **Bundle key** | An app's static X25519 key, named in its certificate, to which the signer seals its key bundles (Section 3.5). |
| **Receive key** | An app's current X25519 encryption key for messages. A fresh random key replaces it after the app reads its feed, about once a day by default (Section 3.6). |
| **Receive key record** | The app-signed record of an app's current receive key, held by the switch and returned by its directory (Section 4.4). |
| **`identity.json`** | The identity-signed document naming the switch, the current apps, removed apps, the current data epoch and the install that signs (Section 4.3). |
| **Version** | The counter of `identity.json`; it increases on every update. Shared records and the chain have versions of their own (Sections 10.3 and 13.6). |
| **Generation** | The counter of the switch named in `identity.json`; it increases when the identity moves to another switch and after a provider loss (Section 12.6). |
| **Scope** | A permission string in an app's certificate, such as `tasks` or `tasks_assign`: a name, or a name and a sub-scope, `name:<sub>` (Section 3.3). |
| **Shared Data Key** | Identity-wide keys, one per scope and data epoch, that encrypt data shared between own apps. |
| **Data epoch** | The counter of the Shared Data Key; it increases on each rotation. |
| **Key bundle** | An app's scope keys for the data epochs it lacks, and the naming key, sealed to its bundle key by the signer (Section 3.5). |
| **Naming key** | An identity-wide key that blinds natural keys and obligation inputs, so the keys of records and claims don't name their counterparty (Section 3.5). |
| **Pubky Switch** (switch) | The service that receives an identity's messages and hosts its coordination primitives. Its mailbox part, where senders' messages land and apps read them, is the inbox. One service hosts many identities, like a Homeserver; each identity uses one service at a time. |
| **Inbox entry** | One encrypted message stored for one or more target apps. |
| **`seq`** | The position of an item at the switch within one generation. Inbox entries and chain items share one sequence. |
| **Feed** | The ordered stream an own app reads: the items after its cursor that it may read, and chain stubs for the other chain items. |
| **Cursor** | An app's position in the feed. |
| **Chain** | The hash chain over operations, `identity.json` deliveries and service transitions, one per generation (Section 8.3). Inbox entries and cursor moves are not in it. |
| **Chain stub** | A chain item's `seq` and hashes, without its content. |
| **Signed head** | The service-signed chain hash at a given `seq`. |
| **Conversation entry** | An allowlist entry an app adds for a counterparty it writes to or invites, so that the two can keep talking until the user blocks the counterparty (Section 7). |
| **Invite** | A conversation entry added before any message, so that the counterparty can write first, for example a shop at checkout (Section 7). |
| **Connect request** | A content-free request from a stranger to be invited, which an identity may allow (Section 7). |
| **Invite code** | A random code an app registers at its own switch and shows, for example as a QR code, so that anyone who has it can write once and start a conversation (Section 7). |
| **Obligation** | Something that must happen at most once, such as a task done once. |
| **Claim** | The server-checked state of one obligation. |
| **Attempt** | One try at carrying out an obligation, with its own outcome. |
| **Step** | The position of an entry in one obligation's log. |
| **Shared record** | A small piece of encrypted shared state, updated by compare-and-swap. |
| **Collection** | A set of shared records that can be listed together. |
| **Policy** | The scopes a shared record requires, fixed at creation. The admission settings in `identity.json` are also called `policy` (Section 4.3). |
| **Operation** | A change sent in a batch: a claim entry, a shared record write, an allowlist or deny list change, a cursor move, an app record, a receive key registration or a key bundle. All are signed by their writer except cursor moves, which the request signature covers. |
| **Transition proof** | The service-signed result of one operation, with its place in the chain. |
| **Condition** | A requirement attached to an operation, checked atomically with it. |
| **Batch** | Up to 8 operations and their conditions, applied all or nothing. |
| **Push relay** | A vendor-run service that turns signed webhooks into APNs or FCM pushes. |
| **Handle** | An opaque ID the push relay maps to one device. |
| **Push key** | The signing key the switch mints for one app's push registration; it signs that app's webhooks and appears in no public document (Section 9). |

## 1. Protocols on the Switch

A protocol on the Switch is the rules its apps follow on top of the switch's formats and primitives, which it uses without changing them. It defines:

- **Scopes:** the names its apps hold in their certificates, such as `tasks` and `tasks_assign`. The switch knows no scope names. It applies one generic rule, a name or a name and a sub-scope, and compares scopes as strings in shared record policies (Section 3.3). Which of its scopes have Shared Data Keys is the protocol's choice (Section 3.5).
- **Permissions:** the switch permissions each of its scopes needs. The signer writes them into the certificate, and the switch enforces exactly that list (Section 3.2). The protocol's own verifiers check that the list is the one the certificate's scopes need.
- **Message kinds:** the `kind` strings of its messages, such as `tasks.assignment`, which scope sends and which receives each kind, and their bodies. A kind is sealed inside its message, so the switch never sees it; apps check it (Sections 5.2 and 5.3).
- **Collections:** its collections of shared records, each with a fixed policy of read and write scopes, and the natural keys of their records (Section 10.3); and what its claims' keys name (Section 10.2).
- **Its own signed formats,** under labels of its own, never a label of the switch's (Section 13.2).

Everything else is the switch's: identities and their `identity.json`, app certificates and records, receive keys, Shared Data Keys and key bundles, envelopes and the signed message frame, admission, the feed and the chain, claims and shared records, the HTTP API, push, limits, export and import, and identity management. The rule of thumb: what any protocol would need is specified here.

**The sample protocol.** This spec's examples use `tasks`, a sample protocol for an identity's shared task lists. Its scopes are `tasks`, to read and write the task lists, and `tasks_assign`, to send and receive task assignments, both with Shared Data Keys, with labelled sub-scopes such as `tasks_assign:team1` for one team's assignments; and `tasks_ext`, without keys, whose sub-scopes such as `tasks_ext:tasks-cap` name extensions. Its kinds include `tasks.assignment`, `tasks.done` and `tasks.reminder`, the last sent only between own apps; its collections include `task_lists` and `task_items`; and its app record member, `protocols.tasks`, lists the app's boards, such as `{"boards": ["home"]}`. A task done once is an obligation, with a claim of its own (Section 10.2).

## 2. Components

| Component | Role |
|---|---|
| **Signer** (Ring, or Bitkit as signer) | Holds the Pubky identity key. Approves apps, signs `identity.json`, derives Shared Data Keys and writes key bundles, enrolls the identity at the switch, performs revocation, key rotation, freeze and recovery. An identity has one signer at a time, the install its `identity.json` names; it can hand the identity to another signer, and backs its records up on the Homeserver (Section 12.8). |
| **App** | Its own keys, scopes, local data, outbox and cursor, and what its protocol adds, such as a tasks app's journal. |
| **Homeserver** | Long-term data: `identity.json`, the records an app publishes, such as those of tasks apps that publish their boards, the signer's backup, optional encrypted backups of apps, and a protocol's own public files and folders. |
| **Pubky Switch** (hosts many identities; each identity uses one at a time, chosen by the user) | Inbox and feed, allowlist and deny list, the coordination primitives (claims and shared records), app records, key bundles, receive key records, push hooks, directory, revocation, freeze, export and recovery. |
| **Push relay** (per app vendor; a reference relay is published) | Turns signed, content-free webhooks into APNs or FCM pushes. |

- The switch is a separate service with its own operator. Closer coupling with Homeservers may come later; the protocol stays decoupled either way, since `identity.json` can point to any switch.
- There is no ordering server and no federation.

## 3. Keys, apps and authorization

### 3.1 Keys

- **Identity key:** exists only in the signer and the signer's backups. Whoever holds it, or the seed it comes from, derives `switch_root` (Section 3.5), and with it the naming key and every data epoch's scope keys: all of the identity's sealed data, past and future.
- **Each app** holds three keys:
  - **Signing key** (Ed25519, static): signs messages, requests to the switch, operations, its own record and its receive key records. It changes only when the app is replaced.
  - **Bundle key** (X25519, static): named in the app's certificate. Only key bundles are sealed to it (Section 3.5).
  - **Receive key** (X25519, rotating): messages to the app are wrapped to it. Each receive key is a new key, from fresh random bytes as recommended, with a number `n` and an 8-byte key ID (kid, Section 13.3). It rotates as Section 3.6 describes.
- **Restoring from backup** keeps the signing key, the bundle key and the receive key it held at the backup (Section 12.4).
- **Derived keys:** an app may derive its signing and bundle keys from a secret it already backs up, such as a seed phrase, under its own derivation labels, so that restoring that secret brings the app back without a new approval. Devices restored from one secret are one app (several devices, below). Receive keys stay random, so the backed-up secret reveals no message sealed to them. It does give the signing key, which can register new receive keys until the app is revoked (Section 3.6).
  - **Recommended profile** (not normative): derive both keys from the secret with the identity's Pubky ID and an index as inputs, for example `derive("<app label>/app-key", secret, identity, u64(index))` and a second label for the bundle key, so that one secret approved for two identities gives two unrelated App IDs. A revoked or departed App ID is never approved again (Section 12.2), so after a revocation the app derives its next keys with the next index and joins as a new app. A new index doesn't help if the secret itself leaked: whoever holds it derives every index.
- **App ID:** the first 16 bytes of `BLAKE3(signing public key)`, z-base-32 encoded. An App ID names an app; it never stands in for its keys: wherever a key matters, apps compare the key itself, or a kid derived from it (Section 3.6).
- **Where keys live:** an app keeps its secret keys (signing, bundle, receive and scope keys and the naming key) only in storage that is bound to the device and not backed up: on iOS, keychain items whose class ends in `ThisDeviceOnly`, one item per receive key, in one access group shared with the push extension (Section 9); on Android, the Keystore or files excluded from backups. Never in plain files of the app's container or a shared App Group container, which go into iCloud and computer backups by default. Other local state that a key could be derived from or that holds key material, such as a journal, is encrypted at rest under a key kept the same way. The app's own backups (Section 12.4) are separate and follow their own rule. Zeroizing keys in memory and platform keystores are production work, on the plan list (the reference prototype: not yet).
- **Deleting a key** means removing it from every copy the app keeps: its key store item, any file, journal entry, cache or snapshot that holds it, on every device that has it, and in any backup the app controls, so that no copy left behind can open what was sealed to it. Overwriting an in-memory value, or dropping it from the app's current state while an append-only journal or snapshot still holds it, isn't deleting it. Forward secrecy (Section 16) assumes this definition.
- **Several devices** are each integrator's choice. Every device can be its own app, or one app can run on several devices with the same keys, which the integrator keeps in sync; the switch sees one app. A claim allows one attempt at a time, but every device holding the app's keys can act on that attempt. The app therefore makes sure only one device carries out a given attempt, for example by passing the attempt ID to the method that carries it out as its idempotency key, and keeps its cursor, receive keys, journal and local state consistent across devices. Such an app is one principal: a stolen device needs no registration of its own to act and read as the app, so losing any of its devices means revoking the app and approving it again. One app per device is recommended.

### 3.2 App certificate

The signer issues a certificate for each app, signed with the identity key (Section 13.2). It delivers the certificate in the approval, the companion claim of the app's Pubky grant approval (`specs/pubky-auth-companion-claims.md`), so one approval gives the app its Pubky grant, its certificate, its scope keys and the naming key (Section 3.5):

```json
{ "v": 1, "kind": "pubky-switch.app_cert",
  "identity": "<pubky id>", "app_id": "<app id>",
  "signing_key": "<ed25519>", "bundle_key": "<x25519>",
  "scopes": ["tasks", "tasks_assign", "tasks_share", "tasks_share_run", "tasks_people", "tasks_people_admin"],
  "permissions": ["claims.read", "claims.write", "lists.read", "lists.manage", "conversation.add"],
  "issued_at": "<rfc3339>", "expires_at": "<rfc3339>" }
```

The JSON samples in this spec, like the test vectors and the prose, use the scope names, message kinds, collections and app record member of a sample protocol, `tasks`, described in Section 1, which the switch treats as opaque.

- **Later suites:** a certificate may carry `suite_keys`, a list of bundle keys of later suites, each tagged with its suite number (the envelope's suite byte, Section 5.1). It is the one place a later suite, such as a post-quantum key encapsulation, adds a key, so it needs no `v: 2` certificate. No suite but suite 1 exists in this version: signers write no `suite_keys`, and readers check its form (`spec/wire-format.md` Section 3.1) and ignore the keys of suites they don't support. The receive key record reserves the same member (Section 4.4).
- **Approval** (`spec/wire-format.md` Sections 3.9 and 3.10). The app asks with an app request signed by its signing key, which proves it holds that key, and binds the Pubky auth request it travels with: its client ID, its client key, the exact capabilities and the hash of its secret. The signer checks the request (its bundle key not of low order, every scope one it knows), derives the App ID from the signing key and the app's paths from the App ID, requires the capabilities to be exactly those paths (Section 3.4), refuses an App ID that is listed with other keys, removed or revoked before (Section 12.2), and shows the user the App ID. The approval it returns carries only public material and one sealed bundle: the certificate, the `identity.json` that lists it, and the app's full key bundle made for that certificate (data epochs 1 to the current one, with the naming key), sealed to the certified bundle key and signed by the identity key (Section 3.5). The app checks that the certificate names its own signing and bundle keys and opens the bundle as it opens every later one. So the auth request's secret, which anyone who sees the QR code or deep link holds, protects only the handshake: the claim it unlocks holds no key. The identity key signs the companion claim, bound to the auth request, as `specs/pubky-auth-companion-claims.md` defines, under the switch's claim identifiers (Section 13.2). A request naming an App ID listed with the same keys renews that app's certificate.
- **Lifetime:** every certificate expires. The signer sets `expires_at` 1 year after `issued_at` by default and never more than 2 years after. Every reader enforces this too: a certificate without `expires_at`, or one that expires more than 2 years after its `issued_at`, is invalid at every app and at the switch (`spec/wire-format.md` Section 3.1). At each run it renews the certificate of every current app once less than half its lifetime remains, with a later expiry (renewal, below), so an app the user keeps never lapses, and a revoked app's key stops working everywhere, at switches that never learned of the revocation too, once its certificate expires. A run renews a bounded number, the soonest to expire first, so many apps due at once are renewed over several runs. Such a renewal keeps the lifetime the certificate has, its `expires_at` less its `issued_at`, counted from the renewal: a lifetime the user chose short stays short. An app that doesn't come back isn't renewed for ever: once two of these renewals in a row went untaken, no record of the app carrying the newer certificate, the signer stops renewing it and tells the user, who renews it or removes it. When the app still owns attempts open or `unknown`, which `GET /v1/{id}/apps` lists, the signer says so: at its expiry it is no longer current, its open attempts become orphaned, and its `unknown` ones are left for the identity's other apps or the user to resolve (Section 10.2). A renewal the user asks for, or a record of the app carrying the newest certificate, starts the count again. Until then the app lapses at its certificate's expiry: from then the switch refuses its every request, its feed read included, so it can neither read nor write there, and readers check its writes and messages against that expiry (`spec/wire-format.md` Section 6.2, 5.1); a renewal the user asks for later still brings it back, with nothing from the app (`spec/wire-format.md` Section 3.8 "An expired certificate").
- **`scopes`** in a certificate are the protocol's permissions, which its apps check.
- **`permissions`** lists the switch permissions the app holds, signed by the identity key with the rest of the certificate: each once, in a fixed order, and no name the switch doesn't define. The switch checks that the list is well formed and then enforces exactly that list. It never derives permissions from `scopes`, which it reads only as strings named in a shared record's policy (Section 10.3), and it needs no table of a protocol's scopes. The signer sets `permissions` from the scopes, using each protocol's table. The trade-off: the switch doesn't check the signer's derivation, so a signer that grants too much is honoured by the switch but refused by every verifier that understands all the certificate's scopes, which derives the list again (below); the signer is trusted with everything anyway.
- **Several protocols in one certificate.** A certificate may hold the scopes of several protocols, so one app, such as a wallet that also chats, takes part in each of them under one App ID. The signer knows every scope the app requests and issues the union of the permissions they need. Any verifier, whichever protocols it knows, requires every permission implied by the scopes it understands, and requires the list to be exactly that when it understands every scope in the certificate. So a wallet that knows two of a certificate's three protocols checks that their permissions are present, applying each protocol's scope rules in full. It still requires its protocol's scope for each of its messages, so another protocol's scopes, and the switch permissions they bring, authorize nothing in its protocols (`spec/wire-format.md` Section 3.1).
- **The switch permissions,** in their fixed order:

  | Switch permission | Lets the app |
  |---|---|
  | `claims.read` | Read claims, and see claim entries in the feed |
  | `claims.write` | Write claim entries |
  | `lists.read` | List contacts, conversation entries and the deny list |
  | `lists.manage` | Change contacts and the deny list, remove conversation entries, and restore the lists after a provider loss |
  | `conversation.add` | Add conversation entries, including invites |

- **Renewal.** The signer renews a certificate to change its expiry or scopes, keeping the app ID, signing key and bundle key, with a later `issued_at`:
  1. The signer stores the new certificate at the service (operation `cert.put`, Section 13.5), with a full key bundle made for it (Section 3.5). The bundle replaces every key bundle part stored for the app, whether the renewal adds a scope, removes one or keeps them all.
  2. It delivers and then publishes `identity.json` listing the new hash and moving the earlier one into `renewed` with `until: null` (Section 4.3). From this delivery the service checks the app against the new certificate.
  3. The app finds `cert.put` in its feed, takes the new certificate once its own `identity.json` lists it, and delivers its updated record (`app.put`), republishing it on the Homeserver if it publishes one. An app that holds an earlier certificate than the one its `identity.json` lists and has no `cert.put` for it, as after a restore from a backup older than a renewal it took (Section 12.4), takes the listed one from its own app record in its directory, which carries it (Section 4.2). It takes it only if the record is signed with its own signing key and the certificate verifies for the identity, names its own App ID, signing key and bundle key, is issued after the one it holds, and has the hash `identity.json` lists for it.
  4. Once the service holds that record, the signer sets `until` to the time the service took it plus the clock tolerance (5 minutes, Section 11), at its next delivery. A renewal isn't a distrust event, so the tolerance goes on the side that keeps the app's last messages: the app stops presenting the earlier certificate when the service takes its new record, and recipients then reject only messages accepted after that.

  - **Reductions close at once.** A renewal that removes a scope or a switch permission, or makes the certificate expire earlier, is a reduction, and its cutoff can't wait for the app, which may never take the new certificate. Right after the delivery of step 2, the signer delivers another `identity.json` that sets `until` of every open renewal of the app to the service time at which the service took that delivery (from the delivery's transition proof, which a retry of the delivery gets too) plus the clock tolerance, and then publishes it. The cutoff is signed by the identity key and needs nothing from the app. A signer stopped between the two deliveries finds the closing delivery it owes at its next run, before any other delivery or provider change: every open renewal that was a reduction, which it judges from the certificates it issued. It delivers the renewing version again, and that retry's answer carries the delivery's proof (`spec/wire-format.md` Section 3.8). Messages accepted before the cutoff keep counting (Section 11). A closed renewal leaves the earlier certificate current nowhere: a switch holding the newer document refuses it, and recipients reject messages carrying it that their inbox accepted after the cutoff. A sender stops wrapping to the app from its next send after it sees the closing document, until the app delivers a record with its new certificate. It sees that document through the Homeserver event stream, from an append answer with a newer `directory_version`, or when it re-fetches a copy more than 10 minutes old (Section 8.1). Until then its appends may still wrap kinds the app may no longer receive, and the inbox can't refuse them, since kinds are sealed. So a removed receiving scope stops at most the sender's directory cache lifetime after the cutoff, while a removed sending scope stops at the cutoff. Own apps deliver the closing `identity.json` to the switches they wrote to recently, as after a revocation (Section 12.2 step 5). Step 3 then only brings the app's record up to date, and step 4 has nothing left to close. Renewals that only add scopes or extend the expiry keep the cooperative flow of steps 3 and 4. Senders tie their cached directories to the `identity.json` version they were read under, and read them again when they see a newer one (Section 8.1), so an app given a new scope receives its kinds as soon as it has delivered its new record.
  - **A refused renewal.** A renewal whose storage or delivery the service refuses for good, with a `4xx` other than `408` and `429` to its operations, a `400` or `413` to its delivery, or a `409 stale_identity` to its delivery whose copy is the version the delivery builds on or doesn't verify (`spec/wire-format.md` Sections 7.1 and 7.4.2), doesn't happen: the app keeps the certificate `identity.json` lists, with its scopes, their keys, its switch permissions and its expiry, so a refused reduction leaves the app's access as it was. So does a renewal whose flow ends without it, as at an alarm. The signer tells the user, whichever of its calls met the refusal, and judges from the certificate `identity.json` lists for the app, whoever's renewal listed it, when to stop: for a reduction the user asked for, it tells them while that certificate still holds a scope the user asked to remove, or a switch permission the reduction would have removed, or expires later than they asked; for another renewal the user asked for, until a certificate holding what they asked is listed, or a later renewal they ask for is delivered; for an automatic renewal, until the app is renewed. Removing the app ends each. A refused automatic renewal doesn't change what the user is told of a renewal they asked for, and a second refused renewal they asked for adds to what the first asked, the user's newest request counting where two contradict.
  - **A removed scope's keys rotate.** The app keeps every key it holds for the data epochs so far, and later writes would go on using the current epoch. So a reduction that removes a scope with keys also rotates the data epoch, as a revocation does (Section 12.2): a scope its protocol gives keys, such as a sub-scope with keys of its own, or a name replaced by some of its sub-scopes, since the name's key derives every sub-scope's (for `tasks`: `tasks` or `tasks_assign`, a sub-scope such as `tasks_assign:team1`, whose keys go, or plain `tasks_assign` replaced by its sub-scopes). Removing only scopes without keys, such as `tasks_ext:tasks-cap`, rotates nothing. The full bundle of step 1 then runs through the next data epoch e+1 and is made for the new certificate, so it holds no key of the removed scope for e+1. The signer also stores every other current app's bundle for e+1, each holding that app's own scopes, so only the certificates that keep the scope get its new key. Only then does it deliver step 2's `identity.json`, which raises `data_epoch` to e+1 in the same delivery that lists the new certificate. From then on writes use e+1 (Section 3.5), so the reduced app can't read data under the removed scope written after that delivery, even if a hostile switch, a cache or a backup hands it the ciphertext. What it read before stays readable to it, as for a revoked app.

  While `until` is null the earlier certificate still counts wherever the app presents it, so nothing it sends before holding the new one is refused. Once `until` is set, it counts only for messages accepted more than the clock tolerance before `until` (Section 11). Messages from before a renewal keep the authority they were sent with, as a removed app's do at or before `distrust_from` (Section 11), and so do the app's shared record writes: the service keeps with each record the certificate it checked the write against and the transition proof that dates the write, and readers judge the write by that certificate at that time (Section 10.3). A write by the earlier certificate that no proof dates before the cutoff doesn't count. Removing a scope takes effect at once at the service and, through the closed renewal, at recipients, which reject the app's messages accepted after the cutoff; senders stop wrapping the removed kinds to it from their next send after they see the closing document (above). A removed scope with keys also rotates the data epoch, so the app reads none of that scope's later data (above). An app whose certificate has expired is refused everything, its feed read included, until the signer stores a renewal and delivers the `identity.json` that lists it (steps 1 and 2), which bring it back without anything from the app: the service takes the signer's new certificate and key bundle for an app the newest `identity.json` lists, whatever its certificate's expiry, and from that delivery checks the app against the new certificate. Meanwhile it counts as not current for the claim rules, so its open attempts become orphaned (Section 10.2).

### 3.3 Scopes

- **One scope rule at the switch.** The switch knows no scope names. A scope is a name, or a name and a sub-scope, `name:<sub>`: the name is 1 to 32 characters of `a-z`, `0-9`, `_` and `-`, starting with a letter or digit, and `<sub>` is 1 to 32 characters of `a-z`, `0-9` and `-`, starting with a letter or digit; `tasks_assign:team1`, for example, is a sub-scope of `tasks_assign`. Holding `name` covers every `name:<sub>` for record reads and writes, so a certificate never holds a name beside one of its sub-scopes. Every reader, the switch included, refuses a certificate whose scopes break this, list one twice, or number more than 32 (`spec/wire-format.md` Section 3.1).
- **Scope roots.** A scope's root is its name, the part before any `:`, and each root belongs to one protocol, so no reader takes one protocol's scope for another's. Each protocol has a name of `a-z` and `0-9`, starting with a letter, without `_` or `-`: the one it uses in app records and as its kinds' prefix. Its roots are its name, or its name followed by `_` or `-` and more characters, such as `chat` and `chat_read`. So a root's protocol is the part before its first `_` or `-`, and no root belongs to two protocols. The rule is the same for every protocol: no name or root is set aside for one. A signer refuses a protocol that breaks it, so independent signers can't give one root to two protocols, and a reader takes a root that isn't one of its own protocols' as another protocol's (`spec/wire-format.md` Section 3.1).
- **A protocol's scope names** are its own: the switch reads a scope only as a string in a certificate and in a shared record's policy. A protocol may bound its scopes further, and its verifiers apply those bounds; the switch applies only the rule above.

### 3.4 Authorization rules

- **Current apps only.** An app is current while the identity's newest `identity.json` lists it with its certificate and the switch hasn't revoked it or recorded its departure. The service applies its own revocations and departures at once. Other parties see them through the directory, which drops the app at once (Section 12.2), and through the next `identity.json`. For orphaned attempts (Section 10.2) the service's view decides. Senders, other readers of app records and the switch use only current apps' records and keys.
- **Scopes** come only from the signer-signed certificate. An app record's `accepts` may narrow them, never widen them.
- **Senders** wrap a message to an app only if its certificate allows receiving that kind and its `accepts` lists the kind. A protocol may narrow this further.
- **Recipients** drop a message when the sender's certificate lacks the sending scope, or the kind is outside their own certificate. They also drop a message that their protocol's narrower rule for senders wouldn't have sent them.
- **Homeserver grants.** Each app's Pubky grant covers only these paths, with `<app_id>` derived from the certified signing key:
  - `/pub/pubky-switch/v1/apps/<app_id>.json`, read and write (its record);
  - `/priv/pubky-switch/v1/apps/<app_id>/`, read and write, for an app that keeps its backups on the Homeserver;
  - the public files and folders of the app's protocol, read and write, only for an app the user allows to edit them; the user may approve the app and decline them. No such path covers another the app's protocols add, so a declined path is off the grant.

  The user allows each path a protocol adds, or declines it, when approving the app, as that protocol's rule on its paths allows: a protocol may require some of them together. The app's record and backup paths aren't the user's to decline. A decline changes only the grant: the certificate, its scopes and its keys are those the app asked for. An app takes a path it asked for that its grant lacks as declined, and asks for it again only when the user does, with a new auth request, which renews its certificate (Section 12.1). A path a later request leaves out isn't declined: that grant covers only what the request names, and the app's earlier grants stay as they were. No step takes one granted path back short of revoking the app (Section 12.2).

  The signer grants these and refuses any capability that covers `/pub/pubky-switch/v1/identity.json` or the signer's backup (Section 12.8), that path or a folder it lies in, such as `/pub/pubky-switch/:rw` or a root grant: only the signer writes `identity.json`, so a grant that covers it would let an app replace it with an older version that still lists a revoked app. It warns the user when another app asks it for such a capability. Each approved request makes a grant of its own, so an app may hold several, each naming the app's record path; when the app is revoked or leaves, every grant that names it is revoked (Section 12.2 step 1). The signer's host revokes them, on the signer's alert, with the Homeserver's grant calls, or the user does in the Homeserver's own settings where the host can't. Readers use a record only if its `app_id` is the one in its path (Section 4.2).

  No grant carries Shared Data Keys; they travel sealed in the approval's key bundle (Section 3.5).
- **Check order.** The service, recipients, senders and other readers of app records check an app in this order and stop at the first failure:

  | # | Check | At the service | A recipient, sender or other reader |
  |---|---|---|---|
  | 1 | The certificate is signed by the identity key | `401 bad_signature` | Drops the message, or skips the app |
  | 2 | It names the identity and the app, whose ID derives from its signing key, and that key signs the request, message or record | `401 bad_signature` | As 1 |
  | 3 | It hasn't expired: at the service's time for a request, at the acceptance time for a message, now for sending or for acting on a record | `403 cert_expired` | As 1 |
  | 4 | The request, message or app record signature verifies with that key | `401 bad_signature` | As 1 |
  | 5 | Its hash is listed for the app in the newest `identity.json` held, or it is an earlier certificate that still counts (Section 3.2), or the app is removed and the message was accepted at least the clock tolerance before `distrust_from` (Section 11) | Own app: `403 not_current`. Another identity's app: `409 identity_needed`, or `403 not_current` if its renewal has closed; an app listed as removed gets a stranger's answer (Section 6.1) | As 1 |
  | 6 | The app record is signed with that key and carries that certificate, or an earlier one of the same app and keys | `403 not_current` | Skips the app |

  Then come scopes and switch permissions (`403 permission_missing`, or the message is dropped), and admission (Section 7). Checks 1 to 3 need only what the caller presents. Check 4 authenticates the caller before the service consults anything it holds, so that someone holding an app's public certificate can't learn whether this switch holds its identity's `identity.json`, which would show the two identities correspond. For an own app the service checks the certificate the newest `identity.json` lists; for another identity's app, the one the request presents (`Switch-Cert`); a recipient checks the one the inbox entry carries, a sender or other reader the one the app record carries.

### 3.5 Shared Data Key

One identity-wide key family encrypts data that own apps share, such as the task lists of `tasks`.

- **Derivation (signer only):** `scope_key(e, s) = derive("pubky-switch/v1/scope-key", switch_root, u64(e), s)`, where `switch_root = derive("pubky-switch/v1/scope-root", identity secret)` (Section 13.3). `e` is the data epoch and `s` a scope name (Section 3.3), without a sub-scope. Only the signer computes `switch_root`; it is never granted or delivered.
- **Sub-scope keys:** a sub-scope `name:<sub>` has keys of its own, derived from its parent's key of the same data epoch: `sub_scope_key(e, name:<sub>) = derive("pubky-switch/v1/sub-scope-key", scope_key(e, name), sub)` (Section 13.3). An app holding `name` derives every sub-scope's key from its `name` key, so no key bundle carries them for it and a new sub-scope needs nothing from the signer. An app holding only the sub-scope gets its keys in its key bundles and can't work back to the parent's key. A data epoch rotation rotates them with the parent's key. Which scopes have keys is the protocol's choice; a scope without keys gets none in any key bundle.
- **Independent of Pubky path keys.** Pubky's hierarchical keys derive every child path's key from its parent directory's key, so a key grant on an ancestor of a path would yield that path's key. Scope keys don't use them: they come from a derivation of the switch's own, so no Pubky grant, on any path, reveals a scope key.
- **What apps hold:** only `scope_key(e, s)` for the scopes in their certificate, a sub-scope key for a sub-scope, for every data epoch from 1 to the current one. Scopes without keys have none, so key bundles and the approval carry keys for the other scopes only (`spec/wire-format.md` Sections 3.5 and 3.10). A scope key reveals no other scope's or epoch's key, nor `switch_root`, and never the identity secret.
- **Delivered at approval:** the approval in the grant's companion claim carries the app's scope keys, for each of its scopes and every data epoch so far, and the naming key as a full key bundle: the same format as later bundles (below), sealed to the bundle key the certificate names and signed by the identity key (Section 3.2). Nothing in the claim is readable with the auth request's secret alone.
- **Naming key:** `naming_key = derive("pubky-switch/v1/naming", switch_root)`, one per identity. It blinds natural keys and obligation inputs (Section 13.3), so the keys of records and claims don't name their counterparty. That protects stored state, exports and dumps taken once the related inbox entries are gone, not against a live operator, which links records and claims to their counterparties through batches and timing (Section 15). The signer delivers it to every app in every key bundle, the approval's included. It doesn't rotate: it hides inputs from the service, not data from apps. An app keeps the naming key it was approved with: it refuses a key bundle part carrying another one and alerts the user, since taking it would split the app's obligation IDs and record keys from the other apps'. A former holder, such as a revoked app or an old backup, keeps it, and together with the operator can test guesses of counterparties against blinded keys whose inputs are public (Sections 14 and 15).
- **Current data epoch:** published in `identity.json` (`data_epoch`). It starts at 1 and only increases.
- **Sealed fields** (Section 13.4) sit inside writer-signed operations, so the switch can neither read nor change them.
- **Writes use the current data epoch.** The switch rejects a sealed field whose data epoch isn't the current one (`409 stale_epoch`), except in uploads during a provider move or recovery (Section 12). An app that doesn't hold the current key yet reads older data but writes no sealed data until it has the key; an entry whose effect needs a key it lacks waits for that key stored locally, with the cursor past it (Section 8.2).
- **Key bundles for later epochs:** an approval happens once, so when the data epoch increases (Sections 3.2 and 12.2) the signer stores each remaining app's key bundle at the switch (operation `key_bundle.put`, Section 13.5). The bundle is an envelope (Section 5.1) sealed to the app's bundle key, signed by the identity key, holding the naming key and the app's scope keys for the data epochs it lacks: those after the ones it already holds (below). So bundles stay small while an app keeps up. A bundle names the certificate it was made for, by hash, and holds exactly one key for each scope of that certificate that its protocol gives keys, a sub-scope with its sub-scope key, and each data epoch of its range, and no other (for `tasks`, every scope but `tasks_ext` and its sub-scopes, and `tasks_assign:team1` with its sub-scope key). **Parts:** a bundle too large for one envelope (64 KiB, about 400 to 800 scope keys by the length of their scopes, about 700 of those of `tasks`), such as a full bundle after many epochs or the delta of an app that was offline through many rotations, is stored as several `key_bundle.put` parts, each covering a contiguous range of data epochs `[first_epoch, last_epoch]` within 64 KiB, each signed and sealed on its own; the app opens every part and assembles the keys. Parts stored for an app never overlap: a new part replaces those whose range it overlaps. Every renewal stores a full bundle made for the new certificate (Section 3.2), which replaces them all, so the parts stored for an app name its newest certificate. No part ever holds `switch_root` or a key for a data epoch after the one it was made for: the current one, or during a rotation the next one, whose parts the signer stores before it raises the epoch. An app refuses a list of parts that overlap or are out of order. It skips a part whose sealed range differs from the range it names in the clear, which the signature doesn't cover, one with a key after the next data epoch, and one whose naming key differs from an earlier part's or from the one the app holds. It also skips a part made for a certificate other than its own or a renewal of it that its newest `identity.json` lists, and a part whose keys aren't exactly those of that certificate's scopes with keys over its range, so it never takes a key its certificate doesn't grant or has to choose between two keys. A key it still lacks leads to a full-bundle request (below; `spec/wire-format.md` Section 3.5). Only that app can fetch it. A new bundle appears in the app's feed, so an app that was offline fetches it whenever it returns. The app keeps the scope keys in its own state and backups, so a rotating key would protect nothing here; the bundle key is static.
- **What each app holds:** the signer learns it from `GET /v1/{id}/apps` (`keys_through`): the newest data epoch through which the app holds every scope key. The service works it out from what it sees: the data epoch of the first `identity.json` that lists the app, which is the epoch of its approval, raised to a part's last data epoch once the app's cursor has passed that part's item in the feed, for each part that continues what the app holds. It is worked out again over every passed part in epoch order, so a part passed before the gap below it was filled counts once the gap is filled. An app fetches a new bundle before its cursor passes the bundle's item, so a cursor past it means the app holds the bundle. For this, `key_bundle.put` names the bundle's first and last data epoch in the clear; data epochs are public in `identity.json` anyway. A bundle that replaces one the app never fetched starts where the app's holdings end, so nothing is skipped. When the service shows no value, for example after a provider loss, the signer stores a full bundle.
- **Full bundles:** after a restore, an app may ask for a full bundle with every epoch so far (`POST /v1/{id}/apps/{app_id}/keys`), which the signer stores the same way. The app asks when, after fetching its current bundle, it still lacks a scope key for some data epoch up to the current one, and asks once until a full bundle arrives. The service shows the request, with the time of the first one, in `GET /v1/{id}/apps` until the parts it stores for the app together cover every data epoch from 1 to the current one. The signer, when next online, stores a full bundle for every current app with a pending request, made for the app's current certificate: every data epoch from 1 to the current one, whatever the parts it stored before already cover. A run answers a bounded number of requests, the oldest first, so many pending at once are answered over several runs. The app that asks may have lost what those parts gave it, and only a put that completes the range answers the request, so storing only what isn't covered would leave a request made while every epoch is covered pending for good. A delivery that was cut short resumes where it stopped. Its parts replace every part made for another certificate, which the app skipped. When the app's record at the service carries an earlier certificate, as after a restore from a backup older than a renewal or after a provider loss, the signer stores the current one with them (`cert.put`), as at a renewal, so the app takes it and then the parts. Any delivery cut short resumes from the epoch after `keys_through`; it starts from epoch 1 only with a pending full-bundle request or without `keys_through`.
- **Recovery:** anyone holding the identity secret re-derives `switch_root`, and from it every data epoch's keys and the naming key, so restoring the signer restores access to all shared data.
- **Exposure:** every app holding a scope key can read all data under that scope. A compromised app exposes its scopes' shared data until it is revoked and the key is rotated (Section 12.2).
- **A copied app state reads on:** the bundle key is static, and later key bundles are sealed to it, so a copy of a current app's state (from a seized device or a backup) opens every key bundle stored for that app and reads its scopes' shared data, past and future, for as long as the app is current, through every data epoch rotation made for other apps. Reading records and key bundles creates no registration, so nothing shows the copy. It stops only when the app itself is revoked and the epoch rotated (Section 12.2), and for a scope a reduction removes, at the epoch that reduction starts (Section 3.2). This is accepted: sealing later bundles to rotating keys would heal only later epochs, at a cost in availability (Section 19, question 2).

### 3.6 Receive keys

Each app rotates its own receive key, without involving the signer, its other own apps or its contacts. Forward secrecy comes from deleting a receive key once everything sealed to it has been read.

- **Generation:** each rotation brings a new X25519 key. The app keeps the secret of its current key, plus those of retired keys it hasn't deleted yet. How the app makes the key is its choice; the spec recommends 32 fresh random bytes, clamped as an X25519 secret. Keys then share nothing, so a stolen receive key reads nothing sealed to an earlier or a later one. Rotation protects against a leaked receive key only. A leaked signing key, which a full copy of the app's state or a backup contains, can register receive keys of its own, so it reads new messages until the app is revoked (Section 12.2); unexpected registrations, below, make that visible. It can also ask counterparties to re-send what they sent in the last 30 days, which they seal to its keys (Section 11), so it pulls that much history too. An app may derive its keys instead, for example from a seed, to make backups or devices easier; whoever copies that seed then reads every key derived from it, and the forward secrecy in Sections 15 and 16 holds only from the app's next fresh random key.
- **Registration:** the app registers each receive key record (Section 4.4) with the switch (operation `receive_key.put`, Section 13.5). Its first record at a service has `n` 0 for a new app; after a provider loss, its first record at the new service may carry any `n` higher than every `n` the app has registered (Section 12.6). Each later record has `n` exactly one higher than the current record's; anything else gets `409 conflict` with the current record. A registration is an item in the chain (Section 8.3), and the key is current from that item's `seq`.
- **Kids are unique:** a kid names one key in the whole account. The service refuses a registration whose kid any app of the identity has registered before (`400`), so an envelope's kid names exactly one recipient key. The 8-byte kid only routes an envelope; HPKE binds the key itself, so a kid shared by chance across identities changes nothing.
- **Low-order keys:** X25519 with a key of low order gives the all-zero shared value, which RFC 9180 aborts on, so such a key can't be sealed to. The service refuses to register one (`400`), a certificate that names one as its bundle key is invalid, and a sender that meets one in a directory skips that app and seals the message to the identity's other apps (Section 8.1), so one bad key never blocks the others.
- **When to rotate:** at the first feed read at least 24 hours after the last rotation, if the app has opened an envelope wrapped to the current key since that rotation. An app may use a shorter interval, down to 1 hour; a server app that reads continuously should. An app that has opened nothing new doesn't rotate, and a push extension's peek doesn't count (Section 9).
- **Cut-over:** from a registration on, the service rejects every envelope wrapped to any other key of that app with `409 stale_key`, whose `current` holds the app's current receive key record (Section 6.4). The sender checks the record (Section 8.1), seals the message again and re-sends it. A sender whose cached directory predates the rotation pays this extra round once, unless it refreshed the directory in the background (Section 8.1).
- **Deletion:** the app deletes a retired key, in the sense of Section 3.1, once its cursor has passed the `seq` of the next key's registration. So the order is: read; register the new key, after which the service rejects envelopes to the old one; read on past the registration, which picks up everything that reached the old key before the registration; then delete the old key. Nothing can reach the old key after its successor's registration, so there is no race. The cursor here is the app's own read position, the one its local state has committed: every entry before it is processed, or stored locally in opened form (Section 8.2), so nothing the app still has to open is sealed to the old key. An entry it holds back unopened or unchecked keeps its position before that entry, and so keeps the key. The deletion doesn't wait until the service holds that position: while a cursor move is deferred (Section 8.2) the app still reads on from its own position, never from the service's. Devices sharing a cursor each hold their own copy of the key, and each deletes its copy by its own read position, so one device's deletion never takes the key from a device that is behind; a device takes no retired key from its sync once its own position has passed the successor's registration. In the foreground the open long-poll returns the registration at once; an app reading in the background passes it at its next read.
- **Backups:** backups are the app's responsibility (Section 12.4). A backup holds the app's current receive key, so the app should refresh it at every rotation, replacing and deleting the previous one, so the receive key in a leaked backup reads at most the messages sent until the next rotation, as the live state would. A backup that also holds the signing key reads new messages until the app is revoked, as above; Section 12.4 recommends keeping that key out of routine backups. A restore from an older backup can't open entries sealed to keys created since; it registers a fresh key and asks those senders to re-send (Section 12.4).
- **Devices:** devices of one app share its receive keys. The device that rotates passes the new key to the app's other devices through the app's own device sync (Section 3.1). A device that finds a registration of its app with a higher `n` than every key it holds reads no further until it has the key, so it never moves the shared cursor past entries it can't open. When two devices rotate at once, the second registration gets `409 conflict` naming the first one's key, and the second device discards its own. A device that can't get keys from its sync should be its own app. A restore from a backup older than the last rotation registers a fresh key instead (Section 12.4).
- **Unexpected registrations:** an app treats a registration of its own app that neither it nor one of its devices made as a compromise, including a `409 conflict` naming such a key: it stops, alerts the user, leaves at once (`leave`, Section 12.3) and asks the signer to revoke it (Section 12.2), with `distrust_from` at the service time at which the registration was accepted, from its chain item. An app that learns of the registration from a `409 conflict` hasn't read that item, and doesn't wait to read it before it leaves. It gives instead the later of two service times it holds: that of the newest chain item it has verified, and that of its own last registration. The foreign registration lies after both, and the service's time never goes back (Section 10.1), so that time is at or before the registration's, and distrusts no less. The leave is app-initiated and irreversible, so the copy that registered the key, which holds the same signing key, is refused by the service from that moment, without waiting for the signer. Readers of the app's records still check only `identity.json`, so they still use its records until the signer publishes the revocation; that window is accepted. An app that shares keys across devices authenticates registrations through its own device sync (Section 3.1), so its devices can tell their own registrations from someone else's.
- **After a restore:** a restored app can't tell a thief's registration made before the restore from one of its own that it made after the backup and no longer remembers. It treats every registration after its backup's newest key whose kid it doesn't know as a possible compromise: it asks the user whether the app ran on that device after the backup was made, and makes no attempts until the user answers. If the user confirms, the app takes those registrations as its own; if not, or in doubt, it leaves at once and asks the signer to revoke it, as above. A registration after the key the restored app registers itself is unambiguous: someone else's. So a restore alone doesn't cut off a thief who holds a copy of the app's state (Section 12.4).

### 4.2 App record

```json
{ "v": 1, "kind": "pubky-switch.app",
  "identity": "<pubky id>", "app_id": "<app id>", "signing_key": "<ed25519>",
  "cert": "<signed certificate>",
  "accepts": ["tasks.assignment", "tasks.receipt", "tasks.list"],
  "protocols": { "tasks": {
    "features": { "board_kinds": ["<board kind>"] },
    "public_boards": { "<board>": "<opaque payload>" } } },
  "label": "alice wallet", "updated_at": "<rfc3339>", "expires_at": "<rfc3339>" }
```

- Signed by the app's signing key (Section 13.2).
- **Path:** a reader uses a record read from `/pub/pubky-switch/v1/apps/<app_id>.json` only if the record names that `<app_id>`.
- **Where it lives.** The app delivers its signed record to the switch (operation `app.put`, Section 13.5) when it is added and whenever the record changes, and the directory serves it to admitted senders. An app whose protocol needs public data, such as a tasks app that publishes its boards, also publishes the same record on the Homeserver. An app publishes a record on the Homeserver only after the switch accepts it (`app.put`), and while a publication fails, or the Homeserver copy differs from the newest record the switch accepted from it, it publishes that newest record again, never an older one and never over a Homeserver copy with a later `updated_at`; it stops once it deletes that record to leave, or leaves (Section 12.3). An app whose devices share its keys writes a missing Homeserver copy back only once the switch has shown the app current: in a read, after its feed, or right after the switch accepts its `app.put`, which the service refuses once the app has left. A copy one device deleted to leave is then not restored by another device that hasn't yet seen the departure in its feed. Other apps need no Homeserver record: recipients verify messages with the certificate each inbox entry carries, and readers check the `identity.json` listing.
- **The later `updated_at` wins.** Each new record of an app has an `updated_at` strictly later than every record of it the app delivered or published. Devices of one app agree on it through the app's own device sync, as for receive keys (Section 3.6). A party that sees two versions uses the one with the later `updated_at`. The switch applies the same rule: it replaces the record it holds only with one whose `updated_at` is later, so a replayed older record never replaces a newer one. The held record again, byte for byte, changes nothing. A different record with the same `updated_at` is refused (`409 conflict`, naming the held record), and the device that gets that answer writes again with a later time (`spec/wire-format.md` Section 6.2).
- **Two records at one time are a conflict.** A reader that sees two records of one app with the same `updated_at` and different bodies, for example one from the switch and one from the Homeserver, acts on that app by neither and tells the user. It keeps using an earlier record of that app it already holds, if any, and can still act on the identity's other apps. A record with an `updated_at` strictly later than both ends the conflict. A record whose `updated_at` is more than the clock tolerance (5 minutes, Section 11) ahead of the reader's clock isn't used at all, so it takes part in no comparison.
- **No encryption key.** Messages are wrapped to the app's current receive key, which has its own record (Section 4.4), so the app record changes only when what it describes does, such as its accepted kinds or a protocol's member, or to renew its `expires_at`.
- **A protocol's members.** `accepts` lists the message kinds the app takes, in its protocol's names. `protocols` holds what each protocol adds to the record, one member under the protocol's name; the switch checks only its form and never reads inside it, and a reader ignores the member of a protocol it doesn't know (`spec/wire-format.md` Section 3.2). `expires_at` is the app's choice, and null means the record doesn't expire; a protocol may require one. The member of `tasks`, for example, lists the app's boards.

### 4.3 `identity.json`

```json
{ "v": 1, "kind": "pubky-switch.identity", "identity": "<pubky id>",
  "version": 12, "generation": 3, "signer": "<16 bytes>",
  "inbox": { "url": "https://inbox.example", "service_key": "<ed25519>" },
  "policy": { "admission": "contacts_and_conversations",
              "connect_requests": { "enabled": false, "max_pending": 50, "push": false } },
  "apps": [ { "app_id": "<app id>", "cert": "<BLAKE3 of the signed certificate bytes>" } ],
  "removed": [ { "app_id": "<app id>", "distrust_from": "<rfc3339>" } ],
  "data_epoch": 4,
  "recovery_from": null,
  "record_max_age": 7776000,
  "renewed": [ { "app_id": "<app id>", "cert": "<BLAKE3 of the earlier signed certificate>", "until": null } ] }
```

- Signed by the identity key (Section 13.2). The certificate hash is over the signed document bytes (Section 13.2).
- **One signer at a time** (`signer`): the signer ID of the install that signs for the identity, 16 bytes it picks at random when it first signs. Only the install the newest `identity.json` names signs. An install that holds the identity key but isn't named refuses every signing call, tells the user that another install manages the identity, and offers to take over (Section 12.8), on the user's confirmation. A hand-over or a restore sets `signer` to the new install's ID in its first delivery. Readers check its form and otherwise ignore it: the identity key's signature is what authorizes, and the field only keeps honest installs from signing at once.
- **Current apps:** `apps` lists every current app with the hash of its certificate, up to the switch's app limit, announced at enrollment: 32 by default, never more than 255. The signer adds an app when it approves it, and moves it to `removed` on revocation or after a leave (Section 12).
- **Each App ID once:** an App ID appears at most once in `apps`, at most once in `removed`, and never in both; a document that breaks this is invalid. An App ID once in `removed` is never listed in `apps` again (Section 12.2): an app holding a version that lists it as removed refuses a later version that lists it in `apps` and alerts the user, and the switch refuses such a version.
- **Record age limit** (`record_max_age`, optional): the longest time, in seconds, that a reader relying on the identity's app records trusts one after its `updated_at` (Section 4.2); 90 days when absent. It is signed with the rest of the document, and only the signer sets it.
- **Removed apps** stay in `removed` until the signer purges them. `distrust_from` is the time the service revoked the app or recorded its departure, or an earlier time the user picks when revoking it after a compromise. Recipients reject its messages accepted later than 5 minutes before that time, the clock tolerance (Section 11). An app in neither list is not current, so once the signer purges an app, its remaining messages are rejected too; signers purge only apps they expect no more messages from, and should wait until the app's certificate has expired: switches of other identities answer an app listed as removed like a stranger but can't tell a purged one from a new one (Section 6.1), while an expired certificate is refused everywhere. The signer and the switch keep a purged App ID for good, and never approve or list it again (Section 12.2).
- **`renewed`** lists the earlier certificates of current apps during and after a renewal (Section 3.2), absent when empty. An entry goes with its app when the app moves to `removed`, and the signer purges it only when no more messages carrying that certificate are expected, for example once no stored request still relies on it.
- **`recovery_from`** names the generation lost in the most recent provider loss (Section 12.6), or is null. Once set, it stays in later versions until a later loss replaces it.
- **`service_keys`** lists the service keys of earlier generations, `{ "generation", "key" }`, ascending, at most 256, absent when empty. Each generation has one service key. A switch keeps with each current record the transition proof of its write, which may be an earlier generation's, and readers, apps added later included, check such a proof with the key listed for its generation, which the identity key signs (Section 10.3). It keeps with each entry of a live claim the transition proof of that entry too, which an export carries and the next service checks with its generation's key (Section 12.5). So a key stays listed for as long as such a proof needs it: the switch reports to the signer every generation that some current record's or live claim's entry's kept proof names (`proof_generations` in `GET /apps`, Section 6.2), and at every cooperative move (Section 12.5) and every key change in place the signer keeps the key of each generation reported and drops only the others. It never drops one that is reported. If they would be more than 256, it refuses the move or key change and shows the user why, until records are rewritten, which moves their proofs to the current generation, and the claims are finished. The switch refuses an `identity.json` that drops a reported key or lists a wrong one (`409 conflict`). A provider loss adds no key: the lost generation's proofs date nothing.
- **Service key:** `inbox.service_key` is the key the switch generated for this identity's account at enrollment (Section 6.2). It signs the service's responses, transition proofs and signed heads for this identity (Section 13.2). Each account has its own key, so a leaked key affects only that identity. Push webhooks are signed with separate push keys that appear in no public document (Section 9).
- **Version and generation only increase.** Apps and the switch reject a document whose version or generation is lower than one they have seen. `data_epoch` only increases too: an app refuses a later version with a lower one, and alerts the user; the switch doesn't check it, since the apps' check enforces it. A new identity starts at `version` 1, `generation` 1 and `data_epoch` 1. Two documents with the same version and different body bytes are equivocation: apps stop acting on that identity and alert the user. The same body under another signature isn't: it shows only a signer that signed one version twice, against Section 13.2. The switch keeps the body it holds at a version: a peer delivery of another body there, by an app of that identity or by an own app delivering a counterparty's document, is refused with the switch's copy, so the sender holds both and stops acting on that identity (`spec/wire-format.md` Section 7.4.5).
- **Enrollment** (Section 6.2), for a new identity or a new provider:
  1. The signer sends `POST /v1/enroll`, signed with the identity key, naming the identity, the service origin, a random nonce and the policy, with the current `identity.json` if there is one and the App IDs it revoked or saw depart, which the new account keeps as tombstones from the start (Section 12.2).
  2. The service creates the account, staged, and answers with the account's service key and limits, signed with that key. Repeating the same enrollment returns the same answer.
  3. The signer delivers an `identity.json` naming that service and key (`PUT /v1/{id}/identity`), then publishes it.
  4. The account becomes active once it holds a document naming it; until then it answers `503 staged` to everything else.
- **Delivery to the service:** the signer sends every new version to the switch (`PUT /v1/{id}/identity`). The service enforces the current apps, removals and data epoch of the newest version it holds, and records each delivery in the chain, so own apps see it in their feed.
- **Compare-and-swap at the service:** the switch is the compare-and-swap point for `identity.json`, so two signers can't both build on one version. `PUT /v1/{id}/identity` names the hash of the previous version the new one builds on (none when the service holds no earlier version), and the service refuses it with `409 stale_identity` unless that is the version it holds. That answer carries the copy the service holds, with its version, generation and document hash, so the signer can republish it and build its next version on it. The signer keeps the generation, version and document hash of the newest version a service accepted from it, or that it adopted, a version it restored from its backup included, and never adopts or republishes a copy with a lower version or generation, or another body at that version: from any service, after an import too, that is a rollback or equivocation, which it shows the user as an alarm instead of building on it. Until a delivery of its own succeeds again, the signer releases nothing that relies on its newest version, such as an approval's claim (Section 3.2). Once the user has seen the alarm, the signer delivers its newest version again, the same bytes naming the version they build on (`spec/wire-format.md` Section 7.4.2): a switch that went back to that version takes it, and one that holds less, none or another body there raises the alarm again. A strictly newer copy, another signer's, it may adopt. The same document delivered again, as a retry, is accepted whatever it names as the version it builds on, and its answer carries the original delivery's transition proof, as a batch retry's does, so the signer learns when the service took it even when the first answer was lost. The signer delivers first, and publishes on the Homeserver only after the service accepts. If the Homeserver copy differs from the service's, the signer republishes the service's copy.
- **Caching for verification and use:** at most 10 minutes, re-fetched after any failure. A sender's cached directory may be older, as long as this document still names the same switch and generation (Section 8.1). A reader that holds both the Homeserver copy and the copy in the identity's directory uses the one with the higher version.
- **The switch's copy:** the switch serves the newest `identity.json` it holds for its identity, as the signer delivered it, with a public, read-only `GET` (`spec/wire-format.md` Section 7.4.15). A reader that is about to act on an identity's public app records and holds no copy fresher than 10 minutes reads the Homeserver copy and then, in parallel with the app record reads that follow it, which need only that document, the switch's copy, and uses the higher version: the same document at an equal version, and a different one at the same version is equivocation (above). So a stale or malicious Homeserver that serves an older document, still listing an app since revoked, doesn't make a first-time reader act on that app's records. Its limits are in Section 14.
  - **No added latency:** the lookup runs beside reads the reader makes anyway, so it adds no request in sequence. It is made only before acting on public app records, and only without a fresh copy, and the reader waits for it at most until its Homeserver reads finish plus a short grace (the reference prototype: 500 ms).
  - **No silent fallback:** a lookup that hasn't answered by then keeps running; in a real app the user confirms the action meanwhile. If the lookup has failed, or still hasn't answered, when the app acts, an action the user starts goes ahead only once the user explicitly confirms it although the identity's switch couldn't confirm the identity's apps, and the app records an event for it. An answer that arrives before the action takes effect is still used. An action without the user waits for the lookup instead, with the client's usual timeout and one retry, and never acts on the Homeserver copy alone: if the lookup still fails, it isn't taken. A failed lookup counts until the reader looks up again, once its copy is more than 10 minutes old.
  - **Hard to switch off:** the service limits the read per network source, with a higher backstop per account (Section 6.5), so one source flooding it can't push every reader onto an unconfirmed action. The answer is a signed public document, the same for every reader, so caches may keep it for a short time (60 seconds); a reader keeps the copy it got for 10 minutes, as any other, so its copy may lag the service's by up to that minute more.
  - **After a move:** an old service, frozen, answers with its last `identity.json` and the signed freeze naming the next service (Section 12.5). A reader that gets a freeze checks it with the identity's key, follows it once to the next service's public read, and uses the higher copy. A next service still staged means the move isn't published, so the old service's copy is the newest. A next service that is frozen too isn't followed, and the lookup counts as failed.
- **Watching for changes:** a running app subscribes to the Homeserver event stream (`/events-stream`, live, filtered to `/pub/pubky-switch/v1/identity.json`) for its own identity and for the counterparties it caches, and re-fetches a document as soon as an event names it. A subscription that closes is opened again from the cursor of the last event it took, never from the newest event, so the events in between aren't missed; while it is closed, the document counts as unwatched. A document it watches this way needs no 10-minute re-fetch for sending; one on a Homeserver it doesn't watch keeps the 10-minute rule. A protocol may require a copy at most 10 minutes old before some actions, watched or not. After waking, the app resumes the stream from its cursor, so it catches up on missed changes in one request.

### 4.4 Receive key record

```json
{ "v": 1, "kind": "pubky-switch.receive_key",
  "identity": "<pubky id>", "app_id": "<app id>",
  "n": 41, "kid": "<kid>", "x25519": "<public key>" }
```

- Signed by the app's signing key (Section 13.2) and registered with the switch (Section 3.6). The directory returns the record of each current app.
- **`n` only increases** for an app.
- **The app signs it, the service holds it.** The service can withhold a record or offer an older genuine one, but can't make one; senders check every record before using it (Section 8.1).
- **Later suites:** like the certificate (Section 3.2), the record may carry `suite_keys`, receive keys of later suites beside the suite 1 `x25519` key. Each such key's kid is derived over its suite and the key (Section 13.3), so it differs from every suite 1 kid. Apps of this version write none and ignore those of suites they don't support.

## 5. Messages

### 5.1 Envelope (binary)

```
header:
  magic "PSW1" (4 B) | version (1 B) = 1 | suite (1 B) = 1 | flags (1 B, bit0 = notify) | recipient count n (1 B, 1-255) | key commitment (32 B)
  n x { kid (8 B) | hpke_enc (32 B) | wrapped_cek (48 B) }
body:
  nonce (24 B) | ciphertext
```

- **Suite 1:**
  - **Content:** XChaCha20-Poly1305 under a random 32-byte content key, with the whole header as AAD.
  - **Key commitment:** `derive("pubky-switch/v1/key-commit", content key)` (Section 13.3). A recipient whose unwrapped content key doesn't match it rejects the envelope, so every recipient app opens the same plaintext or none.
  - **Key wrap:** one per recipient app, to its current receive key, named by its kid. A key bundle is wrapped to the app's bundle key instead (Section 3.5). HPKE base mode (RFC 9180) with DHKEM(X25519, HKDF-SHA256), HKDF-SHA256 and ChaCha20-Poly1305. The HPKE plaintext is the content key; `info` is defined in Section 13.3; the HPKE AAD is the first 40 bytes of the header (magic through key commitment). As RFC 9180 requires, sealing and opening abort when the X25519 shared value is all zero, which a low-order key or `enc` gives (Section 3.6).
  - **Randomness:** the content key, the nonce and each wrap's ephemeral key come from the operating system's secure random generator. No sealing interface takes them from its caller; only test code fixes them, to reproduce the shared vectors.
- **Padding:** the envelope's total size is padded up to 1, 4, 16 or 64 KiB. Maximum 64 KiB.
- **`notify` flag:** authenticated by the AAD and by the sender's signed request. The switch pushes only when it is set, and rate-limits notifying writes per sender.

### 5.2 Plaintext and signature

```
sender app ID (16 B) | signature (64 B) | JSON length (u32, big-endian) | message JSON bytes | zero padding
```

- **Signature:** covers the recipient identity and the exact message JSON bytes (Section 13.2). Nothing is canonicalized; JSON with duplicate keys is rejected.
- **Verification:** against the sender's certificate, which the inbox entry carries, its scopes, and the sender identity's `identity.json` (Section 11). The plaintext app ID must equal `from.app_id`.

### 5.3 Common message fields

```json
{ "v": 1, "kind": "<protocol>.<kind>", "msg_id": "<uuid v4>", "created_at": "<rfc3339>",
  "from": { "identity": "<pubky id>", "app_id": "<app id>" },
  "to": "<pubky id>",
  "refs": ["<BLAKE3 of referenced message JSON bytes>"],
  "body": { } }
```

- **`kind`** is a message kind of the sender's protocol, such as `tasks.assignment`. The protocol defines its kinds, the scopes that send and receive each, and their bodies.
- **No sessions and no ordering.** Every app derives state deterministically from the messages, claims and shared records it holds, using `refs`. A protocol says how its messages that cross resolve.
- **`created_at` is informational,** except that provider-loss recovery uses it to find requests made before the loss (Section 12.6), and that a message its signer queues again goes only until 30 days after it, less the clock tolerance (Section 11). Freshness rules use the inbox's acceptance time (Section 11) and, for request expiry, a clock tolerance of +/-5 minutes. A local clock never decides whether something was paid.
- **Deduplication:** by (sender identity, `msg_id`), durably (Section 11).

## 6. The service

### 6.1 Request authentication

Every call is signed by an app, or by the identity key for signer operations. There are no sessions.

- **Headers:** `Switch-Identity`, `Switch-App` (absent for signer operations), `Switch-Cert` (from apps of another identity: the signed certificate), `Switch-Invite-Code` (optional, Section 7), `Switch-Timestamp`, `Switch-Signature`.
- **Signature covers** the method, path and query, `BLAKE3(body)`, the timestamp, the switch origin and the identity, app, certificate and invite code headers (Section 13.2).
- **The service checks:**
  - for an own app: that it is current in the newest `identity.json` the service holds, and its switch permissions and scopes, from the record and certificate it delivered with `app.put` (its first call carries one);
  - for an app of another identity (inbox appends, connect requests and directory reads): that the presented certificate is signed by the identity in `Switch-Identity`, names the app and its signing key, and hasn't expired; that the request signature verifies with the app's key; its admission (Section 7); and, for appends and connect requests, that the newest `identity.json` of that identity the service holds lists the app with that certificate. The service keeps the newest `identity.json` delivered for each identity (`PUT /v1/{id}/peers`) and names its version in every successful response to that identity's apps and in `409 identity_needed` (`known_version`, in the signed body); other errors don't carry it, so they reveal nothing of what it holds. A sender delivers its identity's document before its first append to an inbox, in parallel with the directory read a first message needs, and again whenever a response shows an older version. An append from an app that the service's copy doesn't list gets `409 identity_needed`; the sender delivers its document and retries. The service fetches nothing from the sender's Homeserver. The document is signed by the sender's identity key, so it can't be forged; the service keeps the highest version it has seen and never goes back to an older one. A revoked app can still reach a switch that hasn't yet received its identity's newer document. Recipient apps reject its messages anyway, since they check senders against the document from the sender's own Homeserver (Section 11), and an own app that holds a newer document than its switch delivers it. An app that the service's copy lists as removed, or that the document it delivers lists there, is answered exactly like an app of an identity the service doesn't admit and holds no copy of: only an invite code admits it, an append or connect request then gets `409 identity_needed` naming no version, and `PUT /peers` answers with the version it delivered. So a revoked app's key can't probe switches to learn which identities correspond with its own; its certificate's expiry (Section 3.2) ends what a switch without the newer document still allows;
  - the timestamp, within +/-5 min;
  - **cheap before costly:** every call has a body cap, refused with `413` before the body is read; the timestamp is checked before any signature, and signatures before anything that reads the account's state; an own app's first call is authenticated from only the first `app.put` naming it, whose key must give its App ID before the request, then the record, certificate and operation are verified; a claimed caller that keeps failing authentication is rate-limited before any signature work (`spec/wire-format.md` Sections 7.1, 7.2);
  - **retries, by content:** an append whose envelope the service still holds returns the original result, and so does a batch whose batch ID is already in the chain, while the service keeps that batch's transition proofs (30 days). After that, a batch carrying an ID the service still holds gets `409 conflict` (Sections 6.3 and 13.5). Any other request is applied as new, which is safe: a repeated message is dropped by its recipients by `msg_id` (Section 11), and a repeated operation in a new batch fails its expected step or version, so the app finds its earlier write in the current state. No key or timer is needed, and a replay within the timestamp window is recognized the same way. Requests outside batches carry no nonce, so their own rules make a repeat harmless: a freeze is used once and the same freeze is answered with its original proof (Section 12.5); a push start changes a registration only when it names the push key it replaces, so the same start again answers the current registration (Section 9); a repeated app record is a no-op, and an older one is refused (`app.put` needs a later `updated_at`); a connect request keeps one pending request per sender; an erasure names the account's service key, so a repeat finds no account, or a later one with another key, and erases nothing (Section 12.7). A replayed cursor-only batch changes nothing: a cursor move to a position behind the app's cursor is a no-op (Section 8.3).
- **Switch origins:** an app or a service that connects to a switch origin it read from an `identity.json`, which the identity's owner chose, applies the classifier of Section 9: HTTPS only, port 443 unless the connecting side's operator allows another, every address after DNS resolution globally reachable, the connection made to the address checked, and redirects not followed. A service such as a merchant's server that reaches many switches should also connect through an egress proxy that applies the same rule.
- **Every response** carries `Switch-Service-Signature`, which binds the status, the server time (`Switch-Server-Time`) and the body to the exact request it answers through the hash of the request's signature (Section 13.2). A client checks it with the service key it pinned for the account, from `identity.json` or, for the signer, from its enrollment answer, and acts on no answer it can't check: without a pinned key it sends nothing but an enrollment, whose answer names the key, and the public read of `identity.json`, where it relies only on the document the identity key signed (`spec/wire-format.md` Sections 7.1 and 7.4.15). Anything else an app relies on goes in the signed body. Responses to own apps and the signer also carry the newest signed head. Responses to apps of other identities carry no `seq` and no head, so counterparties don't learn the identity's activity.

### 6.3 Storage rules

- **Inbox entries are transport.** Writers can't read, overwrite or delete them. An entry is deleted once the cursor of every target app that is still current, and not lagging, has passed it. There is no expiry: an app that stops reading shows an old last-seen time, which the signer uses to suggest removing it (Section 12.3), and removing it releases its entries, while the identity's quota bounds storage meanwhile. Lasting state lives in claims and shared records (Section 8.2), never in the inbox.
- **Lagging apps:** an app whose unread entries exceed its share of the inbox quota (the quota divided among current apps) is marked lagging in `GET /v1/{id}/apps`. Entries no longer wait for it, so one silent app can't fill the inbox for every sender. An app counts as lagging only while another current app is reading, that is, isn't marked and has unread entries within its share: when none is, none is marked (so a single current app never is), entries wait as before, and the inbox quota refuses senders, which tells them the recipient isn't reading (Section 15). A lagging mark ends when the app reads its feed. The feed then tells the app what it missed, and the app asks senders to re-send it (Section 8.2).
- **Sequence:** one monotonic `seq` per identity and generation covers inbox entries and chain items (Section 8.3). Cursor moves take none.
- **Retention:** the service keeps every claim's entries and transition proofs until the claim is finished: once it is SETTLED with no open or `unknown` attempt, the service may compact it, at once or later, to a **tombstone** holding the claim key, its state, and each attempt's ID and outcome, in a transition proof. Apps keep that proof until the later of the bounds that apply has passed: the later of the pinned deadline and their own, where there is one, plus the 30-day reconciliation window below; and, for a claim pinned to no deadline, 400 days after the proof's entry (Section 8.3). A pinned deadline where they compute none is an early pin, and they keep that proof for good. Before attempting, they compare it with the claim; in a cooperative move they upload it, and after a provider loss it is evidence that the claim was settled (Sections 12.5 and 12.6). A re-sent, restored or delayed copy of what created the obligation therefore still shows it done, and late evidence, such as the counterparty's confirmation, is still recorded on the tombstone (row 3 of Section 10.2). The tombstone also keeps the claim's deadline, the one its first attempt pinned, or none (Section 10.2). Other time conditions, such as a protocol's own time windows, never count as a deadline. Once the service's clock reaches it, no compliant app can start an attempt any more. The service still keeps the tombstone for the **reconciliation window**, 30 days after the deadline, so evidence that comes late is still recorded on it, and deletes it once its time base, with trusted time, reaches the deadline plus 30 days (Section 10.1). A tombstone without a deadline is kept until 400 days after the claim's last entry (`max_claim_age`), and deleted then the same way. The same holds for a claim that never settled, whose every attempt has failed: from its deadline no attempt can start any more, but an attempt marked failed may still turn out to have succeeded, and its evidence must name the attempt. So the service keeps it to the deadline plus 30 days too, and deletes it then; one pinned to no deadline, 400 days after its last entry. After the window late evidence can't be recorded on the claim. A claim with an open or `unknown` attempt is never deleted by age, so no unresolved obligation goes. After 400 days an app's own record of an obligation without a deadline, not its claim, stops a second attempt, so the app never deletes that record.
- **Each app's claims are bounded.** An app holds at most 1,000 attempts open or `unknown` at once (`open_attempts_per_app`), and the claims its `attempt` created, live and tombstones, are at most a quarter of the claim limit, rounded down (`claim_share_percent`). Beyond either its `attempt` is refused (`429 quota_exceeded`, `open_attempts` or `claim_share`), and the other apps keep the rest of the limit. So a compromised app can't fill the claim limit for every app. Once it is revoked, its open attempts, at most 1,000, are orphaned, and the user resolves them through another app; its finished claims and its failed ones go at their deadline plus 30 days, or 400 days after their last entry without one. Everything else the service keeps, and for how long, is in the retention table below.
- **Targeting:** envelope kids identify the target apps, and each must be that app's current receive key (Section 3.6). Each app reads only its own entries.
- **What the service keeps.** Defaults are for one identity on a shared service; an operator may raise them and announces them at enrollment (Section 6.2). "For good" in this section means for the account's life: an erasure deletes the account with everything it holds (Section 12.7).

  | Kind | Kept for | Counts against | Default limit |
  |---|---|---|---|
  | Inbox entry | Until every current target's cursor has passed it, not waiting for lagging apps (no expiry) | Inbox quota: its size plus 256 bytes; one sender identity's unread entries at most a quarter of it | 64 KiB each |
  | Unreadable entry (Section 8.2) | Until every current app's cursor has passed it | Inbox quota: 256 bytes; never refused | - |
  | Missed item (Section 8.2) | Until its app's cursor has passed it | Nothing; never refused | One per lagging app; a later miss replaces it |

The certificate and the proof, at most about 34 KB together and about 1.6 KB for an app of the test vectors, aren't counted; the record key limit bounds them | 256 KiB each |
  | Shared record key | While live; once deleted, until the service forgets it, which it may do once nothing refers to it (Section 10.3) | Record key limit: live keys only | 100,000 live keys |
  | Live claim or tombstone | Until finished, then a tombstone until its deadline plus the 30-day reconciliation window, or 400 days after its last entry without one; a claim whose every attempt failed the same way (above); never by age while an attempt is open or `unknown` | Claim limit, and its creating app's share | 1,000,000; 64 attempts per claim; a quarter of the limit created by one app; 1,000 attempts open or `unknown` per app |

- **Two quotas.** The inbox quota counts inbox entries, each with a fixed overhead so that it bounds their number as well as their bytes, and blocks only appends. It is the identity's, so **each sender's share** is capped: one sender identity's unread entries may hold at most a share of it, a policy value, a quarter by default; past it that sender alone gets `429 quota_exceeded`, so one admitted sender within its rate limit can't fill the inbox for every other while the identity's apps are offline. The storage quota counts current shared record values and blocks only writes that make them larger. They are separate, so a full inbox never blocks the record writes that drain it.
- **Per-kind limits** refuse only the write that would create something new: a live record key (a new one, or a deleted one written again), an `attempt` on a new claim key, beyond 64 on one, or beyond its app's share or open attempts (above), a contact, conversation entry or deny list entry, or an invite code. Writes to existing objects, outcomes, deletions and removals always pass.
- **Control reserve.** Control operations count against neither quota nor any per-kind limit: cursor moves, deletions and removals, claim outcomes, key registrations, app records, key bundles and renewed certificates, `identity.json` deliveries, revocation, leave, freeze, export, import and recovery uploads. An operation that would change nothing, an app record, receive key record, renewed certificate or key bundle part the service already holds byte for byte, is a no-op: a batch made only of such operations creates no chain item and no batch record, and its answer carries the current head. The service decides this before it checks the batch's conditions and permissions. That is safe, since a no-op changes nothing and returns only the head. A batch that also moves the app's cursor changes something, so it is checked in full, conditions and permissions included, and the cursor moves only if every check passes. Repeatable control mutations, an app record or receive key record that changes what the service holds (a new record, a new registration), and a deletion or removal of something that isn't there, count against their app's control rate, 60 batches a minute by default, and its operation rate. An unchanged app record or receive key record counts against no rate, also in a batch with other operations. Whether a record is unchanged, and whether something is there, is judged against the state before the batch. Cursor moves, claim outcomes on existing attempts, deletions and removals of something present, and revocation and leave are never rate-limited, so a full inbox can still be drained, an existing attempt reconciled and an abusive app revoked. The state control operations create is bounded: chain stubs by those rates and by checkpoints, which no cursor holds back from a stub 30 days old (Section 8.3); batch records' proofs by their 30 days and their IDs by those 30 days and the stubs; and the rest per app (the table above). The operator plans that capacity apart from the quotas.
- **Operation rate limit.** A batch carrying an ordinary operation or a repeatable control mutation counts against its app's rate, 3,000 batches a minute by default; other batches of control operations alone never do. With the control rate this bounds how fast chain stubs and batch records grow; old stubs may be dropped behind a checkpoint, and with them the IDs of batches whose proofs are gone (Section 8.3).
- **Rate limits per sender** and the 64 KiB envelope cap apply as in Section 7.
- **Dropping is safe.** A dropped peer copy is delivered again after `409 identity_needed`, and never at a lower version than the one dropped, so a revoked app can't take the service back to a document that still lists it by having many fresh identities push the copy out; a repeated enrollment gets the same answer. A batch's transition proofs go at the minute's sweep at a later request after 30 days, and a retry after those 30 days gets `409 conflict`, whether or not they have gone. Its ID stays as long, and also while any of the batch's chain stubs is kept. An app compares a batch ID only with the batches of the last 30 days of the chain, and the service holds every one of those IDs (Section 13.5). So the service never accepts a batch that an honest app would take for a rollback, and an app never compares an ID the service has forgotten. The ID goes once its proofs are gone and none of the batch's stubs is kept. A request is accepted only within 5 minutes of its signed timestamp, so an old batch can come again only in a new request, which only its app can sign, and apps resend a batch only in their immediate retries. So nobody can replay a batch, list changes included, which carry no expected version.
- **Not public:** nothing is ever published to a public feed.
- **Lists:** contacts, conversation entries and the deny list hold Pubky IDs. The operator can read them, as it sees every sender anyway (Section 15).

### 6.4 Errors

Error responses are JSON: `{ "code": "<code>", "message": "<text>", "current": { } }`. `current` is present where noted. **Retry** says whether the same request may succeed later unchanged.

| HTTP | `code` | Meaning | Retry |
|---|---|---|---|
| 400 | `bad_request` | Malformed request or document | No |
| 401 | `bad_signature` | Request signature invalid | No |
| 401 | `stale_timestamp` | Timestamp outside +/-5 min | With a new timestamp |
| 403 | `not_admitted` | Sender not admitted (Section 7), denied, or asking to connect where that is off | No |
| 403 | `permission_missing` | Caller's certificate lacks a required switch permission (Section 3.2) | No |
| 403 | `not_current` | Caller's app isn't current: revoked, left, or not listed in `identity.json` | No |
| 403 | `cert_expired` | Caller's certificate has expired | No |
| 404 | `not_found` | No such object | No |
| 409 | `conflict` | A condition, an expected step or version, or a receive key registration failed; `current` holds the current values | After re-reading |
| 409 | `stale_epoch` | A sealed field uses a data epoch other than the current one; `current` holds the current data epoch | After fetching the key bundle |
| 409 | `stale_generation` | An operation names a generation other than the current one | After signing it again for the current generation |
| 409 | `stale_key` | An envelope is wrapped to a receive key that isn't current, or names an `apps_version` older than an app added since; `current` holds the current receive key records of those apps, the records of added apps, and lists any that are no longer current | After sealing again |
| 409 | `stale_identity` | A delivered `identity.json` has a lower version or generation, or doesn't build on the version the service holds (Section 4.3); `current` holds that version, and for the signer's delivery the copy itself | No |
| 409 | `identity_needed` | The service's copy of the sender identity's `identity.json` doesn't list the sending app, nor list it as removed; `current` holds the version it has | After delivering the document |
| 410 | `moved` | The account is frozen; `current` holds the signed freeze (Section 12.5) | At the new service |
| 413 | `too_large` | Size cap exceeded | No |
| 429 | `rate_limited` | Too many requests | After `Retry-After` |
| 429 | `quota_exceeded` | The identity's inbox or storage quota, or a per-kind limit, is full; the answer names it | Per limit: the inbox quota frees as the recipient's apps read their feed; the storage quota after deletions; the record key limit after deletions, at once, since it counts live keys only (Section 10.3); other limits after a deletion or removal frees room |
| 503 | `staged` | The service isn't named in `identity.json` yet, or is restoring the allowlist after a provider loss (Sections 12.5 and 12.6) | Yes |
| 503 | `unavailable` | Temporary failure; or the account lost committed state and waits for a new generation (Section 6.5) | Yes, unchanged; after a loss, only at the new generation |

**Sending the same bytes again.** What a retry keeps is the body: a batch's signed operations, or an append's envelope. Every send carries a new timestamp and request signature (Section 6.1), so "unchanged" is about the body alone.

- **Kept:** the same body may be sent again after `401 stale_timestamp`, `409 identity_needed`, `410 moved`, `429 rate_limited`, `429 quota_exceeded` and `503`. After `410 moved` it goes to the service the newest `identity.json` names, or to the same one after an unfreeze (Section 12.5).
- **Final for those bytes:** `409 conflict`, `409 stale_epoch`, `409 stale_generation` and `409 stale_key` each ask for a changed request, so the same body never succeeds. The app drops the kept bytes and builds its next request from what it then reads: a new batch, with a new batch ID, or the same signed plaintext sealed again (Section 11). A `409 conflict` may mean that the batch was applied before (Section 6.1), so the app reads the current state before it writes again.
- **Every "No"** is final for those bytes too. An append answered `403 not_admitted` or `403 not_current` may still stay queued for a time, since what refused it can change (Section 11); and an app answered `403 not_current` first looks for a renewed certificate (`spec/wire-format.md` Section 7.2).

### 6.5 Operating a switch

These rules make a service a **consistent switch**, the condition of the guarantees a protocol builds on the switch. A service that breaks them is non-compliant, like one that rolls back on purpose.

- **Durable before acknowledged.** The service releases no answer that carries a `seq`, a transition proof or a signed head until the items it commits are durable: written and synced (fsync) to storage, or committed synchronously to every replica that could ever be promoted to serve the account. An asynchronous replica may serve reads for operators, but is never promoted to serve writes under the same generation. "Not replicated" doesn't allow an asynchronous failover. The confirmation of an erasure carries none of these, and is still released only once the deletion it confirms is durable (Section 12.7).
- **No restore and continue.** Any recovery that may have dropped an item the service acknowledged, such as restoring a database backup, failing over to a replica that may lag, or replaying an incomplete log, is a loss of committed state: the account must not serve under that generation again (Section 10.1). The operator tells the user, and the signer declares a provider loss (Section 12.6), at the same service or another: at the same service the account starts the next generation afresh, with a new service key.
- **The key's mark.** The service keeps, with each account's service key and apart from the state a backup restores (in a key store or HSM that holds the key), the newest head that key signed: its generation, `seq` and chain hash. The key signs nothing for a state behind that head or beside it (a fork), and the account fails stop with `503 unavailable` until the signer starts a new generation; only the enrollment that answers the next generation's pending key, and the `identity.json` naming it, go through. The mark moves with the key: whoever holds the key holds the mark. A checkpoint (Section 8.3) is a head at an earlier `seq` of the chain the key serves, not a state behind its mark: the key signs one only while the account's state is at or past the mark, and a service behind its mark signs none and drops no chain stub.
- **Failed authentications:** before a request verifies, the service trusts nothing it claims, so it limits failed authentications only by network source, an IPv4 address or an IPv6 /64, before it does any signature work. It also counts them per claimed caller (its `Switch-Identity` and `Switch-App`), for monitoring, but never refuses a request because of that count, so a flood of bad signatures that claims a victim app's App ID can't keep that app out. Limits per caller apply only to requests that have verified. (The reference prototype: it counts per source where its HTTP adapter sees the peer address; its in-process transport has no source, so there no limit applies before authentication.)
- **Public reads:** the service limits the public read of `identity.json` per network source, an IPv4 address or an IPv6 /64, with a higher backstop per account, so one source can't use up the account's budget and switch readers' lookups off (Section 4.3). A source's refused reads don't count against the backstop. A cache in front may serve the answer for up to 60 seconds. Behind a reverse proxy the source is the address the proxy reports (the reference prototype: it counts per source where its HTTP adapter sees the peer address; its in-process transport has no source, so there only the backstop counts).
- **Detecting lost state.** The key's mark catches a restore at once. Apps catch it too, as a rollback, when a head or chain item they verified is missing (Section 10.1), and the signer when a service shows an older `identity.json` than it delivered (Section 4.3). Operators should also compare each account's head after a restart with the mark, and alert on any refusal.
- **Provider-loss runbook (outline).** 1. Stop serving the affected accounts (the key's mark does this for them) and keep the old keys' marks. 2. Find the accounts affected: those whose state is behind their mark. 3. Tell their users, through the signer's operator channel, that a provider loss must be declared. 4. The signer declares it (Section 12.6), here or at another service; apps recover, upload their evidence and treat earlier obligations as uncertain. 5. Never serve the lost generation again, and keep the old service keys retired, never reused.
- **Erasure and backups.** An erasure (Section 12.7) deletes the account's service key and its mark too, so nothing can sign for the account any more. The operator lets the erased account's data age out of its backups. Until the last backup that holds it has aged out, it keeps the identity's ID and the time of the erasure apart from the backups, so a restore from an older backup erases the account again before it serves anything.

## 7. Admission

A write to an identity's inbox is accepted when one of these holds:

1. **Contact:** the sender is a contact on the allowlist. Saving a contact adds them; removing the contact removes them.
2. **Conversation:** the allowlist holds a conversation entry for the sender, because an own app wrote to it or invited it.
3. **Invite code:** the sender presents a valid invite code.

The **deny list** overrides all three. The same rule admits a sender to the directory (Section 6.2). Answers never reveal the deny list: every refusal reads the same (`403 not_admitted`, one message), whether the sender is denied, unknown, or holds an unknown, expired or used-up invite code; where connect requests let strangers deliver their `identity.json` and ask to connect, a denied sender is answered exactly as they are, and its request is simply not kept; while a provider loss stages admission, denied senders get `503 staged` like the others (Section 12.6). A denied sender holding a valid invite code still learns from its refusal that it is denied, since the code admits anyone else.

**Conversation entries:**

- **Writing to someone admits them for good.** When an app first writes to a counterparty that isn't a contact, it adds a conversation entry for that counterparty to its own identity's allowlist before sending, in parallel with the directory read a first message needs anyway. An app that can't read the lists writes the entry before its own first message to each counterparty; adding an entry that already exists changes nothing. "In parallel" bounds latency, not order: an app may also write the entry first and read the directory after it (Section 8.2). A `resend_request` adds no entry: it answers entries the service shows the app, which the app can't check, so a forged one must not admit its sender (Section 11).
- **Invites let the other side write first.** An app may add the entry before any message, which is an **invite**. At a checkout, for example, the user's app reads the shop's Pubky ID from the site (a QR code or a link, `pubky://<shop id>?switch=invite`), invites the shop, and the site passes the user's Pubky ID to the shop, which then writes first.
- **Permission:** both need the switch permission `conversation.add`, not `lists.manage`. From then on the two can keep talking, as in any conversation; the entry has no expiry.
- **Stopping it:** blocking the counterparty puts it on the deny list, which overrides every entry, and an app with `lists.manage` may remove an entry.
- **Pruning:** entries never expire on their own, so an app with `lists.manage` prunes them, for example daily, before the list fills: it removes an entry whose counterparty isn't a contact, whose last admitted append is at least 180 days old (the service records it with the entry, `last_used`, or its creation time when never used), to whom the app sent nothing in that time, and with whom no record it holds is unfinished (such as a task assigned and not yet done). A pruned counterparty is admitted again once an own app writes to it, or with an invite code; apps that see the removal in their feed (with `lists.read`) add the entry again before their next message to it. An app without `lists.read` that wrote to the counterparty keeps no such view, so its counterparty's reply may be refused until the user or that app writes again (residual).
- **Visible:** each entry records the app that wrote it. Apps with `lists.read` list entries (`GET /v1/{id}/allow`). An app's entries stay when it stops being current, so its conversations continue through the identity's other apps.
- **Limits:** a conversation entry never overrides the deny list, and it is not a contact: it admits messages, nothing else.
- **What it shows:** the operator learns whom the identity writes to or invites (Section 15).

**Spam:** a stranger can't write at all. Admitted senders are rate-limited per sender identity and per sender app, with a tighter limit for messages that trigger a push, and each identity has an inbox quota and a 64 KiB size cap per message (Section 6.3). One sender's unread messages hold at most its share of that quota, a quarter by default, so a sender that fills its share is refused while others still get in. The service never blocks on its own. It flags senders that keep hitting the limits, which `GET /v1/{id}/allow` shows, and apps may offer the user to block them. Apps should not create records of their protocol for messages from a counterparty the service has flagged, or that the user has blocked; they keep at most a count of them. A message from such a counterparty that updates an existing record is still applied.

**Invite codes** (optional), for a counterparty that the identity doesn't know yet, such as a customer scanning a shop's QR code:

- **Registering:** an app with `conversation.add` registers a code at its own identity's switch (operation `invite_code.put`): the hash of a code of at least 16 bytes from a secure random generator, an `expires_at`, a `max_uses`, and an opaque `context`, such as an order reference. The `context` is stored in the clear, so the operator reads it (Section 15): apps put in it only what they would show the operator, such as an opaque order number, never personal data. It shows the code as `pubky://<id>?switch=invite&code=<code>`. It can withdraw the code at any time (`invite_code.delete`).
- **Using:** a sender presents the code in the `Switch-Invite-Code` header. The switch checks its hash, expiry and remaining uses. A directory read with the code uses none, and such reads are rate-limited per code; an admitted append uses one, atomically with the append.
- **Then a conversation:** the first append admitted by a code also adds a conversation entry for its sender, written by the service and naming the code, so later messages need no code. The feed shows the code's `context` with the entry. The `context` is a hint attached by the recipient's service, not signed by the sender, so apps match what a message is about through its signed content, never through the `context` alone.
- **A bearer secret:** anyone who sees a code can use it until it expires, runs out or is withdrawn, so apps keep uses and lifetimes small.
- **One per order:** an app SHOULD register a code per order or per counterparty, with one use and a short expiry, minutes to hours, as a checkout needs. A shop SHOULD NOT publish a reusable code, such as one printed on a poster: whoever copies it can write to the identity until it runs out. A code with more uses is an explicit choice of the app, rate-limited per code as above, and capped by the operator's policy (`max_invite_uses`, 100 by default; `spec/wire-format.md` Section 6.2).

**Connect requests** (optional, off by default):

- **What it is:** where the identity's `identity.json` allows it (`policy.connect_requests.enabled`), a stranger's app may ask to be invited (`POST /v1/{id}/connect`). The request is content-free: the service keeps only the sender's Pubky ID and the time. The user's app shows the sender's public Pubky profile, so a request carries no text, link or other data.
- **Kept apart:** pending requests are a separate list, not inbox entries, and admit nothing. Each sender has at most one pending request.
- **When the list is full:** once `max_pending` requests are pending (50 by default, set by the user), a new sender is refused (`429 quota_exceeded`, naming connect requests), and the requests already waiting stay, so a flood can't push them out. The refusal is the same for every sender, denied or not, so it reveals nothing about the deny list; a sender already pending is still answered as pending. Apps reading the list see that it is full (`GET /v1/{id}/connect`), so the user can clear it or block senders.
- **Senders** are authenticated like any other sender (Section 6.1) and rate-limited, and the deny list applies. Identities are free, so per-sender limits don't stop a flood from many fresh ones: connect requests, and the `identity.json` deliveries of senders admitted only because connect requests are on, are also limited per account, 60 a minute together by default, and a stranger's peer copy never pushes out an admitted identity's (Section 6.3). `POST /v1/{id}/connect` answers a denied sender exactly as it answers anyone else, as pending or, while the list is full, refused, so the answer doesn't reveal the deny list. Residual risk: a request that isn't kept takes no slot, and a denied sender's isn't kept, nor is that of a sender already admitted or already pending. A sender working with a fresh identity can therefore learn whether its own request was kept, once it knows the list is one short of full (the public `max_pending` alone doesn't give the count): after it asks, the fresh identity's request is still kept only if the sender's wasn't. It learns "not kept", which it can tell from "denied" only if it knows it isn't admitted or pending.
- **No push** for connect requests unless the policy turns it on (`push`); apps show the list when the user opens them. With `push`, a request queues the apps' webhooks like an entry does, at most once per app a minute however many requests arrive.
- **Answering:** accepting is an invite, which removes the request; declining removes it (`DELETE /v1/{id}/connect/{pubky}`); blocking puts the sender on the deny list.
- **Names are unverified:** anyone can call themselves "Bitkit Support", so apps show the sender's Pubky ID prominently.
- **Filters** for who may ask, such as identities on trusted Homeservers or in a social graph, are left for later (Section 17).

**Own apps** are admitted to their own identity's inbox only for messages between own apps, of the kinds its protocol defines for that, such as `tasks.reminder`; any other kind from an own app is dropped by its recipients.

## 8. Routing and shared state

### 8.1 Routing

- Senders read the recipient's directory and wrap each message only to current apps allowed by Section 3.4.
- **Directory caching:** a sender may use a cached directory of any age, while the recipient's `identity.json` still names the same switch and generation. The sender watches that document through the Homeserver event stream, or re-fetches it in the background when its copy is more than 10 minutes old (Section 4.3). When it names another switch or generation, the sender drops the cached directory. If the new document records a provider loss since the sender's copy (its `recovery_from` is at least the generation of that copy), the sender also re-sends to the new switch the messages the old one accepted since its previous check; after a cooperative move it doesn't, because the new service imported the old one's pending entries. Each append response carries the recipient's `directory_version`; when it is newer than the cached one, the sender refreshes the directory in the background for its next send. A cached directory is also tied to the version of the recipient's `identity.json` it was read under: once the sender sees a newer version, it reads the directory again before its next send, since a renewal may have changed which apps receive which kinds (Section 3.2). Each append MUST also name the `apps_version` it was sealed for, a version of the recipient's app set that changes only when apps are added or removed. A rotated or removed app's key, or an app added since, gets `stale_key` (Section 3.6), whose answer includes the added apps' records, so a stale cache costs at most one extra round and no current app is left out.
- **With the Homeserver unreachable:** a sender that can't re-fetch the recipient's `identity.json` may still route a message on the copy it holds, whatever its age. That is safe for a message: a switch the identity has moved from answers `410 moved` (Section 11), an app removed or rotated since gets `stale_key`, and a message that a lost switch accepted is sent again once the sender sees the new document (above). An action that needs a fresh copy of that document doesn't go ahead on the held one. Which actions do is the protocol's rule (Section 4.3).
- **Refreshing ahead of rotations:** a sender that expects to write a recipient again may refresh the recipient's directory in the background once its cached receive key record is older than about a day, the default rotation interval (Section 3.6), so that its next append is sealed to the new key. This costs one directory read per active counterparty per day, off the critical path, against one refused append, re-seal and re-send on the critical path per rotation.
- Counterparties see which of the sender's apps sent each message (`from.app_id`).
- **Checking receive keys.** Before wrapping to a receive key record, from the directory or a `stale_key` answer, the sender checks:
  1. its signature, with the signing key in the app's record;
  2. that the app record's certificate is signed by the recipient identity, hasn't expired and allows the kind being sent (Section 3.4);
  3. that the app is current in the newest `identity.json` the sender holds, with that certificate;
  4. that the record's `identity` and `app_id` are that identity and app;
  5. that its `n` isn't lower than the highest `n` the sender has seen for that app;
  6. that its key isn't of low order (Section 3.6), and its kid is derived from it (Section 13.3).

  A record that fails a check is ignored, and the app counts as unreachable until a valid record is found: the sender seals the message to the identity's other apps, so one bad record never blocks them. A sender whose cached directory leaves no app that may receive the kind re-reads the directory before treating the recipient as unreachable.

### 8.2 Shared state

- **Messages are transport.** An inbox entry is deleted once every current target app has read it, not waiting for apps marked lagging (Section 6.3).
- **Shared state lives in claims and shared records.** Everything that own apps share, including apps added later, is in the claims and the shared records of their protocol; for `tasks`, its `task_lists` and `task_items` collections. Contacts and blocked IDs are the switch's own allowlist and deny list (Section 7), not records. Names and pictures come from each counterparty's public profile. State that belongs to one app alone, such as a tasks app's journal, stays in that app.
- **Shared by scope, by design:** every app holding a record's read scope can read it, including what other own apps wrote and what was written before it was added. That is the purpose of shared state: all the identity's apps of a protocol show the same state, and a new one starts with it. Encrypting per app was rejected: every record would grow with the number of apps, and adding an app would mean re-encrypting existing records for it. A compromised app exposes its scopes' data until it is removed and the keys rotate (Section 12.2). A sub-scope narrows this: an app holding only `name:<sub>` reads, of the records that `name` covers, only those under its own sub-scope, and the apps holding `name` read them all (Section 10.3). For example, an app holding only `tasks_assign:team1` reads only the records under that sub-scope.
- **Receiving:** an app that processes a message with a lasting effect writes the effect to its shared record and advances its cursor in one batch. If the record already reflects the message's `msg_id`, because another own app processed it first, the app only advances its cursor. Advancing the cursor alone, for items the app has nothing to apply, needs no shared record write. An app may apply several messages in one batch, within the batch limit, and may defer cursor moves that apply nothing and send them with its next batch, for at most a few seconds while it runs, never more than 10 seconds. It sends a deferred move before it stops reading, for example when a phone app goes to the background. The inbox keeps the entry until the cursor passes it, so a failed batch is retried from the feed. An entry whose sender can't be checked yet, for example because its Homeserver is unreachable, doesn't hold up later ones: the app processes those and keeps its cursor at the oldest entry it hasn't processed, so nothing is deleted before it is processed. After a bounded wait, which the app chooses, it MUST store that entry locally and move its cursor past it, so a long outage doesn't fill the identity's quota. An entry whose effect needs a scope key the app doesn't hold yet (Section 3.5), such as one that reads a record sealed at a data epoch whose key hasn't reached the app, or would write while the app lacks the current data epoch's key, doesn't wait for it behind the cursor: the app MUST store it locally and move its cursor past it at once. It asks for the key as Section 3.5 gives, once for all such entries rather than once for each, and processes the entry again once a key bundle brings that key. An entry stored because its sender's standing couldn't be checked, or because it waits for a scope key, is kept at most 21 days from its acceptance, judged on the service time the app verified, and at most 64 such entries per sender identity, the identity its certificate names, and 128 in all, the two kinds counted together. It drops first every such entry kept past the 21 days; then, past a sender's 64, that sender's entries accepted earliest; then, past 128 in all, one at a time, the entry accepted earliest of the sender identity that holds the most such entries, and of identities that hold as many, of the one whose newest entry is newest (accepted latest, then first stored latest). Of two entries accepted at the same time, the one first stored locally earlier is the earlier, in each of these orders. The two kinds aren't ranked: they are counted and ordered alike. It drops each without processing it and tells its protocol, which may ask the sender to send it again while the sender still keeps it (Section 11). The tie rule doesn't keep two sender identities acting together from dropping a third's entries: one that holds as many entries as the third, accepted before the third's, and another whose one entry takes the total over make the app drop the third's entry accepted earliest; a sender can make its own entries wait for a key at will, so this holds for those too. The app tells its protocol of each drop, and the protocol may ask the sender again (question 32 in Section 19). An entry that waits, for its sender's check or for a key, doesn't hold up its sender's later entries either, so a protocol doesn't assume that one sender's messages reach it in the order their inbox accepted them. It applies these bounds at every read, to entries it stored before too. So such entries take at most about 16 MiB of what the app commits at once when it restores from a backup. Re-reading entries it already processed is harmless, since it keeps their IDs (Section 11).
- **The feed never stalls.** An app whose record write for an entry hits a per-kind limit or the storage quota (`429 quota_exceeded`, Section 6.3), or would take the record over the 256 KiB limit for a shared record value (`413 too_large`), MUST store the entry locally and move its cursor past it. It writes the record once room frees. An effect the service refuses for good is handled the same way: an answer whose Retry is "No" (Section 6.4), other than `403 not_current` and `403 cert_expired`, which concern the app itself (Section 12), such as `403 permission_missing` on an operation its protocol built. So is an effect that doesn't fit one batch with its cursor move (Section 13.5), and one too large for the app to keep before it sends it or to commit with its outcome, such as one whose local writes exceed what the app's store takes in one commit: the same effect is refused again however often it is built. The app stores the entry locally and moves its cursor past it, and tells its protocol, which may build the effect again in another form; the app doesn't send the refused effect again by itself, since the same request can't succeed. A host may forget any entry stored locally. Forgetting is being done with the message: every entry stored for it goes at once, and its message stays processed so that a re-send stays a duplicate, unless none of those entries had its sender's standing checked and read as a message. A host may also release an entry whose effect's fate couldn't be known (Section 12.5) to be tried once more as a fresh receive, its message no longer processed until then. An entry released this way is handed to the protocol marked as released, so a protocol that may have compensated for the effect since declines it; the service refuses it again where an operation depends on what its first application changed, such as a record write's expected version or a claim's step; otherwise its operations, and its local writes, may apply twice. Telling its protocol is durable: the app records the notice in the same commit as the change it reports and delivers it until the protocol has kept it, so a crash never loses it; a protocol tolerates a notice delivered twice. A message whose body doesn't parse for its kind is dropped like any message that fails the recipient checks (Section 11): the app keeps its (sender identity, `msg_id`) as processed and moves its cursor past it, so one bad message never holds up later ones.
- **Entries an app can't open,** for example after a restore from a backup older than its last rotation (Section 12.4), are passed with the cursor. The app sends each entry's sender a `resend_request` for the messages accepted at that entry's time, which the feed shows, but never for a time before the time of its cursor, less the clock tolerance (Section 11).
- **Entries an app missed while lagging** (Section 6.3) are gone, and the feed tells it. When the service deletes an entry that a lagging app hasn't read, it records the miss and shows that app a `missed` item: how many entries it missed, and the first and last of their acceptance times. Like the unreadable items of a departed app (below), the item takes a new `seq`, so the app's cursor reaches it wherever it stands, and it goes once the app's cursor passes it. A later miss replaces an item the app hasn't passed yet with one covering both. On a `missed` item the app asks the counterparties of its unfinished activity records to re-send what their inboxes accepted from the later of the item's first acceptance time and the time of its cursor, less the clock tolerance, as after a provider loss (Section 12.6). The service writes the item, and the app can't check it, so the app never asks for anything accepted before its cursor's time on the item's word. It also lists its collections again, to check what it holds against the service after a gap; the service forgets no deleted key before every app it lists has read past the delete (Section 10.3), so the listing never hides a delete the app missed. It owes that listing from the commit that passes the item and makes it before it hands any entry to its protocol, a stored one included: a read stops at the item until the listing succeeds, and one whose listing fails ends there, the next read listing first. An item whose times don't parse asks for no re-send, but still owes the listing. If the protocol can't act on a re-send or missed-entries notice yet, the app keeps the notice and gives it again later; passing the item doesn't drop it.
- **Entries left unread by a departed app:** when an app is revoked or leaves, or stops being current through an `identity.json` delivery, each entry it never read and that no current app can open is added to the feed of the identity's other apps as a new, unreadable item, with its sender and acceptance time but no content. Each of them asks the sender to re-send, as above, with the same floor: never for an entry accepted before the time of its cursor, less the clock tolerance. Re-sends are deduplicated by `msg_id`. So a message sent to a lost phone's app reaches the identity's other apps. The service writes these items too, so an app acts on one only after it has verified a departure of another own app in its chain, the `leave` or `revoke` transition, and only for an entry accepted at or before it.
- **Sending:** before sending a message with a lasting effect, the app records two jobs in its outbox: delivering the envelope, and writing the matching shared record. It runs both in parallel and retries each until it completes. Where this spec has steps run in parallel, here and for the conversation entry, the directory read and the delivery of the sender's `identity.json` that a first message needs (Sections 6.1 and 7), it bounds latency and the number of requests in sequence, not order: an app may run those steps one after another, as long as the conversation entry is written before the first message is sent, and the outcome is the same. Delivery completes when the recipient's inbox accepts the envelope (Section 11). A first message to a counterparty that isn't a contact also needs its conversation entry, written before it is sent, except a `resend_request` (Section 7).
- **Verifiable copies:** a record stores, for each message it reflects, the signed plaintext (sender app ID, signature, JSON bytes) and the sender's certificate from the inbox entry. Any own app, including one added after the sender app was removed, can verify the signature independently of the app that wrote the record. Whether the sender app was current when its message was accepted was checked by the app that recorded it; A protocol whose actions can't be undone, such as moving money, needn't rely on that check: it can check the sending app against the current `identity.json` before acting.
- **Verified on use, never trusted:** an own app can write any record its scopes allow, so no app trusts a record because an own app wrote it. Before acting on a stored message, an app verifies it as it would a new one: its signature and certificate, that its sender identity is the record's counterparty and its kind fits the record, and that it names what the record is about, such as its obligation, by its own signed fields, which its protocol names for each kind, so that each record is bound to the key the reader derives with its own naming key (Section 13.3). A message whose binding field is missing, or that names something else, makes the record invalid. The sender's standing is the exception: it is checked once, when the message is recorded, against the sender identity's `identity.json` current then, and not against later versions, so a signer that purges `removed` or `renewed` entries (Section 4.3) doesn't invalidate stored evidence. A protocol may still check the sending app against the current document before acting (above). A record's status is worked out from its verified messages and, while the service holds it, the obligation's claim, never taken from a field on its own. An app that has seen a record also ignores a write that replaces a message with an older one of the same role from the same sender. Where its protocol's record holds one message per role, the app also ignores a write that drops or replaces a message it has seen in one, such as a `tasks.done`, which would make a task it saw done look open again. Deleting a finished record isn't such a write, but what the app saw stays seen, so a later write that brings the record back without it is. That holds for the app's own delete too: an app that deletes a record keeps what it saw of it, and checks a later write by another app against that. A protocol may fence an action on a record's field that is informational for status, which comes from the claims, so that a write that changes that field without a condition on the matching claim is a conformance error: an app that holds the version the write was built on ignores and flags it, and keeps the field as it was. The reader judges a write against such a rule by the conditions its operation signed (Section 13.5), which come with the write and which the service checked when it applied it, so a write the rule requires a condition of is judged by what its writer signed, not by the reader's own view of the claim. A record that fails these checks is not acted on: the app keeps the content it trusts, writes its next update on top of the record's current version, and shows the user which app signed the bad write, so the user can remove that app.
- **Apps added later** read the current shared records their scopes allow, then follow the feed. They start with the identity's full shared state and never need older messages.

- **Writing over a refused write:** an app that refuses a record write the switch shows as the record's current one keeps what it trusts, and builds its next write on that write's version to put it back; when the refused write is a delete, it names `{0, 0}`, as for a delete it holds (Section 10.3).

### 8.3 Feed and chain

- **One order per generation.** Every item at the switch has a `seq` within its generation. Chain items, which are operations other than cursor moves, `identity.json` deliveries and service transitions, also have a place in the chain (Section 13.6); inbox entries don't. A cooperative move continues the sequence and the chain under the new generation (Section 12.5); a provider loss starts both afresh (Section 12.6).
- **What an app reads:** `GET /v1/{id}/feed` returns, for each `seq` after `after`:
  - the full item, if the caller may read it: inbox entries targeting the caller, with the sender's identity and certificate, the acceptance time, and the `context` of the invite code that admitted it, if any; the unreadable and `missed` items made for it (Section 8.2); its own key bundle writes; app records and receive key registrations of its identity's apps; `identity.json` deliveries and service transitions; claim entries, if it holds `claims.read`; allowlist and deny list changes, including those the service makes itself such as an invite code's conversation entry, if it holds `lists.read`; invite code changes, if it holds `lists.read` or `conversation.add`; and shared record writes whose `read_scope` it holds, while they are current (a superseded write is shown as its stub);
  - the chain stub of any other chain item, and of every superseded one: a record write, key bundle part or app record superseded since, a renewed certificate replaced or carried since, the entries of a claim compacted or deleted since, and a forgotten key's delete. The service deletes those documents in the request that supersedes them, keeping only the stub (`spec/wire-format.md` Section 7.5);
  - nothing for other apps' inbox entries.

  Each page also returns `scanned_through`, the last `seq` it covered, including items it shows nothing for, and whether more items follow, so an app always makes progress.

  A feed page never ends inside a batch. Every app can therefore verify the chain from its cursor onward.
- **One cursor per app,** shared by its devices, written as `<generation>:<seq>`. The cursor only moves forward: a move to a position behind it changes nothing and is no error, so a batch sent again or replayed can't take it back (`spec/wire-format.md` Section 6.2). An app that wants earlier items reads the feed from an earlier position, which shows the entries the service still holds; deleted entries don't come back. A cursor from a sequence that a provider loss ended reads from the start of the current sequence, whose first item is the recovery record (Section 12.6).
- **Chain version:** this spec defines chain version 1, a linear hash chain (Section 13.6), which a service serves by default. A later version, such as a Merkle log, can be added without breaking anything (Section 17).
- **Checkpoints:** the service may drop chain stubs that are older than a checkpoint, a signed head it keeps for that purpose (Section 13.6), and that the cursor of every current app has passed or that are 30 days old in service time. It drops them oldest first, so the stubs it keeps run unbroken from the oldest one to the head, and it keeps the `seq` and chain hash of the newest stub it dropped. Only an app's cursor holds stubs back, never its reads, and only for 30 days. So the stubs from an app's verified position are kept while the chain item there is less than 30 days old, since every later stub is younger, and an app that reads without moving its cursor, or stays more than 30 days behind, can't hold chain retention back for good. A checkpoint is a head signed by the current service. The service signs one whenever the stubs it could drop would free a useful amount, by default once 1,000 chain items may go (`spec/wire-format.md` Section 9.2); how often, and at which item, is the operator's choice, since apps verify from their cursor whatever the checkpoint, but never inside a batch: the service signs a checkpoint, and drops stubs, only up to a batch's last chain item or an item of no batch, so the stubs it keeps never begin with part of a batch (`spec/wire-format.md` Section 7.4.4). So a checkpoint may lie ahead of stubs the service still keeps. An export starts at the oldest stub the service keeps, not at its latest checkpoint, so it leaves out no stub an app may still need; its checkpoint signs the `seq` and chain hash of the newest stub dropped (Section 12.5). After a cooperative move, N verifies the export's checkpoint with O's key and signs it again, at the same `seq` and chain hash, with its own. Apps verify from their cursor onward as before.
- **Pruning behind a checkpoint:** feed pages carry the service's latest checkpoint. Behind it an app keeps no chain hash: the checkpoint head stands for them, and heads at or before it are no longer compared (Section 10.1). Batch IDs don't follow checkpoints: the app compares each one for 30 days of the chain, by the service time of its stubs, and then forgets it, whatever checkpoints it sees (Section 13.5). For each finished obligation, one its kept SETTLED proof shows with no open or `unknown` attempt, the app also drops the signed claim entries whose items lie at or behind the checkpoint, and keeps the SETTLED proof. Dropping them there is allowed, not required: an app may keep a finished obligation's entries and drop them together with its SETTLED proof, when that proof's time, below, has passed. No rule depends on which it does, nor on an app showing the checkpoint it accepted. It keeps a SETTLED proof until the later of the obligation's pinned deadline and its own, plus the 30-day reconciliation window, has passed on the service clock, and without one until 400 days after the proof's entry (Section 6.3). A checkpoint at or behind the app's verified position, and not behind a checkpoint the app accepted from an earlier service, must match the chain it verified, or the service has rolled back or forked (Section 10.1). A checkpoint behind the one the app accepted before from the same service can't be matched, since the app keeps nothing behind that one, so it is a rollback too. After a cooperative move the app compares N's checkpoints only with those it accepted from N: N's first is the export's, which may lie behind one the app accepted from O (Section 12.5). Behind the one accepted from O the app keeps no chain hash, so N's checkpoints there, the export's and any later one, can't be matched and aren't compared.
- **A checkpoint beyond the verified position** is never accepted on its signature alone, since its signer is the service being checked. If the feed carries the stubs from the app's verified position, the app verifies that they extend its chain through the checkpoint and that the checkpoint matches that chain, and only then accepts it; one that doesn't match is a rollback (Section 10.1). Without those stubs, it depends on the app. The service rule above keeps them while the chain item at the app's verified position is less than 30 days old, so for an app whose verified item is that recent, that wasn't restored since, and whose devices don't share its cursor, their absence is evidence of a rollback; it judges the item's age on its own clock, with the clock tolerance. How often the app reads doesn't matter. An app whose verified item is older but that holds a signed head or a proof of its own write between its verified position and the checkpoint, from an answer less than 30 days old, has evidence too: the service keeps that item's stub behind the app's cursor, so its absence is a rollback, unless other devices of the app share and may have moved the cursor, or the app was restored since. For an app whose verified item is older, so one more than 30 days behind, one restored from a backup that hasn't yet moved its cursor and read its feed again, or a device of an app whose devices share its cursor, which another device may have moved past them, the stubs may otherwise be gone honestly, and the app has no evidence of continuity. It enters an explicit "continuity unverified" state, which is reconcile mode (Section 12.4): no automatic attempts, every obligation checked against the SETTLED proofs and claims it keeps before attempting, and the state shown to the user. It continues from the checkpoint's head only as that recovery decision, and reconciliation ends it; reconciliation checks the app's obligations, but doesn't prove the missing chain's continuity. Until then it uploads no head in a cooperative move (Section 12.5).
- **Starting point for a new app:** the app follows the feed from the first `seq` of the batch that registered its first receive key, which comes before any message wrapped to it. Its scope keys came with its approval (Section 3.5). It also lists the current records of each collection it may read. A record write it then sees in the feed applies only if its version is newer than the one the app holds, so the listing and the feed combine into one consistent state, with no pending message skipped. Listing pages need no common snapshot: every write after the starting point appears in the feed, and the newest write of each record is shown in full because it is current when read, so whatever the page boundaries, each record ends at its current value, and a deleted record ends as a delete.
- **Long-poll:** an app in the foreground keeps one feed request open (`wait=25`).

## 9. Push

1. **Start a registration.** The app sends its relay URL to its switch (`PUT /v1/{id}/push`), with no handles and no push key. If the app holds no registration there, the service mints a new **push key** for it, a signing key that appears in no public document, and answers its public half. While the app holds one, a start replaces it only when it names that registration's push key (`replaces`); otherwise the same relay gets the current registration back unchanged, handles kept, and another relay gets `409 conflict` with the current push key. So a retried start, or one replayed within the timestamp window, resets nothing. A start that names the current push key is how an app rotates its push key or moves to another relay. After a provider change the new service holds no registration for the app, so the app starts afresh.
2. **Register with the relay.** Each device of the app sends its device token and that push key to the vendor's relay. The relay returns a random, opaque handle **bound to that push key**. So the relay can't look up which identity a handle belongs to.
3. **Set the handles.** The app sends `PUT /v1/{id}/push` again with the relay URL, the handles, one per device, at most 8, and the push key, which names the registration they belong to. An identity's apps hold at most 8 handles at one relay host between them; a list past that is refused, so every handle the service holds gets its webhook. A push key that isn't the current registration's, or another relay URL, gets `409 conflict` with the current push key, and the app starts a new registration. The setting is bound to the caller and removed when the app stops being current. The handles sent replace the ones the service holds. An app that runs on several devices already keeps them in step, with its receive keys and its cursor (Section 3.6), so its handles are part of that shared state: whichever device sets them sends the whole merged list.
4. **Trigger.** When a `notify` entry targets the app, the service calls the relay webhook once per handle, with **only** the handle, signed with the registration's push key. An entry sends at most 8 webhooks toward one relay host, which step 3's limit keeps every handle within.
5. **Deliver.** The relay verifies the signature and sends the push.
   - **iOS:** a visible notification. Its extension peeks: it fetches and opens the message and runs the same checks as receiving (Section 11), without their side effects: the signature and certificate, the sender app current in a copy of the sender identity's `identity.json` at most 10 minutes old and not marked stale (Section 4.3), the kind's scopes, that the app hasn't processed the message already, which it only looks up, and the page's chain, checked on a copy of the app's chain state (Section 10.1). If they pass, it shows the message, for example "Bob requests $5"; otherwise, or when it has no such copy, or after the app found itself compromised (Section 3.6), it shows a generic notification, and nothing for a message already processed. It reads a bounded number of feed pages, and shows one generic notification for the entries past them. It writes nothing. It doesn't move the cursor, write records, change its chain state or rotate the receive key; the app processes the message when it next runs. Its feed read still updates the app's last-seen time at the service, which is intended: the app is installed and reachable.
     - **What the extension holds:** the keys of the table below, and nothing else, as long as it only shows messages. This is the default this section describes: automatic attempts wait until the app runs. Whether an app acts in the background, from its extension or from tasks the platform schedules, is the app's choice; an extension that acts, such as one that carries out attempts, also holds the keys acting needs, readable after the first unlock, and the app takes on that exposure.
     - **What a shown message leaves behind:** the text the extension shows goes into the operating system's notification store, outside the app's keys and their deletion, until the user clears it. A peeked message is still unread: the app processes it, and counts it towards rotation, only when it next reads (Section 3.6), so apps should read in the background soon after a push where the platform allows it.
   - **Android:** a high-priority data message.

**Key material of the iOS push extension.** Every request is app-signed, the peek's feed read included, so the extension needs the app's signing key. It reads keys in place from the keychain items it shares with the app (Section 3.1) and writes no key state.

| Key | In the extension | Why |
|---|---|---|
| App signing key | Yes, readable after the first unlock | It signs the feed read |
| Receive keys, current and retired | Yes, readable after the first unlock | It opens the entry it shows |
| Bundle key, scope keys, naming key | No; the app may keep them readable only while the device is unlocked | The peek reads no key bundle and writes no record |
| Identity key | Never | Only the signer holds it (Section 3.1) |

The extension runs while the device is locked, so its items use the class `AfterFirstUnlockThisDeviceOnly`. A forensic extraction of a locked phone after its first unlock therefore gets the signing key, which acts as the app until the app is revoked (it can register a receive key and read new messages, and send forged outgoing messages, Section 14), and the receive keys. A feed-only key for the extension isn't defined in this version.

**Webhook format:**

```
POST <relay URL>
{ "v": 1, "handle": "<handle>", "ts": "<rfc3339>", "nonce": "<16 random bytes>" }
Switch-Signature: push-key signature over the relay origin and the body (Section 14.2)
```

**Rules for the switch:**

- **Relay URLs:** HTTPS on port 443 only. Every connection resolves the host and refuses every address that isn't globally reachable, checked after DNS resolution, and connects to the address it checked. One classifier decides, the same for switch origins (Section 6.1): an address is usable only if the IANA IPv4 and IPv6 special-purpose address registries mark it globally reachable, and it isn't multicast; an IPv6 address that embeds an IPv4 address (IPv4-mapped, NAT64 at the well-known prefix `64:ff9b::/96`, 6to4) is judged by the IPv4 address it embeds, and the forms that hide one (IPv4-compatible, Teredo, local-use NAT64) are refused. A host with any unusable address is refused. Redirects are not followed. An operator may further restrict relays to a list it accepts, and should send webhooks through an egress proxy that applies the same rule.
- **Isolation from messages:** webhooks are sent from a background queue with a 5 s timeout and at most 3 attempts, each begun within 1 minute. A failed or slow relay never delays or fails accepting a message; the app still receives it on its next read.
- **Spam limits:** notifying writes are rate-limited per sender (Section 5.1).

**Relay rules:**

- Accept a webhook only with a valid signature from the push key bound to the handle, a timestamp within +/-5 minutes and an unseen nonce.
- Rate-limit pushes per handle.
- A handle is usable only with the push key it is bound to, which only the switch that minted it holds, so a leaked handle can't be used from another switch.
- **After a provider move or recovery** (Sections 12.5 and 12.6), apps re-register their handles bound to a push key from the new service.

**What a push reveals:** nothing about content. The relay learns that a push is due for a handle, when, and which handles share a push key, so which devices belong to one app; Apple or Google learn that the device received a push. Push keys appear in no public document, but the relay is usually the app's vendor and can still link a handle to an identity without the operator's help: the webhook comes from the switch's address, and its timing follows the messages the identity receives, which a relay that also sees other activity, such as the sender's own app, can match. A switch operator and a relay operator together link senders to devices (Section 15). Operators should send webhooks from shared egress addresses and keep no record of which relay they called for which account; relays should keep no source addresses.

## 10. Coordination primitives

The switch offers two generic primitives: **claims** and **shared records**. It never interprets what a feature means: it doesn't know what a budget, a subscription or a task list is. Features are built in apps on these primitives, so a new feature needs no change to the switch.

### 10.1 Common rules

- **Operations and transition proofs.** Every change is an **operation**: a JSON body signed by its writer (an app, or the signer) that names the object, the change and its conditions (Section 13.5). The service validates the operation, gives it a `seq`, links it into the chain and returns a **transition proof**, signed with its service key, with the resulting state (Section 13.6). Changes the service makes itself, such as recording a revocation or a recovery, are service-signed transitions in the chain.
- **Conditions.** An operation may carry conditions, checked atomically with it against the state before its batch:
  - `record_version(K) == v`;
  - `claim_step(K) == n`;
  - `server_time_in(start, end)`: the service's time when it applies the operation lies in `[start, end)`; either bound may be null.

  If any condition fails, nothing changes and the service answers `409 conflict` with the current values.
- **Batches.** `POST /v1/{id}/ops` applies 1 to 8 operations and their conditions as one transaction: all or nothing (Section 13.5). Every operation names its batch, so a service can't apply part of one without the apps noticing.
- **Server clock.** Every item records the server's time, and every response carries it. Orphan age, deadlines and time windows use it, never a device clock. For each identity it never goes backwards: the service stamps nothing earlier than the last time it committed, and a cooperative import carries that time to the new service, which continues from it. The new service takes it only on its own trusted time: it refuses an import whose last committed time, or freeze time, is more than the clock tolerance ahead of its own, and one it can't check because it has no trusted time (Section 12.5), so a faulty old service can't move its clock ahead for good. Each app keeps the highest service time it has verified. The time a `401 stale_timestamp` answer carries in `current.server_time` isn't the identity's service time: it is a hint for the retry's timestamp, which the app uses for nothing else and doesn't count as a verified service time. A signed time from the same service key that is earlier than one the app has seen is misbehaviour: the app raises an alarm. **Clock bound:** at each verified answer the app also measures the service's signed time against its device clock. While they differ by more than the clock tolerance (5 minutes), in either direction, or the highest service time it verified lies more than that ahead of the device clock, automatic attempts, those made without the user, pause and the app tells the user; manual attempts stay possible, with a warning. The app's own checks, such as expiries and a record's `updated_at`, run on the device clock and the service's on its own, so an automatic attempt never relies on two clocks that disagree. A device clock that far off the service's time base can't sign requests the service accepts anyway (`401 stale_timestamp`), so in practice the bound catches a service whose stamped time ran ahead, since it never stamps back, and a device clock that jumped since its last answer. A service time far ahead of the device clock (more than 24 hours) is shown to the user too, and bounds what the app deletes: a bound for dropping evidence the app keeps, such as a SETTLED proof (Section 10.2), has passed only when it lies before the earlier of the highest service time the app verified and its device clock plus 24 hours, so one far-future signed time can't make the app drop its evidence.
- **Trusted time.** The service keeps its newest authenticated time sample, from the operator's choice of source, such as NTS-secured NTP or Roughtime, sampled at least hourly. Trusted time is that sample plus the time elapsed since it on a monotonic clock, which a change of the wall clock doesn't move; its uncertainty is the sample's own plus the elapsed time times a stated drift bound (for example 100 ppm). The service has trusted time while its sample is at most a maximum age old (for example 24 hours) and the uncertainty is at most 5 minutes. While the wall clock agrees with trusted time within 5 minutes the service uses its wall clock; when they disagree by more, it uses trusted time and alerts its operator. Request timestamps are checked against that time, so a jump of the service's wall clock doesn't lock out apps with correct clocks, and stamped time per identity still never goes back. So service time keeps moving between samples, and a deadline that has passed stays passed however long ago the last sample was taken.
- **Without trusted time** (no sample within the maximum age, or an uncertainty above 5 minutes) the service refuses, with `503 unavailable`, exactly these, whose outcome depends on its time: an `attempt`; a write with a `server_time_in` condition; a claim outcome that only an attempt's orphan age or its owner's certificate expiry allows, that is, an outcome by an app other than the attempt's owner while the owner is current; and an append, directory read or peer delivery admitted only by an invite code, whose expiry is a time. A certificate's expiry can't be judged without trusted time, so "current" in that rule means that the newest `identity.json` lists the owner, or holds its renewal open, and that the owner is neither revoked nor departed. Deletions at a deadline wait (Section 6.3), and once trusted time is back they compare the deadline with it, never with the stamped time, which a time read without it may have moved ahead. Everything else is served as usual: reads, cursor moves, appends and peer deliveries admitted otherwise, record writes without a time condition, list and invite code changes, the other claim outcomes, deletes and removals, and revocation. Request timestamps, certificate expiry and rate windows are then checked against the wall clock, corrected by the last sample (`spec/wire-format.md` Section 7.3).
- **Rollback detection.** Every response to an own app carries the newest signed head, which commits to the chain up to its `seq`. Each app keeps the newest head it has seen, and checks that every later head and the chain items and stubs in its feed extend it, with every batch complete, no stub stamped earlier than the one before it, and no batch ID repeated less than 30 days, by the stubs' service time, after the batch that first carried it (Sections 13.5 and 13.6). Every full item in the feed must match its stub's item hash, and a feed read that reaches the end of the feed must reach every head the app has seen. A service's signed answer that contradicts itself, such as an item that doesn't match its stub or a transition proof naming another operation than the one it answers (Section 10.3), is treated as a rollback too. A head older than the newest one, from a response that was overtaken, must match the chain the app has verified, unless it lies at or behind the latest checkpoint (Section 8.3). If they don't, outside a declared provider loss (Section 12.6), the service has rolled back or forked. The app then makes no new attempts through that service, manual or automatic, and shows the conflict to the user, who resolves it by moving to another provider (Section 12.5) or, if the operator can't explain it, by declaring a provider loss (Section 12.6). Apps detect conflicting history in this way while they can verify continuity. If a restore or long absence predates retained history, they enter explicit recovery; reconciliation does not prove the missing chain's continuity (Section 8.3).
- **A service that loses committed state,** for example by restoring a database backup, must not keep serving under the same generation. Its operator tells the user, and the signer declares a provider loss, to the same operator or another. At the same operator and origin, the service starts the new generation in the existing account, afresh and with a new service key (Section 12.6). A service answers with a `seq`, a proof or a head only once what it commits is durable, and its key refuses to sign for a state behind the newest head it signed (Section 6.5): without that, a failover could lose an acknowledged attempt, and another app could get a second attempt on the same obligation authorized at the same `seq`, a fork seen only afterwards.
- **Not covered: a split view.** A service can show different apps different histories after any shared prefix, from the start or from any later point, and that isn't detected: each app checks only that new heads and items extend the newest head it has seen, and a new or restored app anchors on what the service shows it. The service signs both branches, so two of its heads at one `seq` with different hashes would prove the split, but no app compares heads with another in this version (Section 17; Section 19, question 4). A service that loses an acknowledged write and serves on is non-compliant (Section 6.5) and makes the same split; an app holding a head past the lost state sees it as a rollback, and the others don't. On a split each branch can authorize one attempt per obligation.

### 10.2 Claims

A claim tracks one thing that must happen at most once, named by its **claim key**. Every app that might act on it, manually or automatically, uses that same claim. For example, a tasks app uses one claim per task done once, and `done` means the task is done.

- **Access:** reading claims needs `claims.read` and writing them `claims.write` (Section 3.2). A protocol's apps derive a claim key from what the obligation names, blinded with the naming key, so they all find the same claim; the service treats the claim key as opaque.
- **Claim operation fields** (Section 13.5): `claim_key`, `type`, `app_id`, `expected_step`, optional `conditions`, and per type: `attempt_id` (every type), `orphan_after` in seconds (required) and an optional `deadline` on `attempt`, and on `done` its `basis` with at most one `evidence_ref`, the BLAKE3 hash of its evidence. It is required with basis `evidence`, the counterparty's confirmation, and optional with basis `owner` or `reconcile`, the app's own proof. Anything else is `400 bad_request`.
- **Server responsibilities:**
  - validate every operation and its conditions atomically, on its **own clock**;
  - reject a stale `expected_step` with `409 conflict` and the current state;
  - never interpret `attempt_id` or `evidence_ref`.

**Attempts and states.** Each attempt has an outcome: `open`, `done`, `failed` or `unknown`. The claim's state is `FREE`, `ATTEMPTING{owner, attempt_id}` (its current attempt), or `SETTLED`. These rules connect them:

- A claim becomes SETTLED as soon as any of its attempts is done, and stays SETTLED.
- It returns to FREE when its current attempt fails or is marked unknown and none of its attempts is done.
- Outcomes of other attempts are still recorded after SETTLED, so a second `done` shows up as a `duplicate`.
- Each outcome is recorded once per attempt: a repeated `done` for an attempt that is already done is answered `409 conflict` with the current state, so the rest of its batch doesn't apply; the app re-reads and writes the rest alone.

An **orphaned** attempt is an open attempt whose owner isn't current, or whose `orphan_after` has passed since its `attempt` entry, or which a new service rebuilt from uploads after a provider loss (Section 12.6); the service checks this. For these rules an owner whose certificate has expired isn't current (Section 3.2). The attempting app sets `orphan_after` to the longest its method can take to complete or fail, for example, hours for a method that settles fast and days for one that may stall. Until then, while its owner is current, no other app can resolve the attempt, so an attempt still in progress can't be taken over by another app. An owner whose certificate expired isn't current, so its open attempts are orphaned at once, whatever their `orphan_after`. The signer renews certificates well before they expire (Section 3.2), and a UI should suggest renewing an expired owner before it offers `failed`.

| # | Applies to | Entry | Allowed writer | Effect |
|---|---|---|---|---|
| 1 | FREE | `attempt` | Any app with `claims.write` | Attempt a opens; ATTEMPTING(writer, a). If an earlier attempt is `unknown`, or was resolved by an app other than its owner (`failed` or `unknown`), a is flagged `possibly_duplicate` |
| 2 | Open or `unknown` attempt a; or a `failed` attempt a of a claim rebuilt from uploads after a provider loss (Section 12.6) | `done`, basis `owner` | Owner of a | a done; claim SETTLED; `duplicate` if another attempt was already done |
| 3 | Open, `unknown` or `failed` attempt a, also on a tombstone | `done`, basis `evidence` | Any app with `claims.write`, citing `evidence_ref` | As row 2. Before writing, the app verifies the evidence by its protocol's rules. |
| 4 | Open, orphaned attempt a | `done`, basis `reconcile` | Any app with `claims.write`, after the user confirms | As row 2 |
| 5 | Open or `unknown` attempt a | `failed` | Owner of a; or, for an `unknown` or orphaned open attempt whose owner isn't current, any app with `claims.write` after the user confirms | a failed. If a is the current attempt and none is done: FREE |
| 6 | Open, orphaned attempt a, claim not SETTLED | `unknown` | Any app with `claims.write`, after the user confirms | a unknown; FREE |
| 7 | SETTLED | `attempt` or `unknown` | - | Rejected |

- **Attempts never expire.** Orphan age only allows reconciliation (rows 4 to 6); it never frees the claim by itself.
- **Finished claims** may be compacted to tombstones, which keep their outcome until 30 days after the claim's deadline, the reconciliation window, or 400 days after their last entry if it has none (Section 6.3). A claim whose every attempt failed is kept as long, so late evidence, such as the counterparty's confirmation, can still correct it (row 3).
- **Per app:** the app whose `attempt` creates a claim is its creator, and the claim counts against that app's share of the claim limit, a quarter by default; an app holds at most 1,000 attempts open or `unknown` at once (Section 6.3).
- **User confirmation** in rows 4 to 6 is an app rule; the service can't check it.

### 10.3 Shared records

A shared record is a small piece of encrypted shared state, readable by every own app holding its read scope, including apps added later.

**Shared record** (a signed `record.put` operation, Section 13.5): `{key, collection, read_scope, write_scopes, expected_version, value_sealed, app_id}`.

- **Policy:** one `read_scope` and one or more `write_scopes`, fixed at creation. A writer needs any one of the write scopes. Values are sealed under the read scope's key (Section 13.4), so writers also hold the read scope. The service only compares scope strings with the caller's certificate, with one rule of hierarchy (Section 3.3): a scope `name` covers every sub-scope `name:<sub>`, so a `name` holder reads and writes every policy naming one of its sub-scopes, and a `name:<sub>` holder only its own sub-scope's; for example, `tasks_assign` covers `tasks_assign:team1`. A protocol's collections have fixed policies.
- **Keys are checked at creation.** A record key is derived from its collection, its blinded natural key and the hash of its policy (Section 13.3). The operation that creates a record carries those inputs (`id_inputs`); the service recomputes the key with the operation's policy and rejects a mismatch. A key can therefore only ever hold the record it was derived for, and no app can occupy it with a different policy. The service sees the collection name and the natural key blinded with the naming key (Section 13.3), so the stored key names neither the counterparty nor the request; equal inputs still link related records, and a live operator links them to counterparties through batches and timing (Section 15).
- **Versions:** a record's version is the `seq` of the write that produced it, written as (generation, `seq`). Versions are ordered by generation, then `seq`, so they only grow across the account: any write in a later generation is newer than every write from an earlier one, and a `record_version` condition names both.
- **Write:** compare-and-swap. The operation names, as `expected_version`, the version the writer read, or 0 for none, which creates the record; the service gives the new version. Policy and collection are fixed at creation; later writes repeat them and the service checks they match. `expected_version` 0 matches a record that is absent, forgotten or deleted, and carries `id_inputs`. A writer that holds or follows a delete names `{0, 0}`: a delete it holds, or one the switch shows as the record's current write though the app refused it (Section 8.2). So it never has to know whether the service has forgotten the key, which would refuse the delete's own version for good once it has.
- **Sealed value:** up to 256 KiB, padded to a size bucket (Section 13.4). The service reads only its data epoch and scope, and the bucket, never the content. The AAD binds the record key, so a value can't be moved to another record.
- **Read:** needs `read_scope`. Returns the signed operation that wrote the current version, with the writer's certificate the service checked that write against and the transition proof that gives that version and dates it, both of which the service keeps with the record for as long as that write is current, whatever its batch's proof retention (Section 6.3). List pages and a `409` answer carry them too, and an export carries them with the record (Section 12.5). A record taken from a recovery upload after a provider loss has no proof (Section 12.6).
- **List:** by collection, in pages ordered by record key (`after` is the last key of the previous page), returning the current records the caller may read and the `seq` each page is current at.
- **Accepting a record write.** The service only compares scope strings and gives every version, and a sealed value's AEAD shows only that some holder of the read scope's key sealed it. So an app checks every record write it reads, from the feed, a read, a list page, a `409` answer or a re-read after an upload, before it acts on it:
  1. The operation's signature verifies with its writer's certificate, signed by the identity key and naming the operation's `app_id`. The app finds the certificate in the read, in its own state, or in the records of the identity's apps it keeps from the directory and the feed.
  2. The writer had standing at the write's time: in the own `identity.json` the app holds (Section 4.3), the certificate is listed; or it is an earlier certificate of a listed app, while its renewal is open or for a write before the renewal closed; or it is a removed app's, for a write at or before its `distrust_from`. Only a transition proof or a verified stub dates a write. A proof of an earlier generation, which a switch keeps with a record after a key change or carries after a cooperative move, dates it too when it verifies with the key the newest `identity.json` lists for that generation in `service_keys` (Section 4.3). An earlier certificate of a listed app counts only for a write so dated before its `until`, or while `until` is null: a write by it that nothing dates has no standing, so a switch can't pass off a write after a reduction's cutoff as an old one by withholding its proof. A removed app's write that nothing dates is doubtful, so no automatic attempt relies on it (Section 12.2). A certificate that had expired at the write's time doesn't count.
  3. The key, collection and policy are those of the record read, the policy is the collection's fixed one, as its protocol defines it, the sealed value's scope is the read scope, the writer's certificate holds one of the write scopes, and a create's key derives from its `id_inputs`.
  4. When the app holds the write's chain stub, from the feed, the stub's item hash is the operation's (Section 13.6).

  The version comes only from a transition proof that names the operation, by its stub's item hash and the record key, or from the write's stub in the chain the app verified. Any other version, such as one in a read without a proof (an upload after a provider loss) or from an earlier service's proof, is the service's word: unauthenticated. It must still be in the write's own generation and after the version the write signed as `expected_version`. A write replaces the one an app holds only if it is newer: by number when both versions are authenticated, and otherwise by what the writes signed. A write whose version is unauthenticated must be built on the held version or a later one, and one held with an unauthenticated version is known only to be after the version it was built on. So a service can't pass an older genuine write off as newer. A write is a delete only when its sealed value opens to an empty plaintext. A write that fails a check is ignored and shown with the app it names (Section 8.2), and signed evidence of misbehaviour, such as an item that doesn't match its stub, is a rollback (Section 10.1). An app that doesn't know the writer yet reads its own `identity.json` and directory again first. A read carries the certificate the service checked the write against, kept with the record, so a renewal or a revocation later doesn't change what the write is judged by: an earlier certificate counts for a write its proof dates before the renewal closed, or while the renewal is open (check 2), and an app that reads later still takes the writer's earlier writes under a scope a renewal dropped, since the proof stays with the record. Only such a write needs a date: one by a listed certificate, or by an earlier certificate while its renewal is open, counts without one. Since `identity.json` lists the earlier generations' keys, an app added after a move or key change dates such a write as any other app does. The AAD binds the record key and scope; the operation's signature binds the writer, so the AAD needs nothing more (`spec/wire-format.md` Sections 6.2 and 7.4.9).
- **Delete:** a write whose sealed value is empty. It passes the same checks as any write, and the version keeps increasing.
- **Forgotten deletions:** the service may forget a deleted key once nothing refers to it: its current write is the delete, the cursor of every app the held `identity.json` lists, neither revoked nor departed, is at or past the delete's `seq`, lagging or not and registered here or not, so every app that may still read the record or upload it after a provider loss has seen the delete, no divergent upload names the key (Section 12.6), and the account isn't frozen, since an export carries it. A forgotten key's delete keeps only its chain stub. A listing shows only the records the service holds, so an app that hadn't read the delete would keep the record; forgetting is the service's choice, an app that stops reading only delays it, and removing that app frees its keys. The wait is per app, not per device: devices that share an app's keys share its cursor and must share its state too (Section 3.1), or a device behind the shared cursor keeps a forgotten record live. A record created again at that key, with `expected_version` 0, gets a newer version than any the key had, so it still looks newer to every app. Only live keys count against the record key limit (Section 6.3).
- **Current state only:** the service keeps each record's current value; earlier writes leave only their chain stubs (Section 6.3).

## 11. Delivery

| State | Meaning |
|---|---|
| Queued | In the sender's local outbox |
| Accepted | The recipient's inbox returned an `entry_id` and `accepted_at`. Delivery is complete; it doesn't mean an app has read it |

A protocol may add states of its own.

- **No acknowledgements.** The inbox keeps an entry until every target app that is still current has read it, however long that takes, unless the app is marked lagging (Section 6.3). A protocol's replies carry its flow, such as a `tasks.done` answering a `tasks.assignment`; nothing else confirms delivery.
- **Retries until accepted:**
  - The outbox is durable. The app retries with backoff whenever it runs: on start, on returning to the foreground, when the network comes back, and in background time the platform gives it. It reuses the envelope bytes and so the `msg_id`, and retries `503` answers, including `staged`, and `429 quota_exceeded`.
  - A send answered with `stale_key` is sealed again to the current receive keys, with the same signed plaintext and so the same `msg_id`.
  - A send answered with `410 moved` waits until the recipient's `identity.json` names the new service, then goes there. If the freeze is cancelled instead (Section 12.5), the old service accepts writes again, and the sender retries it.
  - A send answered with `403 not_admitted` or `403 not_current` may stay queued and be retried with backoff, although the same request can't succeed as things stand (Section 6.4): admission can change, when the recipient adds a contact, invites the sender or writes to it again (Section 7), and so can the sender's standing, when it takes a renewed certificate (Section 3.2). It stays queued for at most 30 days from the first such answer. Then the app deletes the message, its plaintext included, from the outbox and tells its protocol that it wasn't delivered. A protocol may set a shorter time.
- **Queued again by its signer:** an app may queue again a message it signed itself, from the signed plaintext it stored, with those bytes and so the same `msg_id`. This is for a message no outbox holds although the app's records show it sent: a batch that queues a message puts it in the outbox only with the batch's answer, so after a restore from a backup taken while that batch was kept unanswered, a record the batch wrote may store the message while no outbox does. The copy goes as any queued message. A recipient that processed the message drops it as a duplicate only while it keeps the pair, at least 30 days from the first acceptance, which comes after the message's `created_at` less the clock tolerance; so the app queues and delivers the copy, and any re-send of it, only until 30 days from that time. Past it, the app queues nothing; a copy still undelivered then is given up, and the app tells its protocol once that it wasn't delivered. A message whose delivery the app gave up is not queued again.
- **Provider changes:** pending entries go to the new service in a cooperative move (Section 12.5). After a provider loss, entries the old service held are gone, and the recovering apps ask their counterparties to re-send (Section 12.6).
- **Deduplication:**
  - The server recognizes a repeated append while it still holds the entry (Section 6.1).
  - Each app keeps processed (sender identity, `msg_id`) pairs with the message's hash durably, for at least as long as senders answer re-sends (30 days from a message's first acceptance) plus clock tolerance. A second message with the same pair and different bytes is rejected and shown as a conflict.
  - A pair goes sooner only in these ways: a host releases an entry stored locally, whose message is no longer processed until it is tried again, or forgets one none of whose entries had its sender's standing checked and read as a message (Section 8.2); a restore holds only the pairs its backup carries, so none made after the backup was taken, and none at all from a backup that carries no pairs, which reconcile mode covers (Section 12.4); and a protocol forgets it. A protocol that gives up what a message brought, for example to stay within a bound on its own state, may have its app forget that message's pair, in its own receive step, with that step's commit, or with its own writes outside one, never while an entry stored locally or an effect kept to be sent holds the message (Section 8.2). From then on a re-sent copy is processed again as a new message, and a copy with other bytes is no conflict. The protocol bears that: the app's deduplication no longer covers the message, so the protocol must not apply it twice itself, through its own state or the records it reads.
  - Shared records list the `msg_id`s of the messages they store and of at most 16 others they reflect, the newest, so a second own app doesn't apply a message twice. Older IDs are dropped, and each app's own processed pairs cover them, so a record stays bounded however many messages repeat a role it holds; a message a record stores counts as reflected whether or not the list names it.
  - Deduplication and the conflict check hold per reading app: each app judges a (sender identity, `msg_id`) pair by its own processed pairs and the records it reads. A sender that sends different messages under one `msg_id` to different own apps is noticed only by an app that sees both, and a copy that reaches an app past its window, or an app added later, is judged by the records alone.
  - A cursor advances only together with, or after, the shared record write, or after the app has stored the entry locally because the write can't be made yet (Section 8.2).
  - Rollback to an older backup and external effects are handled by reconcile mode, claims and the journal (Section 12.4).
- **Removed senders:** recipient apps check every sender app against the sender identity's `identity.json`. A message from an app listed in `removed` is rejected if the recipient's inbox accepted it after its `distrust_from`; a message from an app in neither `apps` nor `removed` is rejected. A message carrying an earlier certificate listed in `renewed` is accepted while its renewal is in progress or if the inbox accepted it before `until`, and a message whose certificate had expired when the inbox accepted it is rejected. The feed carries the acceptance time. `distrust_from` and `until` are times on the sender's service, while `accepted_at` is stamped by the recipient's, so these comparisons allow the clock tolerance (+/-5 minutes) against the sender: a removed app's message counts only if the inbox accepted it at least 5 minutes before `distrust_from`, and a message carrying a renewed certificate only if it was accepted more than 5 minutes before `until`. A renewal isn't a distrust event, so the signer adds the tolerance to `until` (Section 3.2), and recipients then reject only messages accepted after the service took the app's new record, or, for a reduction, the renewing `identity.json`. A re-sent copy (below) is judged at its new acceptance, like any message: only the app that signed it can append it again, since recipients check that the entry's certificate is the signing app's, and a copy a removed app re-sends after its `distrust_from` is rejected however old the message.
- **Equivocating senders:** once an app has seen a sender identity equivocate, two `identity.json` documents at one version with different bodies (Section 4.3), it processes no message from that identity: neither document can be trusted to say which of its apps are current, so the sender can't be checked. The app holds such an entry like any whose sender can't be checked yet, stores it locally and moves its cursor past it after the bounded wait (Section 8.2), and tells the user. A stored entry stays unprocessed while the equivocation stands.
- **Re-sends** are the protocol's: a message kind that asks a counterparty to send again what it sent, with the limits the protocol sets; this spec calls such a kind `resend_request`. The lifecycle of this spec relies on one for entries a provider loss or an old backup lost (Sections 12.4 and 12.6).

## 12. Lifecycle

### 12.1 Adding an app

1. The app generates its keys and asks for a Pubky grant, with an app request signed by its signing key and bound to the auth request (Section 3.2). The signer checks the request, shows the user the App ID it derives, its scopes and the capabilities, which must be exactly the app's own paths (Section 3.4), lets the user decline the paths its protocol adds (Section 3.4), and refuses an App ID it revoked or saw depart, or that is listed with other keys. It approves it, and the one approval carries the grant, for the capabilities the user allowed, the app's certificate with its scopes and bundle key, and its scope keys and the naming key, sealed in a key bundle to that bundle key (Sections 3.2 and 3.5). The signer delivers `identity.json` listing the app to the switch, and publishes that version once the service accepts it (Section 4.3).
2. In one batch with the switch, the app delivers its record and registers its first receive key (Section 3.6). An app whose protocol needs public data, such as a tasks app that publishes its boards, also publishes the record on the Homeserver.
3. The app reads the current shared records its scopes allow, then follows the feed (Section 8.3). It starts with the identity's full shared state. No other app needs to be online.
4. Senders include it at once: an append sealed for an older app set is answered `stale_key` with the new app's records, and the sender seals it again (Section 8.1).

### 12.2 Revocation

1. **Revoke at the service.** The signer calls `revoke`. Immediately, the service:
   - rejects every read, write and push from that app;
   - stops serving it entries;
   - removes its record and receive key record from the directory;
   - rejects envelopes wrapped to its receive keys with `409 stale_key`;
   - withdraws the invite codes it registered (Section 7).

   Every Pubky grant of the app, each naming its record path, is revoked too, so it can no longer write its Homeserver record: the signer's host revokes them on the signer's alert, or the user does (Section 3.4). The signer and the service keep the App ID for good, also once it is purged from `removed`: it is never approved, listed or served again, and a key that once was the app's stays refused even if the user restores the app from a seed and asks again (Section 3.1). Its open attempts remain, orphaned once it is revoked, and so do its `unknown` ones, for the identity's other apps or the user to resolve (Section 10.2). So before the user revokes an app that owns attempts open or `unknown`, which `GET /v1/{id}/apps` lists, the signer shows how many, and the user may revoke it all the same: a revocation is never held back, since it may answer a compromise. Its conversation entries stay, so its conversations continue through the identity's other apps (Section 7).
2. **Rotate keys.** The signer stores a new key bundle for each remaining own app, holding only its scopes' keys for data epoch e+1 and any earlier epochs it lacks (Section 3.5). Storing the bundles first means writers have the new keys before they are required.
3. **Publish.** The signer delivers `identity.json` with a higher version, the app moved from `apps` to `removed` with its `distrust_from` (the revocation time, or an earlier time the user picks after a compromise), and `data_epoch` increased to e+1, to the service, then publishes it. From then on, the service accepts sealed fields only at data epoch e+1, and other identities' apps stop using it. Own apps treat every chain item the app wrote after its `distrust_from` as doubtful: no automatic attempt relies on it.
4. **Clean up.** The signer deletes the app's Homeserver record, if it has one; its grants are revoked as step 1 says.
5. **Counterparties** stop wrapping to it at their next send, when the service answers `stale_key`. If ciphertext wrapped to it before the revocation leaks, the departed app can still decrypt it with any receive key it hasn't deleted. Messages from it accepted later than 5 minutes before its `distrust_from` are rejected (Section 11). Own apps also deliver the new `identity.json` (`PUT /v1/{id}/peers`, Section 6.1) to the switches of the counterparties to which they sent a message that was accepted in the last 30 days, the time senders keep sent messages (Section 11), so those switches stop admitting the revoked app at once. Each own app delivers when it sees, in its feed, an `identity.json` delivery that adds an app to `removed` or closes a renewal (Section 3.2), and only to a switch whose copy is older, by the `known_version` it last answered (Section 6.1), so most deliveries are skipped. The delivery is at least once: an app that can't tell whether it already delivered for a removal or a closed renewal, such as the first one it judges, delivers again, and a delivery that fails stays owed until it succeeds. A repeated delivery is harmless: a switch that holds that version takes it as a no-op (`spec/wire-format.md` Section 7.4.5).

**What the revoked app keeps:** everything it already read, including the scope keys for data epochs up to e, whether from its approval or from bundles, and the naming key, which doesn't rotate (Section 3.5). The service stops serving it immediately (step 1). After step 3 it can't read shared records written later, even if the service or a leaked backup hands them over. Older data is not re-encrypted.

**Reductions rotate too.** A renewal that removes a scope with keys rotates the data epoch the same way, steps 2 and 3 with the app kept: its bundle for e+1 is made for its new certificate and lacks that scope's key, and the renewing delivery raises `data_epoch` (Section 3.2). So the reduced app can't read data under the removed scope written after that delivery.

### 12.3 Leaving and inactivity

- **Clean leave** (the user logs out or disconnects the app): the app calls `leave` and then deletes its keys. The service treats it exactly like a revocation, records the departure (listed by `GET /v1/{id}/apps` and included in exports, so the departed app can't come back from a stale record) and flags it for rotation. When the signer is next online, it revokes the app's Pubky grant and completes steps 2 to 4 of Section 12.2, with the departure time as `distrust_from`; the App ID is kept for good, as after a revocation. Deleting keys can't be verified, so a leave always leads to a rotation. Until then `identity.json` still lists the app, so counterparties may still act on its records. An app that publishes a record on the Homeserver therefore leaves in two steps where it can: it deletes its Homeserver record and calls `leave`, and deletes its keys only after the signer has published the app as removed and counterparties' 10-minute caches have passed. A delete that fails holds back neither an immediate leave nor a leave after a compromise (Section 3.6): the app calls `leave` all the same, publishes nothing from then on, and the signer deletes the record at its clean-up (Section 12.2 step 4). An immediate leave, for example on uninstall, warns the user that counterparties may still act on its record until their cached copies expire.
- **Silent leave** (the app is uninstalled, or every device is lost or wiped): nothing reports it.
  - The service records each app's last-seen time, and the signer lists them (`GET /v1/{id}/apps`).
  - The signer app decides when to suggest removing an app that hasn't been seen for a while; 90 days is a reasonable default. Nothing is removed automatically, and removal is a normal revocation.
  - Every certificate carries `expires_at`, 1 year after it is issued by default and at most 2, which the signer renews for current apps at its next run once less than half the lifetime remains, over several runs when many are due at once (Section 3.2). The service rejects expired certificates, so an app nobody has removed stops being served once the signer stops renewing it.
- **Reinstalling:** a reinstall that can't restore the app's keys and state enrolls as a new app, and the old app is removed. Keys left in platform storage (on iOS, keychain items can outlive the app) are deleted unless the app restores its full state with them.

### 12.4 Restore

- **Backups** are the app's responsibility: whether it keeps one, where, and how. Keeping it in the app's private Homeserver folder (Section 4.1) is an option, not a requirement. Whatever the app chooses, a backup is encrypted under a key that the app or its user holds, never one derived from a Shared Data Key, since every app with that scope could otherwise read the backup's signing key, and it is best refreshed at every receive key rotation (Section 3.6). A backup that holds the signing key lets whoever reads it register receive keys and read new messages until the app is revoked (Section 3.6). Apps should therefore keep the signing key out of routine backups, or encrypt it under a separate key the user holds, so that a leaked backup is a confidentiality incident, not an impersonation. An app without a backup that loses its state joins again as a new app (Section 12.3).
- **First, is the previous device still yours?** Before restoring, the app asks the user whether the device the backup came from is still in the user's hands. If it was lost or stolen, a restore would give the new device the same signing key as whoever holds the old one, so a restore alone doesn't cut off a thief. The user revokes the old app instead (Section 12.2, with `distrust_from` at or before the loss) and adds this device as a new app (Section 12.1), with new keys or the next index of a derivation profile (Section 3.1); the old app's open attempts become orphaned and are resolved as Section 10.2 says. Only for a device the user still holds, or one known to be wiped, does the restore go on.

1. **Restore:** the signing key, bundle key, receive key, scope keys and naming key come back, and the app reads its feed from its backed-up cursor. Operations stay in the chain, so the feed shows every claim entry since the backup and the current value of every shared record written since; an entry of a claim compacted since shows only as a stub (wire 7.5, 6.8), and the claims themselves are read in step 2.1. A backup that names a lost provider follows the newest `identity.json` to the new one first (Section 12.6).
   - **Older than the retained history:** if the service has checkpointed past the backup's position and dropped the stubs behind it, the app can't verify continuity from the backup and continues from the checkpoint only as a recovery decision (Section 8.3); this reconcile mode covers it, and its end ends that state.
   - **Certificate:** if its backup predates a renewal it took, the app takes the certificate its `identity.json` lists from its own app record (Section 3.2 step 3) before it sends anything or reads its key bundle parts, which name that certificate (Section 3.5).
   - **Receive keys:** the app reads its current receive key record from the directory. If its restored key is the current one, the app continues with it. If not, because it rotated after the backup, it registers a fresh key before reading the feed. Entries wrapped to keys it doesn't hold, and its own earlier registrations of them, are passed, and the app asks their senders to re-send (Section 8.2); the senders seal those messages again to the new key.
   - **Registrations since the backup:** every registration after the backup's newest key whose kid the app doesn't know may be its own or a thief's. The app asks the user whether it ran on this device after the backup, and makes no attempts until the answer; a "no" is a compromise (Section 3.6).
   - **Stored entries:** a restore from a backup taken before an entry was forgotten or dropped brings the entry back; the app applies the bounds of Section 8.2 to it again and tells its protocol again.
2. **Reconcile mode:** it makes **no new attempts** until these steps have run:
   1. Fetch the shared records it uses, and the claims of the obligations in records that aren't final.
   2. Mark as uncertain any attempt of its own, seen in the feed or the claims, that is missing from its restored journal, on any obligation its records name. Mark as uncertain too every attempt its restored journal shows unfinished and the claim shows still `open` or `unknown`, whatever its journal stage: the backup may predate the attempt, so a protocol's rule for an attempt a crash interrupted doesn't apply. Resolve those through the history of the method that carries attempts out, as far as that method declares it authoritative across a restore: any record of the attempt settles it, and an empty history means "never started" only for such a method, within its retention. Otherwise they stay "may be done", resolved by evidence or by the protocol's reconciliation; the app never writes `failed` for them on its own.
   3. Rebuild derived state, such as a protocol's running totals, from the shared records and claims.
   4. Resume. Reconcile mode ends once these steps have run and the journal holds every own attempt they found, even if some are still uncertain. From then on uncertainty is per obligation, as in Section 12.6: an obligation with an uncertain attempt stays "may be done" until that attempt resolves, and every other obligation is attempted as usual.
3. **Recoverability:**
   - **Always:** claims and shared records, so every lasting effect of a processed message.
   - **If they still exist:** inbox entries after the backed-up cursor.
   - **Best effort:** messages the counterparty still has (`resend_request`).
4. **What the app shows:** attempts missing from its journal, and restored ones its method's history can't account for, are "may be done" until resolved. Until then there is no automatic attempt on their obligations, and a manual attempt on one only after the user confirms that it may already be done; other obligations aren't held back.

### 12.5 Moving to another provider (cooperative)

1. **Enroll:** the signer enrolls the new service N with the current `identity.json` and the App IDs it revoked or saw depart, which N keeps as tombstones from the start (Section 12.2). N stays staged: until it holds the `identity.json` that names it, it accepts only the import and uploads, and answers everything else with `503 staged`.
2. **Freeze:** the signer sends O a signed freeze naming N's URL and service key, the next generation g+1, its `issued_at` and a random nonce. Before it does, it completes the rotations that departures still owe (Section 12.3), so N never has to take a pending departure on O's word, and it checks that N's announced import limit is at least O's (Section 6.3); otherwise it doesn't move. It keeps the signed freeze before it sends it and sends those same bytes again until it has an answer: O answers the same freeze again with its original proof, and any other freeze while it is frozen with a conflict naming the freeze it holds, so a lost answer never strands the signer. A freeze is used once: one that an unfreeze cancelled is never applied again, so a replay can't freeze O after an abort. A move waits while admission is staged after a provider loss (Section 12.6 step 2): O refuses the freeze until the lists are restored or the signer ends the staging, since an export doesn't carry staged admission. From then on O's chain is final: apps can still read it, but it rejects every operation, late outcomes included, and answers inbox writes with `410 moved`, carrying the signed freeze. Feed pages of a frozen account carry the signed freeze too, so an app that only reads, with its cursor moves deferred (Section 8.2), learns of the move and uploads its evidence (step 3). O's public read of `identity.json` answers with its last document and the signed freeze, so a reader holding an old document that names O follows the freeze to N (Section 4.3). O keeps answering it so, after the move, for at least the identity's record age limit (90 days by default), after which no app record from before the move is used (Section 4.2) and the signer may erase the account there (Section 12.7). Apps queue their writes, including late outcomes, and submit them to N after step 4; senders hold their messages (Section 11).
3. **Export and verify:**
   - **Uploads:** after the freeze, apps read O's feed to its end, then upload to N their newest signed head and the evidence they hold. Every write an app sends O meanwhile gets `410 moved` with the freeze, a request for a full key bundle included, so nothing it asks of O is lost with the export: it asks N again once it follows the freeze. What they upload: the SETTLED and tombstone proofs they keep, through the later of each obligation's pinned deadline and their own plus 30 days, the record versions they hold, with O's transition proofs, and the proofs of their own attempts still open. An app whose continuity is unverified (Section 8.3) uploads no head until it has reconciled, since it hasn't verified the chain the head would vouch for. Reading O's feed to its end means verifying O's chain from the app's verified position up to the freeze transition, O's last item, so the head the app uploads vouches for a chain it checked, and the app knows which of its batches O applied. It needn't process the entries on the way at O, where it can write nothing: it processes them at N, which imports the pending entries and the app's cursor and continues O's sequence (step 4).
   - **Manifest:** the signer reads O's export manifest (`GET /v1/{id}/export`). O exports only while frozen, builds the export once per freeze and answers every retry the same way. The manifest is signed with O's service key and names the signed freeze, generations g and g+1, the last committed service time, the signed head the export ends at, and the chunks: each chunk's ID, length, BLAKE3 hash and the range of parts it holds, at most 1 MiB each. The parts cover every chain stub O still keeps, from the oldest, with the current value of each object, claims and tombstones, shared records with the transition proof that dates each one's current write, apps with their records, receive key records, key bundles, cursors and last-seen times, departures, pending inbox entries, contacts, conversation entries, the deny list, invite codes, connect requests, peer copies of `identity.json`, and the version floors dropped peer copies left (Section 6.3), so N refuses an older delivery as O did. Each operation travels once: a shared record names the chain item that holds its operation instead of carrying it again, and no batch proofs travel, since they serve only retries at O; N refuses an export that carries any. Every part fits one chunk, however long the account has lived: an app's key bundle parts, a live claim's entries and a record's divergent uploads each travel as parts of their own, and a signed operation is at most 512 KiB (Section 13.5), so N can take every account the limits allow (`spec/wire-format.md` Section 10.3). The manifest's checkpoint is a head O signs for the newest stub it dropped, at the `seq` and chain hash it keeps for it (Section 6.3). O drops stubs oldest first, so that is the chain item just before the oldest stub it keeps, and its chain hash is that stub's previous chain hash; there is none when O keeps the whole chain. It needn't be O's latest checkpoint, which may lie ahead of stubs O keeps (Section 8.3). So every app whose stubs O's cursor rule keeps still finds them at N.
   - **Chunks:** the export goes from O to N directly, not through the signer's device. The signer signs an **export transfer** (`spec/wire-format.md` Section 3.11): the authorization, under the identity key, naming the freeze, the manifest, O (its origin and the account's key there) and N (its origin and the key the freeze names). It starts the import at N with the manifest, the signed freeze and the export transfer (`POST /v1/{id}/import`). N checks that the freeze names it, that O's service key, as N's `identity.json` names it, signed the manifest, and that the export transfer is for this move; it then fetches each chunk it lacks from O (`GET /v1/{id}/export/chunks/{chunk_id}`), presenting the export transfer and signing each request with its own key for the account, checks it against the manifest and stores it. O serves the export to N only under an export transfer the identity signed that names its freeze, its manifest, itself and the next service the freeze names, and only to that service's key. N answers with the chunks it still lacks, and why it stopped, if it did. A production N fetches in the background once it has answered the import start, and the signer polls the import status by sending the same start again, which answers an import in progress with its status, until no chunk is missing or N names why it stopped (the reference prototype: it fetches before it answers, so that call lasts as long as the transfer; `spec/wire-format.md` Section 10.4). **Fallback:** the signer can still fetch each missing chunk from O itself and store it at N (`PUT /v1/{id}/import/chunks/{chunk_id}`), for example when N can't reach O. A chunk already stored is a no-op; bytes with another hash are refused. Nothing is live yet, and every step can be repeated: an interrupted signer asks N which chunks it still lacks. The signer signs the freeze, the export transfer and the activation; it needn't carry the export.
   - **Activation:** the signer activates the import (`POST /v1/{id}/import/activate`), naming the manifest hash. N checks that every chunk is present, rebuilds the state, verifies the chain from its stubs, from the checkpoint or the first item, up to the manifest's head, which must be O's freeze transition, with every check an app makes on a stub (Section 10.1), so the apps O kept stubs for can read them at N, and checks that it extends every head the apps uploaded at or after the checkpoint. A head older than the checkpoint can't be checked against the imported chain, which starts after the checkpoint, so N ignores it: it is neither evidence for nor against the import. An honest app holds one only if O dropped the stubs after its position, as O may for an app more than 30 days behind or one restored from a backup (Section 8.3), so N doesn't refuse the activation for it. Parts out of the order the wire format fixes are refused (`spec/wire-format.md` Sections 10.3 and 10.5). It checks that the imported `identity.json` is the one it was enrolled with or a newer one, at the same generation, and the newest one the imported chain holds, so O can't roll the identity back to a version that still lists a revoked app or an earlier data epoch; the signer, for its part, never builds on a lower version than it delivered (Section 4.3). It checks the rest of the state against the signed items it stands for, never taking a label O wrote. It accepts O's last committed time and the freeze time only within the clock tolerance of its own trusted time, and refuses the activation without trusted time (Section 10.1); the checkpoint must lie before the head, and O's last `seq` must be the head's. A shared record is derived from its signed operation, which verifies with a certificate of the writer it names that holds one of its write scopes, and carries the transition proof of its current write, which names that write and verifies with the service key of its generation, O's or one the imported `identity.json` lists (Section 4.3), unless it came from a recovery upload: its key, collection, policy, writer, delete and size are the operation's, a write after the checkpoint is the chain item at its `seq` with that `seq` as its version and no later write of its key in the chain, and one at or behind the checkpoint is no later than the checkpoint. A live claim is replayed from its signed entries: each verifies with a certificate of the writer it names, which holds `claims.write`, so O can't make one up, nor pass one app's entry off as another's; their steps increase; each is the chain item at its `seq`, and none the chain holds is left out, with the proof of the service that applied it, of the entry's own generation and checked with that generation's key, O's or one the imported `identity.json` lists; and N applies each entry's effect, the state after each being the one its proof shows, without judging again which apps were current then, so the claim is the state its entries lead to and O can't export an open attempt as failed. A claim rebuilt from uploads after a provider loss (Section 12.6) is accepted only when the imported `identity.json` declares that loss. N checks it attempt by attempt, whatever the order its uploads came in: each attempt is one an upload added, or the one an entry wrote, with that entry's members, and has the outcome its latest entry wrote, or, for one an upload added, `done`, which a later upload may have made it; only what uploads alone change is taken as O gives it. Every app the imported `identity.json` lists, and every app whose registration the chain holds, has its part, so O can't leave an app out. An app's receive key records come in increasing order, each is its chain item, and the newest registration the chain holds is the current key; a departure or revocation the chain records stays one, whatever the app's part says. Finally it checks the import against the evidence apps uploaded: an obligation a proof shows SETTLED must be SETTLED, unless its tombstone's deadline plus the 30-day reconciliation window is at or before O's last committed time, or, without a deadline, 400 days after the proof's entry is; an attempt an owner's proof shows must still be held, and in a live claim with the outcome the proof shows unless a later entry of the claim wrote another, or an upload settled it; and a record must be the write a proof names, by its item hash, or one built on that version or a later one. It refuses the import otherwise. Evidence an app uploads after the activation is checked at once, and a mismatch is an import conflict, which holds back the `identity.json` naming N until the signer aborts. Only then does N make the imported state live, in one step. N continues O's `seq`, chain and service time under generation g+1, so cursors and heads stay valid. It refuses the `identity.json` naming it until the activation.
4. **Publish:** the signer delivers `identity.json` with generation g+1 and a higher version, naming N and keeping in `service_keys` the key of every generation O reports that a current record's proof names (Section 4.3), to N, which then accepts app operations and inbox writes, and then publishes it. Apps re-register their push handles bound to a push key from N (Section 9). Once it follows, each app:
   - uploads O's SETTLED proofs it keeps again, so the evidence of an app that missed the move still counts: N merges each one bound to the imported chain as after a provider loss (Section 12.6 step 3), rebuilding a tombstone O left out, or making the obligation divergent where it holds it open, and refuses any other mismatch;
   - reads its own entry in N's directory: an older key of its own shown as current is a rollback of its registrations, so it alerts the user and registers its current key again; a key it never registered is a compromise (Section 3.6). An app may also send its `app.put` and its current `receive_key.put` again at N, signed for the new generation: N holds both records from the import, so it takes them as no-ops (Section 6.3);
   - compares N's admission lists with what it knows: an app with `lists.manage` adds back the contacts and deny list entries of its own copy that N lacks, and shows the user contacts N holds that it never saw added, since its copy starts at its own registration; an app that may read the lists withdraws the invite codes N holds in its name that it never registered, and those of apps that aren't current.
5. **Authorization rule:** an `attempt` counts only when the app holds a fresh `identity.json` naming the service that signed its transition proof (Section 4.3).

- **Abort:** while N holds no `identity.json` naming it, the signer may cancel the move with a signed unfreeze naming the hash of the freeze it cancels (`POST /v1/{id}/unfreeze`). It sends the unfreeze to N first. N discards the import bound to that freeze, partial or activated, refuses any manifest bound to it from then on, and answers with a signed confirmation that it discarded the import. The signer then sends the unfreeze to O with that answer. O checks N's answer with the service key the freeze names, and resumes only when it holds that answer, so O and N never both accept writes; from then on its public read carries no freeze. Apps then submit their queued writes to O. The cancelled freeze is used up: a later move signs a new one. If N can't be reached, the move can't be cancelled: the signer completes it to N, or, if N is gone, declares a provider loss (Section 12.6).
- **Fencing:** an app whose cached `identity.json` still names O can't get an attempt authorized there, because O is frozen. In a cooperative move the freeze is the fence. An app acts only on an attempt whose transition proof is signed by the service key its own `identity.json` names and whose chain stub is of the generation it names, so a stale instance of an earlier generation authorizes nothing, even at the same origin.
- **Key rotation in place:** each service key serves one generation, so rotating it is a generation change at the same service: the signer enrolls there again, which answers a pending key, and delivers and publishes the next version at g+1 naming it, keeping in `service_keys` the key of every generation the service reports that a current record's proof names, the outgoing one included when a record needs it (Section 4.3). The service continues its sequence and chain under g+1 with the new key, and apps follow as after a move; nothing is exported. The records' proofs signed with the outgoing key stay with them and still date their writes. Nothing tells a signer that a service wants its key rotated: a rotation is the signer's own step, which its user starts, so an account's service key changes only at an enrollment, this one included, or a move.
- **Kept batches:** an app that kept a batch to send again, signed for generation g, and didn't read the old feed to its end, because it never saw the account frozen or the key changed in place, can't tell from its own chain whether the batch was applied. It sends the batch again unchanged to the service at g+1 before it signs anything in its place, and the answer decides (`spec/wire-format.md` Section 6.4 steps 5 and 6). The original proofs, which a key change in place keeps, or `409 conflict`, which an import gives since it carries a batch's ID and operation hash but no proofs (step 3, Manifest), mean that the batch was applied: the app never signs it again, and reads its effect from the current state. `409 stale_generation` means that the service holds no batch of that ID, so the batch was never applied, and only then does the app sign its operations again for g+1, under a new batch ID. The service holds a batch's ID for at least 30 days after it applied the batch (Section 6.3), so the answer decides only for a batch first sent less than 30 days before, less the clock tolerance; an older kept batch is dropped, and the app tells its protocol. An app that kept a received message's effect past that window doesn't build it again: it stores the entry locally, moves its cursor past it, keeps the message's (sender identity, `msg_id`) as processed so a re-send is deduplicated, and tells its protocol, which decides from the current state of what the effect writes. The same holds when the batch was within the window at the provider change but its resend is answered past it. Only an answer made at or after the batch ID lookup (`spec/wire-format.md` Section 6.4 step 5) tells whether a kept batch was applied. A refusal about the request's own shape or size, made before that lookup, will be made again for the same bytes: the app stops sending the batch and handles it as one kept past the window. A refusal about the caller says nothing about the batch: the app keeps it and sends it again once the service accepts its requests. None of this holds after a provider loss, where the new sequence holds no batch of the lost one and `409 stale_generation` says nothing about what O applied (Section 12.6). An `attempt` learned this way to be applied is not carried out on that answer (Fencing, above): the app reads the claim and resolves its attempt as its protocol says.
- **Residual risk:** N checks the import against the chain and the evidence apps uploaded. A faulty or malicious O that omits state, such as a tombstone or a shared record, is detected only by apps holding evidence of it: the proofs and record versions they uploaded, before the activation or after it (step 4), the SETTLED proofs they compare before attempting, and a protocol's own evidence. A record whose newer write O dropped from the chain together with its document, and admission state no app can vouch for, aren't detected by N; the latter is shown to the user (step 4).

### 12.6 Provider loss (O unreachable or hostile)

1. **Declare:** the signer enrolls N, naming in the signed enrollment every App ID it revoked or saw depart that the document it delivers doesn't list, so N refuses them from the start although no export reaches it (Section 12.2). It then delivers `identity.json` with generation g+1, a higher version and `recovery_from: g`, naming N, to N, and publishes it once N accepts. N may be the same operator and origin as O: the enrollment there answers a pending key for the next generation, since each service key serves one generation, and the document at g+1 naming that key starts generation g+1 in the existing account. It starts afresh, as a new service would: committed state it may have lost can't be trusted, so it keeps only its service time, which never goes back, its directory's version counters, which never restart (`spec/wire-format.md` Section 7.4.10), and the App IDs it must refuse, and the old key signs nothing more. N starts a new sequence and chain for generation g+1, beginning with a service-signed recovery record naming g; that record's server time is the time of the declaration. Apps read N's feed from its start, deliver their app records, register a receive key record with an `n` higher than every `n` they have registered (Section 3.6), and re-register their push handles bound to a push key from N (Section 9). Every app watches its own `identity.json` (Section 4.3), so even one that only receives finds N.
   - **What the document carries:** it builds on the newest version the signer signed, one O may have taken without its answer reaching the signer included, never on an older one: apps that saw that version would refuse a lower `data_epoch` and see its removals and certificate changes go back (Section 4.3). It has the same `data_epoch`: no scope key ever reached O in the clear, so nothing rotates. An app the signer revoked that no version removed yet stays listed, and is removed at N: right after N takes the document, before the signer publishes it, which is how apps find N, the signer revokes the app there; the version that removes it, with its rotation, follows, as at any service (Section 12.2). A revocation the user asks for while the recovery is in progress waits for N the same way: nothing goes to O. A revocation N doesn't take stays pending, with its alert, and publication doesn't wait for it. A reduction whose closing the signer still owes (Section 3.2) can't be closed at O, so the document closes it itself, its `renewed` entry's `until` the time the signer signs it plus the clock tolerance: a reader takes the earlier certificate's writes up to that time and none after, the purpose of the closing. Cooperative renewals stay open; N's records close them as at any service.
   - **Who may declare it:** the signer, also while an alarm is held, since a provider loss is the way out of one; an erased install, at the same service or another, which is how an erased account is enrolled again (Section 12.7 step 4); and one whose erasure is in progress, in doubt, or erased but unconfirmed, which ends the erasure, the account at O counting as lost. Not an install whose records are behind, which restores first (Section 4.3), one another install signs for, nor one handing the identity over or taking it over (Section 12.8). O can't be asked which, so before it signs, the signer reads the signer backup and the Homeserver's `identity.json`: either one showing another install that signs, or a newer version of its own, stops it. So does an `identity.json` that doesn't verify, which the signer's own steps never leave, or none where its records don't explain it (an erasure deleted it, or no version was ever published: an unpublished newest version explains nothing once an earlier one was published), unless the user confirms that no other install signs: another install may have published there, deleted since.
   - **Declaring again:** until N takes the document, the signer may declare the loss again, at N or another service, as for a service that never answers or that refuses the document: the new declaration replaces the one in progress, and its document has a higher version still, so no version has two bodies (Section 4.3). Declared again at the service its document is in flight to, the signer sends that document again instead. Declared again at a service an earlier declaration enrolled at, it first reads there, under the key that enrollment was answered with, whether that document was taken: a service that took it serves it, and answers a new enrollment with a pending key and the new document's refusal with its own key (`spec/wire-format.md` Sections 3.7, 7.4.2), so a refusal the pinned key didn't sign is read the same way. A document of this recovery that N holds under the key pinned for it, as after a lost answer, is the recovery delivered. Enrollment errors are signed with the operator key, which no client can check (`spec/wire-format.md` Section 7.4.1), so none is N's word: a `400` makes the signer send the same enrollment again, and a `409 conflict` means enroll again (Section 3.7 there): it signs a new enrollment, with a new nonce, and sends it. After three sends in all in one run of the declaration, either one ends it, and declaring again there enrolls afresh. Meanwhile the signer signs nothing else.
2. **Restore admission:** an app with `lists.manage` uploads the contacts and deny list from its own copy of the lists, which it keeps from the feed (Section 8.3). Apps with `lists.read` may upload deny entries too, which only restrict admission. Every app re-adds conversation entries for the counterparties in its records, except identities on its own copy of the deny list. Until the contacts upload arrives, N answers senders it can't otherwise admit with `503 staged`, so they retry instead of giving up; denied senders get the same answer, so the staging doesn't reveal the deny list. N stages admission at the recovery whenever the recovery document lists at least one current app, since permissions reach N only with each app's certificate, after the recovery; a document that lists no app stages nothing. The signer ends the wait (`POST /v1/{id}/recovery/admission`): at once, right after the recovery's document is delivered and published, when none of the listed apps holds `lists.manage`, since no upload could ever end it, and later whenever the user decides, for example when the app that manages contacts is gone for good. That call is a step of the signer's recovery, which it sends again after a crash, and ending a wait that isn't staged changes nothing.
3. **Collect:** apps upload what they hold, without decrypting anything for the service: signed operations, transition proofs, signed heads and sealed shared records. The SETTLED and tombstone proofs among them are every one an app still keeps: through the later of the obligation's pinned deadline and its own, plus 30 days. Uploads are evidence: N merges them without renumbering its own sequence or rewriting entries already there. Each uploaded operation comes with its writer's certificate, which N checks against the identity key; an operation of an app listed in `removed` counts only if O's transition proof dates it before that app's `distrust_from`. An app uploads what it holds before any write at N other than its registration (step 1): before its first record write, claim entry and list change, so nothing it writes at N is judged against a state its own evidence would still change. An app in reconcile mode (Section 12.4) ends it only after its upload. Writes at N follow N's current version of a record, whatever was uploaded. For each upload N appends one service transition listing what changed:
   - **Shared records:** uploaded versions fill in records that N lacks or holds only from earlier uploads at a lower version. They never supersede a write made at N; an upload that conflicts with one, or two different uploaded values at one version, is kept and listed as divergent until a writer writes a newer version at N. An uploaded record's version is the one O's transition proof gives it. Without that proof, the version it built on, plus one, is a lower bound: it fills in a record N lacks, and two different uploads that build on one version are divergent. A write at N conflicts with an upload newer than the uploaded version the writes at N built on, or with any upload if they built on none.
   - **Claims:** uploaded writer-signed entries merge per `attempt_id`, without re-checking their conditions or `expected_step`; evidence for an obligation N holds only as a tombstone re-opens it: the obligation is live again, rebuilt from uploads, with the tombstone's step and attempts, whose entries compaction removed, and stays SETTLED. An entry that carries no transition proof from O must satisfy the live writer rules of Section 10.2: `done` with basis `owner`, and `failed`, count only from the attempt's owner. Entries can only add attempts or move an obligation toward SETTLED: a writer-signed `done` of any basis settles it, flagged `duplicate` if another attempt is done; `failed` or `unknown` applies only to an attempt still open at N. An uploaded open attempt that N lacks is added, orphaned (Section 10.2): on a FREE obligation it becomes the current attempt; if N already has an open attempt, the uploaded one is recorded beside it and the obligation is divergent. Evidence that conflicts, such as two outcomes for one attempt, makes the obligation divergent instead of applying `failed`, and a divergent obligation is doubtful: no automatic attempt. It clears once every attempt on it that isn't final is resolved by its owner, by evidence such as the counterparty's confirmation, or by a user-confirmed outcome. The owner may still record `done` on a `failed` attempt of a rebuilt obligation (row 2 of Section 10.2). An O-signed proof that an obligation is SETTLED with every attempt done or failed rebuilds a tombstone for an obligation N holds nothing for. It can only move an obligation toward SETTLED, so a hostile O gains nothing by it; this is what lets apps drop claim evidence behind a checkpoint (Section 8.3).
   - **O's transition proofs and heads** show order and what apps saw; N doesn't treat them as authority, since O may be hostile.
4. **Ask for re-sends:** inbox entries that O held are lost. Each app sends `resend_request`, for messages accepted after the time of its cursor at O (the acceptance time of the last entry it processed there, which it keeps), to the counterparties of its unfinished activity records.
5. **Treat the unknown conservatively.** A missing claim is never treated as unused.
   - **Obligations from before the loss** are uncertain. Uncertainty is per obligation: an obligation is uncertain if an attempt on it could have been authorized at O, that is, if it could be attempted before the declaration plus the residual window (residual risk, below); which ones could is the protocol's. There is no automatic attempt for uncertain obligations, and a manual attempt requires the user to confirm that another app may already have made it. That confirmation lets that one manual attempt go ahead; it doesn't end the uncertainty, so if the attempt fails, the obligation stays uncertain. They resolve only through the protocol's reconciliation and step 6.
   - **Kept attempts:** a batch an app kept to send again that carries an `attempt` signed for the lost generation is dropped, never signed again for N: whether O applied it can't be known, so its obligation is uncertain like any other from before the loss. The app reports the dropped attempt to its protocol, which treats the obligation as above.
   - **A protocol's own pauses:** a protocol may hold back more of its automatic attempts, such as standing ones the user set up, until the user confirms them again: a missed attempt can't be ruled out, because both N's rebuilt state and the apps' journals may lack it.
6. **Close:** recovery ends per obligation, and per whatever else its protocol holds back. An uncertain obligation closes when it is SETTLED at N, or when the user states that it wasn't carried out before the loss; nothing else closes it, not a confirmed manual attempt that failed nor an `unknown` or `failed` resolution. A closed obligation is attempted like any other, automatically too.

**Residual risk:** N can't stop O. An app that still trusts O through a cached `identity.json` could get an attempt authorized there for up to 60 s after the declaration, or longer if its Homeserver serves it a stale `identity.json`. The residual window is 60 seconds plus the clock tolerance, since an app makes no attempt without an `identity.json` revalidated in the last 60 s (Section 4.3), plus the offset between O's and N's clocks, since O applied its time conditions on its own clock while N's dates the declaration. Each app measures that offset as the difference between the last service time it verified from O and the first from N, each taken against its own clock, and assumes twice the clock tolerance when it has none from O. Signed heads detect rollback of history an app saw; they can't prove that no newer authorization exists, which is why step 5 is conservative.

### 12.7 Erasing an account

The signer can erase the identity's account at a switch (`POST /v1/{id}/erase`, `spec/wire-format.md` Section 7.4.16), so that a user can delete their account.

1. **Request:** a signer call like any other, signed with the identity key over the method, the path, the service's origin and a timestamp within the clock tolerance of the service's time (Section 6.1). It names the account's service key, so a replay can't erase a later account of the identity at the same service, which has another key. It also names the hash of the newest `identity.json` the signer holds, so a switch that holds another, delivered after the signer's last check, as by an install that took over, refuses it and erases nothing; a request without the hash, from an older signer, is checked by the key alone. A request signed with an app's key, for another service's origin or at a stale time is refused.
2. **Deletion:** the service signs a confirmation with the account's service key, the last thing that key signs, and then deletes everything it holds for the identity: inbox entries, the chain and its batch records, shared records, claims and tombstones, contacts, the deny list, conversation entries, invite codes, connect requests, app records, receive key records and key bundles, cursors, push registrations and handles, its copy of the identity's `identity.json` and the peer copies it keeps for the account, enrollment answers, freeze, export and import state, rate-limit counts, and the service key with its mark (Section 6.5). It releases the confirmation only once that deletion is durable, so a crash can't leave the erased account recoverable; if the deletion can't be committed, no confirmation goes out and the signer retries. Until the service key itself is gone, the identity's signer gets a temporary failure, not the answer for an identity the service doesn't host, so that answer never comes while the key exists. After that it knows nothing of the identity: every call for it, a retried erasure included, is answered as for an identity it doesn't host, and so is a call already in flight when the erasure lands, unless its answer was signed before the confirmation (a write it committed went with the account), and a later enrollment starts a new account, with a new key and nothing of the old one. What other accounts hold about the identity, such as their contacts, conversation entries and peer copies of its `identity.json`, is theirs and stays.
3. **Not during a move:** a frozen account refuses the erasure (`409 conflict`) until its export is finished, every chunk of it fetched at least once, and so does a staged account holding an import, until the signer aborts the move (Section 12.5). So a move can't lose data, and the old service can still resume. After a move given up for a provider loss (Section 12.6), the signer finishes the old service's export by fetching it itself, then erases there.
4. **For the account's life:** what Section 6.3 keeps for good, such as the App IDs of revoked and departed apps, is kept for the account's life and goes with it. The signer keeps its own records (Section 18), so a later enrollment names those App IDs again, as every enrollment does (Section 4.3). The new account starts as after a provider loss (Section 12.6), so the signer's next `identity.json` has a higher version and generation than any reader has seen.
5. **Effects:** erasing the account at the current switch is a provider loss for the identity's apps (Section 12.6), and lookups of `identity.json` there fail closed (Section 4.3). So the signer asks the user to confirm, and offers erasure in two cases: at the old service after a move, once its pointer window, the record age limit, has passed (Section 12.5 step 2); and when the user stops using the Switch. In the second case it first deletes `identity.json` and the app records from the Homeserver and has the apps' grants revoked (Section 3.4), so counterparties find no identity on the Switch instead of one whose switch doesn't answer. An own app has no authenticated sign of an erasure: the erased account answers `404` signed with the operator key, which no client can check, and a Homeserver fault can read as a missing file. So an app takes a `404` it can't check together with a missing `identity.json` as an erasure only once both have held at every try for 24 hours. Until then it treats the service as unreachable: it keeps its state, makes no attempts and tries again (Section 19, question 25). The signer follows the same rule for its own erasure: it takes that `404` as its erasure done only after an erasure request of its own that may have landed went unanswered, and only once the `404` has held at every try for 24 hours; one answer signed with the account's key ends the wait, and the erasure goes on (`spec/wire-format.md` Section 7.4.16). Otherwise it keeps its records. Declaring a provider loss is the way out of that wait, as of an erasure in doubt whose switch never answers again (Section 12.6 step 1). Meanwhile it shows the erasure as erased but unconfirmed, and refuses revocations as during any erasure: each would need the switch, to revoke the app there and to deliver the version that removes it, and the switch answers neither; the erasure has already removed the app records from the Homeserver, and the reminders to revoke the apps' grants, which need neither, stay shown.
6. **Backups** are the operator's duty (Section 6.5).

### 12.8 Handing the identity to another signer

An identity has one signer at a time, the install its newest `identity.json` names (`signer`, Section 4.3). Any app can be its identity's signer, through the SDK's signer core, and the user can later hand the identity to a dedicated signer such as Bitkit or Ring (Section 19, decision 24). The hand-over moves the identity key and the signer's records to the new signer, as one sealed export of at most 128 envelopes that travels through the switch (`spec/wire-format.md` Section 3.12).

1. **The new signer is an app of the identity.** The user first approves it like any app (Section 12.1), so its certificate names its bundle key. The old signer splits the hand-over into parts, each sealed in its own envelope to that certified key, as it seals a key bundle (Section 3.5), and signs them together with the identity key over the new signer's App ID, their number and their order. Only that app opens them, and it refuses parts swapped, missing or added. The old signer stores them at the switch for that app (`PUT /v1/{id}/handover`), as it stores key bundle parts, and the app fetches them as it fetches its bundle. The switch keeps at most one hand-over per account, which a new one replaces, and deletes it with the next `identity.json` version it takes, whichever signer delivered it: the hand-over has then taken effect, or an abort won. It deletes it on erasure too.
2. **What it carries:** the identity key and the signer's records:
   - the newest `identity.json` a service accepted from it: its version, generation and hash are the signer's high-water mark (Section 4.3), and it names the service keys the signer keeps (`inbox.service_key` and `service_keys`);
   - the App IDs it revoked or saw depart, kept for good (Section 12.2);
   - the certificates that `identity.json` references, of every listed app and each earlier one in `renewed`, so the new signer judges renewals and reductions as it did (Section 3.2). The signer acts on certificates only through that document: a removed or revoked app is handled by its App ID, and readers judge old writes and messages from the certificates they carry. So no other certificate is needed, and the hand-over stays within its bound however long the identity lives;
   - the limits the switch announced at enrollment, which it gives only then (Section 4.3);
   - the key bundle parts it stored for each listed app, made for that app's listed certificate, so the new signer knows what it needn't store again (Section 3.5).

   Before it seals the hand-over, the old signer delivers any closing version it owes (Section 3.2), and its newest version must be delivered. There is no hand-over during a provider move (Section 12.5).
3. **Handing over:** once it has sealed the hand-over, the old signer is handing over. It signs nothing new for the identity, no delivery, approval, renewal, revocation, rotation, key bundle, move or erasure, except an abort or a take-back (below), and it keeps the key and its records until it sees the proof of step 5. It writes nothing to the Homeserver either until its abort or take-back has won, so it never republishes the switch's copy.
4. **The new signer checks** that the hand-over opens, that the key it carries is the identity's, that its `identity.json` verifies and lists the new signer's app, and that every certificate that document lists is among those handed over. It then checks the records against the switch and the Homeserver: the switch must hold the `identity.json` handed over itself, and the Homeserver none newer nor another one at its version, so a hand-over older than the switch's copy, or a switch that went back, is refused. It makes these checks once, before it first sends its delivery, and checks then too that its secure storage can take the key: one that holds another key refuses the hand-over, with nothing stored. App IDs the switch reports revoked or departed join the kept ones. It then delivers the next `identity.json` version, built on the one handed over (Section 4.3) and naming its own install as `signer`. From before that first send until the delivery is decided and its key is stored, it keeps the hand-over it fetched, the install ID it picked and the signed delivery, as Section 3.1 requires, since the switch deletes its copy of the hand-over at the next version. Only the answers to that delivery, sent again with the same bytes, decide. **The hand-over takes effect** when that delivery wins the compare-and-swap at the switch, and from then on the new signer is the only signer: nothing cancels it, and it never deletes the key on a later answer. It then stores the key, reads it back and checks it, writes its backup, and only once the backup is written publishes the version, its republishing of the switch's copy included (Section 4.3); a store that fails is tried again, and so is a backup write, which publication waits for. A new signer that refuses the hand-over once it has opened it, at any of these checks, or whose delivery loses, deletes the identity secret and the records it received, and tells the user the hand-over was refused or cancelled. Its delivery loses only to a `409 stale_identity` whose copy verifies for the identity, is at or above the delivery's version and names another install; one whose copy is the delivery itself means it won, and any other answer, or none, decides nothing, and the delivery is sent again (`spec/wire-format.md` Section 3.12). A refusal or a cancellation deletes only what that hand-over brought, never a key the install held before it arrived, in its secure storage or in another hand-over it keeps: an install that already signed for the identity, or held its key, keeps it whatever hand-over it fetches, so a hand-over stored or served again after it took effect costs nothing.
5. **The old signer deletes** the identity key and every record of the signer, in every copy it keeps (Section 3.1), only on proof that another install holds the identity: the switch shows a version newer than the one it handed over, verified, naming another install and not its own abort, and the signer backup on the Homeserver opens with the identity's backup key, verifies, and holds a newer version naming that same install. Only a holder of the identity key can make that backup, and the new signer writes it only once its key is stored, so neither the switch nor the Homeserver, alone or together, can make both signers delete the key. A newer version without that proof, other than its own abort or take-back, stops the old signer as an install that isn't named; it keeps the key and looks for the proof again at each run. Its own abort or take-back at the switch means that delivery won. It keeps its own app keys and goes on as an ordinary app, and tells the user that it no longer manages the identity, and which app does.

- **Abort and retarget:** until the hand-over takes effect, and while the switch still holds the version it handed over, the old signer may abort it. It delivers the version it handed over again, with the same content, at that version plus 2 and with `prev` its hash; once the abort has won, it writes its backup and then publishes it. Plus 2, so that it never shares a version with the new signer's first one, plus 1: two documents at one version would be equivocation (Section 4.3). Exactly one of the two deliveries wins the compare-and-swap. If the abort wins, the export is dead: the new signer's check of the switch's copy (step 4), or its own delivery, fails, and either way the new signer deletes what it received. The old signer is then the signer again, and may seal a new hand-over from the new version, to the same app or another one, or carry on. If the new signer's delivery won first, the abort gets `409 stale_identity`: the old signer stops, and deletes its copy once it sees the proof of step 5. Aborting is the user's choice, for example after the target app was lost or failed for good. The app may suggest it when a hand-over hasn't taken effect after a while.
- **Take-back:** if the switch's copy, verified, is at the handed-over version plus 1 and names another install, but no proof follows (step 5), as when the new signer, or an install that restored from the old signer's backup, was lost before it stored the key or wrote its backup, the old signer may take the identity back on the user's confirmation that that install is lost. It delivers that copy's content naming its own install, built on it, above every version it signed, its abort included, and once that has won writes its backup and publishes: the old signer is the signer again, as after an abort. A take-back whose answer was lost is sent again, the same bytes. A take-back that loses leaves the old signer stopped, keeping the key. The compare-and-swap decides a race with a new signer still alive, which then finds itself not named and stops, keeping its key; both installs then hold the key and neither deletes it, so each tells the user.
- **The limit:** the protocol can't stop an old signer that keeps a copy of the key. It is the same identity key, so the hand-over is a trust step, and the user is told so before it starts. The new signer's newer `identity.json` wins over anything older, as always (Section 4.3).
- **Keeping the key safe and backed up** is the new signer's job from then on (Section 3.1).
- **Backing up the signer:** the signer backs its records up as a hand-over addressed to the identity itself: the newest `identity.json`, the revoked App IDs, the certificates, the stored key bundle parts and the switch's limits, sealed to a key derived from the identity key and signed by it (`spec/wire-format.md` Section 3.13). The backup lives on the Homeserver at `/pub/pubky-switch/v1/signer-backup.json`, which only the signer writes. It is ciphertext, but public, so its size and the times it changes are visible. The signer writes it before each delivery of a new version, holding that version, so it is never behind the switch's copy, and after it stores key bundle parts. A take-over, a restore, an abort and a take-back, which race another signer, write it once their delivery has won, so a delivery that loses never overwrites the winner's backup. A backup that names another install at or past the signer's high-water mark (Section 4.3) shows that install has taken over: the signer stops, as an install that isn't named. The exception is the backup of a delivery that lost to the mark, one that builds on what the mark built on and isn't the mark itself: the service accepted no other document there, so the signer's own write replaces it (`spec/wire-format.md` Section 3.13).
- **Restoring the signer** is taking over from the backup, with the identity key, on the user's confirmation, and with the checks of step 4 against the switch and the Homeserver, so a stale backup is refused. The switch must hold the backup's version, or the version it builds on, which the backup names: a signer stopped between writing its backup and delivering leaves that one, and the restore delivers the backup's version first. The restored install then delivers the next version, naming itself as `signer`. This is also how an install that isn't named takes over. A provider move in progress isn't in the backup: a signer restored during one meets the frozen account and continues as after a provider loss (Section 12.6).

## 13. Encodings

### 13.1 General

- **JSON:** UTF-8 without BOM. Readers reject duplicate member names, compared after unescaping, reject lone surrogates, and reject documents whose `v` they don't support. They reject unknown members in conditions, operation bodies (at every depth, except opaque members), the entries of a batch request, certificates and receive key records (their `suite_keys` entries included), app requests and export transfers (their `from` and `to` included), so a future restriction there is never silently skipped, and ignore unknown members everywhere else. A later suite's keys still fit certificates and receive key records without a new version: they go in the reserved `suite_keys` member (Sections 3.2 and 4.4). Every integer is from 0 to 2^53 - 1, written without sign, fraction or exponent; readers, the switch and apps alike, reject any other number outside the opaque members, which the wire format names by their path: the opaque members of a protocol's message bodies, and an invite code's `context`, wherever it is carried. The check runs on the whole document when it is parsed, before its fields are read (`spec/wire-format.md` Section 1.1).
- **Binary values in JSON:** base64url without padding.
- **Times:** RFC 3339, UTC, with seconds.
- **Identifiers in JSON:**

  | Value | Form |
  |---|---|
  | Pubky ID | z-base-32 public key, as defined by Pubky |
  | App ID | 16 bytes, z-base-32 |
  | kid | 8 bytes, base64url |
  | Obligation, record key, collection, hashes | 32 bytes, base64url |
  | `msg_id` | UUID version 4, lowercase hyphenated string; this form is a MUST, and readers reject any other |
  | `attempt_id`, batch ID, and the nonces of enrollments, freezes and push webhooks | 16 random bytes, base64url |
  | XChaCha20-Poly1305 nonces in envelopes and sealed fields | 24 random bytes (Sections 5.1 and 13.4) |

  Requests to the switch carry no nonce: their timestamp and signature bind them, and the service recognizes a retry by its content (Section 6.1).
- **Length-prefixed concatenation:** `lp(x1, ..., xn) = u32_be(len(x1)) || x1 || ... || u32_be(len(xn)) || xn`. Every signature input, derivation input, AAD and HPKE `info` below uses it, so fields can't be shifted between positions.
- **Field encodings inside `lp`:**

  | Field | Bytes |
  |---|---|
  | Identity, Pubky ID | 32-byte Ed25519 public key |
  | App ID | 16 bytes |
  | kid | 8 bytes |
  | Integer (`u64`) | 8 bytes, big-endian |
  | Label, scope name, collection name, method, path and query, origin | UTF-8 text |
  | Request header values (`Switch-Timestamp`, `Switch-Identity`, `Switch-App`, `Switch-Cert`, `Switch-Invite-Code`) and `Switch-Server-Time` | The exact header text, UTF-8, empty when the header is absent. The identity and app headers are signed as their z-base-32 text, not as key bytes |
  | Hash, object ID, key | Raw bytes |
  | Document or message body | The exact bytes |
  | Absent value | Empty (length 0) |

### 13.2 Signatures

- **Algorithm:** Ed25519 (RFC 8032), verified exactly this way, so that every implementation accepts and refuses the same signatures (`spec/wire-format.md` Section 2.1 has the steps and the vectors):
  1. S, the second half of the signature, is below the group order L.
  2. The public key A and R, the first half, each decode to a curve point and encode back to the same 32 bytes (canonical).
  3. Neither A nor R is of small order (order 1, 2, 4 or 8).
  4. The cofactorless equation holds: the encoding of `[S]B - [k]A`, with `k = SHA-512(R || A || message)` reduced mod L, equals R's bytes.

  A mixed-order public key, a point of order 8L, is accepted, as RFC 8032 allows; nothing requires A to be torsion-free. A cofactored verifier, or one that skips step 2 or 3, isn't compliant. ed25519-dalek's `verify_strict` alone doesn't check step 2 for A.
- **Sign once:** a writer signs each document, operation and message once, keeps its exact bytes, and sends those bytes again for every retry, re-delivery and later use; it never signs or serializes it again. Retries recognized by content (Section 6.1), the no-op rules (Section 13.5), the compare-and-swap on `identity.json` and every hash over a signed document compare whole signed bytes, so a second signature of the same body counts as another document there. Deterministic signing (RFC 8032) is recommended, but nothing depends on it: a platform whose Ed25519 uses random nonces is compliant as long as it keeps the bytes. Equivocation compares bodies (Section 4.3).
- **What the identity key signs:** only the formats of the table below whose signer is the identity key (app certificates, `identity.json`, enrollments, key bundles, the signer hand-over and the signer's backup, freezes, unfreezes, export transfers, and the signer's own requests to the switch and operations), the approval's companion claim (Section 3.2), and the formats Pubky defines for the same key (PKARR records, Pubky auth tokens and grants). Every input of the table starts with the 4-byte length of its `pubky-switch/v1/` label, so its first byte is 0; the companion claim's starts with the text of its query parameter, `x-pubky-switch-claim|` (`spec/wire-format.md` Section 3.10); Pubky's inputs start otherwise (an auth token's with `PUBKY:AUTH`, a grant's JWS with base64url text, a PKARR packet's with `3:seq`), so no input of one format is valid in another. A signer never signs bytes a caller supplies: there is no generic signing with the identity key. A new format gets its own label in this table, and the list is kept in step with Pubky's.
- **Signature input:** `lp(label, field1, ..., fieldn)` with the label and fields below.
- **Signed documents** are carried as `{ "body": "<base64url of the exact JSON bytes>", "sig": "<base64url>" }`. Examples in this spec show the decoded body.
- **Signed document bytes** are `lp(body bytes, signature)`. Every hash over a signed document, such as a certificate hash or a chain item hash, covers these bytes, never re-serialized JSON.
- **Labels:** every format the Pubky Switch defines signs under a `pubky-switch/v1/` label. A protocol's own formats sign under labels of the protocol's, such as `tasks/v1/`, never under a label that starts with `pubky-switch/`: every such label is the Switch's, in this version and every later one, and an app refuses to sign a protocol's format under one.

### 13.4 Sealed fields

```json
{ "data_epoch": 4, "scope": "tasks_share", "nonce": "<24 bytes>", "ct": "<ciphertext and 16-byte tag>" }
```

- **Key:** `scope_key(data_epoch, scope)` (Section 3.5).
- **Cipher:** XChaCha20-Poly1305 with a random 24-byte nonce.
- **Padding:** the plaintext is `u32_be(len(JSON)) || JSON || zero padding`, padded to the smallest size bucket that holds it, so the stored length shows the bucket, not the exact size, as envelopes do. The buckets run from 512 bytes to 256 KiB in steps of at most half again, so padding adds at most half a value's size and about a fifth on average (`spec/wire-format.md` Section 6.2 lists them). A delete stays the empty plaintext, unpadded, so it remains recognizable. A value too large for the largest bucket isn't sealed: the writer refuses it, as the service refuses its ciphertext by its length alone (`413 too_large`). The service refuses a value whose length isn't a bucket.
- **AAD:** `lp("pubky-switch/v1/sealed", identity, scope, record key)`.
- **Service check:** `data_epoch` equals the current one, otherwise `409 stale_epoch`, except in uploads during a provider move or recovery (Section 12); and `scope` equals the record's `read_scope`, otherwise `400 bad_request`.

### 13.5 Operations, batches and conditions

Each operation is a signed document (Section 13.2) whose body names its type in `op`:

```json
{ "op": "claim", "identity": "<pubky id>", "app_id": "<app id>", "generation": 4,
  "batch": { "id": "<16 random bytes>", "count": 3 },
  "claim_key": "<id>", "type": "attempt", "expected_step": 2,
  "attempt_id": "<16 bytes>", "orphan_after": 86400, "deadline": "<rfc3339>",
  "conditions": [ { "record_version": { "key": "<id>", "generation": 4, "version": 17 } },
                  { "server_time_in": { "start": "<rfc3339>", "end": "<rfc3339>" } } ] }
```

| `op` | Body fields besides `op`, `identity`, `app_id`, `batch` and `conditions` | Who |
|---|---|---|
| `claim` | `claim_key`, `type`, `expected_step`, `attempt_id`, on `attempt`: `orphan_after` and optional `deadline`, and on `done`: `basis` and `evidence_ref`, required with basis `evidence` and optional otherwise (Section 10.2) | App with `claims.write` |
| `record.put` | `key`, `collection`, `read_scope`, `write_scopes`, `expected_version` (the version read, or 0 to create, Section 10.3), `value_sealed`, and `id_inputs` when, and only when, `expected_version` is 0 | App with a write scope |
| `allow.put`, `allow.delete` | `pubky` and `kind` (`contact` or `conversation`) (Section 7) | App with `lists.manage` for contacts; app with `conversation.add` for adding conversation entries, and `lists.manage` for removing them |
| `deny.put`, `deny.delete` | `pubky` | App with `lists.manage` |
| `invite_code.put` | `code_hash`, `expires_at`, `max_uses`, `context` (Section 7) | App with `conversation.add` |
| `invite_code.delete` | `code_hash` | App with `conversation.add` |
| `cursor.set` | `position`, as `<generation>:<seq>` (unsigned and not counted in `batch.count`, but one of the request's 8 entries; the request's signature covers it) | The app, for itself |
| `app.put` | The app's signed record (Section 4.2), with a later `updated_at` than the one the service holds unless it is that very record | The app, for itself |
| `receive_key.put` | The app's signed receive key record (Section 3.6) | The app, for itself |
| `key_bundle.put` | `target_app_id`, the signed key bundle, and `first_epoch` and `last_epoch`, the first and last data epoch it holds keys for, in the clear (Section 3.5); a bundle in parts takes one `key_bundle.put` per part | Signer |
| `cert.put` | Target `app_id` and the signed renewed certificate (Section 3.2) | Signer |

- **`generation`:** every operation names the generation it was written for. The service rejects an ordinary operation naming another generation: older operations reach a new service only as recovery evidence (Section 12.6), and apps sign queued operations again after a move.
- **`batch`:** a random ID and the number of signed operations in the batch, the same in each of them. The operations of one batch take consecutive `seq`s, and their chain envelopes carry the batch ID and count (Section 13.6), so every app can check from items and stubs that a batch is complete. A batch ID appears at most once within any 30 days of the chain. The service holds a batch's ID for 30 days, and after that while any of its chain stubs is kept (Section 6.3). It answers the ID with the original result while it keeps the batch's transition proofs, those 30 days, and with `409 conflict` after that. An app never sends a batch ID again after its immediate retries. A batch whose every operation changes nothing is a no-op and takes no `seq` (Section 6.3). An app that finds part of a batch, or a batch ID repeated within 30 days, treats it as a rollback (Section 10.1). It takes a new batch for a repeat when its ID is that of an earlier batch and `t_new - t_old < 30 days` (2,592,000,000 ms), both the service time of each batch's first stub, and forgets older ones on its own, whatever checkpoints it sees (Section 8.3). The service holds a batch's ID at least until 30 days after its first stub's service time and refuses the ID while it holds it, so an honest service never trips the check. Within that window an honest service holds every ID, so a repeat there is evidence of a replay or a rollback. Beyond it the app doesn't compare, so an ID an honest service has forgotten can never cause a false alarm. The 30 days are measured by the service's own stamps. An app refuses a stub stamped earlier than the one before it (Section 10.1), but nothing bounds the stamps by the app's clock. The window has a cost: a dishonest service that replays a batch older than 30 days isn't caught by its ID. One that stamps a stub ahead widens what the window lets through: a replay of any earlier batch, however recent, isn't caught by its ID either. The operations' expected steps and versions still refuse what a replayed batch already did. List operations carry neither, so a replayed list change looks like a new one; the service decides admission anyway (Section 7).
- **`id_inputs`:** the collection name and blinded natural key a record key is derived from (Section 13.3), without the policy hash, which the service computes from the operation's policy.
- **Conditions:** `record_version` (`key`, `generation`, `version`), `claim_step` (`claim_key`, `step`) and `server_time_in` (`start`, `end`, either may be null), each an object as in the example.
- **Signer operations** use `app_id: null` and the identity key. The signer writes `key_bundle.put` and `cert.put` and no other operation: any other it signs is `403 permission_missing` (`spec/wire-format.md` Section 6.2).
- **Request:** `{ "ops": ["<signed operation>", ..., { "op": "cursor.set", "position": "3:1042" }] }`, 1 to 8 entries. A signed operation takes at most 512 KiB in its compact carrying form, without whitespace (`spec/wire-format.md` Section 6.1), enough for a 256 KiB record value, so whatever a chain item or record holds fits one export chunk (Section 12.5); a larger one is `413 too_large`.
- **Order:** operations apply in order. Each operation's own `expected_step` or `expected_version` is checked against the state the earlier ones left, so one batch can write two entries for one claim. A batch writes each record at most once, since a record's next version is known only when the service gives it (Section 10.3); a batch that writes one record twice is refused (`400 bad_request`). Explicit `conditions` are checked against the state before the batch.
- **Atomicity:** all conditions and every operation's own checks pass, or nothing changes and the service answers `409 conflict` with the current values the caller may read.
- **Response:** `{ "proofs": ["<transition proof>", ...], "head": "<signed head>" }`, one proof per signed operation, in order.

### 13.6 Chain and transition proofs

- **Chain items:** every signed operation, every `identity.json` delivery and every service transition. Inbox entries and cursor moves are not chained.
- **Item hash:** `item_hash = BLAKE3(lp("pubky-switch/v1/item", item type, item bytes))`. The item type is `op`, `identity` or `service`; the item bytes are the signed document bytes (Section 13.2).
- **Chain envelope** for each chain item, built by the service: `{ chain_version, generation, seq, prev_chain_hash, server_time, item_type, item_hash, batch_id, batch_count }`, with `chain_version` 1, where `prev_chain_hash` is the chain hash of the previous chain item, and the batch fields are those of the operation's batch, or absent for other items. It is sent and stored as exact bytes: `{ "envelope": "<base64url of the exact JSON bytes>", "chain_hash": "<base64url>" }`.
- **Chain hash:** `chain_hash = BLAKE3(lp("pubky-switch/v1/chain", prev_chain_hash, chain envelope bytes))`, with 32 zero bytes before the first item of a chain. An export that starts from a checkpoint starts from the checkpoint head's chain hash instead (Section 8.3). A chain stub is the chain envelope plus its chain hash.
- **One chain per sequence:** a cooperative move continues the chain; a provider loss starts a new one (Section 8.3).
- **Later versions:** every chain envelope and signed head names its chain version. A later version, such as a Merkle log with consistency proofs (RFC 9162 style), would be added beside version 1: a service keeps serving version 1 stubs and heads by default, and messages, claims and records don't change. How an app asks for a later version is defined with that version. Apps that know only version 1 keep verifying as this section describes.
- **Transition proof:** a service-signed document `{ chain, object, step, version, state }`: the item's chain stub, the object it changed, the claim's step or the record's version where they apply, and the resulting state (`spec/wire-format.md` Section 6.5 gives the exact fields).
- **Signed head:** `{ chain_version, generation, seq, chain_hash, sig }` of the newest chain item, `sig` being the service signature over `(identity, chain version, generation, seq, chain hash)` (`spec/wire-format.md` Section 6.7).

## 14. Threat model

| Adversary | Can | Can't | Protections |
|---|---|---|---|
| **Switch operator, curious** | See the metadata listed in Section 15 | Read messages or sealed data; forge messages or operations | Envelopes (5.1), sealed fields (13.4), signatures (13.2) |
| **Switch operator, malicious** | Delay, drop or withhold messages and changes, unnoticed by senders, whose delivery ends at acceptance; refuse writes; show different apps different histories after any shared prefix (a split view, Section 10.1); serve an old state to an app that hasn't seen a newer one; offer a new sender an older genuine receive key record, or keep accepting envelopes to a retired key, so with a stolen receive key it can keep senders that haven't seen a newer record on that old key and read what they send; with any receive key of an app, stolen or leaked, open an envelope sealed to it and seal its content again to the app's current key, which the message signature doesn't cover, so recipients notice nothing; withhold a counterparty's newer message, so an app may act on an older one; together with anyone who once held the naming key (a revoked app, an old backup, a vendor), test guesses of counterparties against the blinded keys it stores whose inputs are public, for as long as they exist, since the naming key never rotates (Section 3.5); acting alone, link related records and claims through equal blinded inputs | Forge or alter signed content; read content; roll back history an app has seen, or apply part of a batch, without that app noticing; make a sender use a receive key older than one it has seen | Chain, batch IDs and signed heads (10.1), the reader's checks of record writes and transition proofs (10.3), versions and generations (4.3), conservative recovery (12.6), receive key checks (8.1) |
| **Homeserver operator** | Withhold app records or `identity.json`, which stops actions on them once an app can't revalidate it; serve stale copies, so a reader may act on an app record the app has since replaced or withdrawn, until that record expires or reaches the identity's record age limit, and serve a reader that never saw a newer `identity.json` an older one that still lists a removed app, whose records it then acts on within the same limits, unless the identity's switch answers the reader's lookup with the newer one (Section 4.3), and a reader whose lookup gets no answer acts only on the user's explicit confirmation, never automatically; `identity.json` has no expiry of its own, so freshness comes from the Homeserver and, before acting on public app records, the identity's switch | Forge signed documents; lower a version or generation an app has seen; make a reader trust a record longer than its `updated_at` plus the identity's record age limit | Version and generation monotonicity (4.3), the switch's copy before acting on public app records (4.3), expiry and the record age limit of app records (4.2) |
| **Network attacker** | Observe TLS metadata | Read or alter traffic; replay requests | TLS, signed requests with timestamps, and retries recognized by content (6.1) |
| **Push relay, Apple, Google** | Learn push timing per handle or device, and which devices belong to one app; the relay, usually the app's vendor, can link a handle to an identity from the webhook's source and timing (9) | Learn content or sender; trigger pushes without the push key | Content-free webhooks, signed with unpublished push keys; shared egress and no source logs (9) |
| **Counterparty** | Send admitted messages while it is a contact or has a conversation entry; see which of your apps sent each message; see from your directory, `stale_key` answers and `directory_version` when each of your apps rotates its receive key, so roughly when it is online and has opened something (15); show anyone what you sent, since messages are signed; withhold its replies; through an app it has revoked, keep writing to a switch that hasn't yet seen its newer `identity.json`, though recipient apps reject those messages; have its counterparties act on the record of an app it removed in the last 10 minutes, while their cached copies last | Forge your messages; message you without being admitted; learn your identity's activity from responses | Signatures (5.2), admission (7), responses without `seq` or head (6.1) |
| **Stranger** | Ask to connect, where the identity allows it; with an invite code, write until the code expires, runs out or is withdrawn; nothing else until invited | Write to the inbox or read the switch's directory; push the user, unless the identity turned that on | Admission and connect requests (7) |
| **Compromised app or stolen device** | Act within the app's scopes; read its scopes' shared data; pause automatic attempts until the user confirms again, by rewriting the records they rely on; replace or omit records in collections it may write, or replay older messages from the same counterparty to apps that never saw newer ones; drop a message from a record before an app that never saw it reads the record, such as a `tasks.done`, so that app may take the task as open and act on it, automatically too within the limits its protocol sets (apps that saw it keep it, 8.2); read messages the app hasn't read yet or received since its last rotation; with only its current receive key, read new incoming messages until the app's next rotation; with its signing key, which a full state copy or backup contains, register a receive key of its own and read new incoming messages until the app is revoked, which the app sees as an unexpected registration and answers by leaving at once (3.6), and ask counterparties to re-send what they sent in the last 30 days, which they seal to its key (11); a copy of a current app's state reads its scopes' shared data, past and future, through every key bundle stored for the app, until the app itself is revoked (3.5); a restore of the app from a backup doesn't cut off a thief holding a copy (12.4) | Exceed its scopes; keep an app record it signed in use for long, since readers trust one at most until its `updated_at` plus the identity's record age limit (4.2); read other scopes' keys; act after revocation; read shared data written after the app is revoked and the data epoch rotated, or under a scope a reduction removed, written after that reduction; read messages sealed to receive keys the app has deleted, except copies counterparties still hold and re-send on request (11) | Scopes (3.3), per-app key bundles (3.5), the record age limit (4.2), revocation and rotation (12.2), receive key rotation (3.6) |
| **Revoked or departed app** | Keep what it already read; with a key that once was the app's, reach another identity's switch that hasn't yet received the newer `identity.json`, and so learn that it corresponds with this identity, until its certificate expires (at most 2 years, usually 1) | Read new shared data after rotation; write to the switch; write its Homeserver record or `identity.json`, since its grant is revoked with it and no app grant covers `identity.json` (3.4); be approved or listed again (12.2); learn from a switch holding the newer `identity.json` whether it corresponds with this identity, since it is answered like a stranger (6.1) | 3.2, 3.4, 4.2, 6.1, 12.2, 12.3 |
| **Signer compromise** | Everything for the identity, including all its sealed data, past and future, and the naming key, which `switch_root` gives (3.1, 3.5) | - | Out of scope: identity-level recovery |

- **Residual risk, removed apps at other switches:** a switch of another identity answers an app it holds as removed like a stranger (Section 6.1), but it learns of the removal only when an own app or the removed app itself delivers the newer `identity.json`. Until then it treats the app as current: the app can write to it, which recipient apps reject, and so learn that the identity there corresponds with its own. Where that identity allows connect requests, a removed app can also deliver an older document that still lists it, and so tell whether the switch already holds a newer one. Both end when the app's certificate expires, at most 2 years after it was issued and 1 year by default, since every reader refuses an expired certificate (Section 3.2).

The guarantees these protections provide are stated once, in Section 16.

| Party | Learns |
|---|---|
| Anyone (including counterparties) | From the Homeserver: `identity.json`, which lists every current app by ID and certificate hash, and the records (signing key, accepted kinds, the app's `label`, its certificate with the scopes, switch permissions, `issued_at`, `expires_at` and bundle key it names, and what their protocols add, such as the boards of a tasks app) of apps that publish them, such as tasks apps that publish their boards |
| Admitted senders | The directory, including receive key records, whose `n` shows roughly how often each app reads its inbox. From a `429 quota_exceeded` for the inbox quota, that the recipient's apps haven't read for a while |
| Recipient's switch | Sender identity, time, size bucket, the `notify` bit, target apps, and from them which class of kind a message is, since apps of different scopes receive different kinds; each sending app's full certificate (its scopes, switch permissions, `issued_at` and bundle key), contacts, denied IDs and conversation entries (so whom the identity writes to), who asked to connect, the `context` of every invite code in the clear (Section 7), claim states and times, shared record size buckets (values are padded, Section 13.4), versions and collections, the scopes each policy names, app last-seen times and when each app rotates its receive key; each app's push relay URL, which names its vendor; the network address and timing of every request; and, when it also serves the counterparty, both sides of the conversation. The exception is collusion with anyone who once held the naming key, which never rotates: together they can test guesses of counterparties against blinded keys whose inputs are public, while those records exist. Never the content of envelopes or sealed values |
| Own apps | When items they can't read were written, from chain stubs and gaps in `seq` |
| A revoked or departed app | Everything it read before leaving; nothing written after the next key rotation. Not which identities correspond with its own, from a switch holding the newer `identity.json`, which answers it like a stranger (Section 6.1); one that hasn't received it still serves it until its certificate expires |
| Counterparty | Which of your apps sent each message, as a signed copy it can show others. Not your identity's activity: responses to it carry no `seq` or head |
| Push relay | That a notification is due for a handle, and when, and which handles share a push key, so which devices belong to one app. Push keys appear in no public document, but the webhook's source address and timing can still link a handle to its identity, without the switch operator's help (Section 9). Together with the switch operator, which sender's messages reached which device |
| Apple or Google | That a device received a push |
| The device's notification store | The text of every message the push extension showed, kept by the operating system outside the app's keys until the user clears it (Section 9) |
| Homeserver | Published records, and the encrypted backups of apps that keep them there; from each app's grant, the Homeserver paths it covers (Section 3.4). The signer's backup is public ciphertext, so anyone sees its size and when it changes, which is when the signer acts (Section 12.8) |

- **Forward secrecy by rotation.** An app deletes a receive key once it has read everything sealed to it, after its next rotation (Section 3.6). Rotation follows reads: about once a day by default, as often as once an hour if the app chooses, and not at all while the app opens nothing new, so there is no fixed bound for an app that doesn't read. An envelope someone captured (operator logs, a breach) stays readable through a leak of the app's state only until that deletion: about a day for an app that reads daily with the default interval, and longer for messages that sit unread. Someone who steals only a receive key reads new incoming messages only until the next rotation, with fresh random keys as recommended. A full copy of an app's state, or a backup, also holds its signing key, which can register a receive key of its own, so it reads new incoming messages until the app is revoked, whatever the rotation; the app sees that registration and alerts the user (Section 3.6). A malicious operator holding a stolen receive key can also keep senders that haven't seen a newer record on the old key (Section 14). This protects captured envelopes, not stored history: senders keep what they sent for at least 30 days and re-send it on request, shared records keep the messages they reflect, and backups keep both, so those copies are protected only by the app's own state and keys. Whoever holds an app's signing key, or a stolen current receive key together with the operator, can pull up to 30 days of what counterparties sent through `resend_request`, sealed to keys it holds, within the senders' limits (Section 11). Apps keep the scope keys of every data epoch, and a newly approved app receives them all (Section 3.5), so stored shared data remains readable to every app holding its scope keys, a seized one included, however old it is. A copy of a current app's state goes on reading shared data written later too, until that app is revoked (Section 3.5). A malicious operator that holds any receive key of an app can open what was sealed to it and seal it again to the app's current key, so forward secrecy doesn't hold against it for those messages (Section 14). A message the push extension showed also stays in the operating system's notification store, outside this deletion (Section 9).
- **Erasure.** The signer can erase the account at a service. The service then deletes everything it holds for the identity, and its operator lets that data age out of its backups (Sections 6.5 and 12.7). An erasure doesn't reach what others keep: counterparties' accounts and the messages they received, senders' copies of what they sent, and the identity's own apps and their backups.

## 16. Guarantees

- **Confidentiality:** message content and sealed shared data are readable only by own apps holding the matching keys: recipient apps for messages, apps with the read scope for shared data. Every recipient app of one envelope reads the same plaintext (Section 5.1); two envelopes under one `msg_id` may carry different plaintexts, which an app notices only if it sees both (Section 11).
- **Forward secrecy:** a message can't be decrypted from its recipient app's state once the app has deleted the receive key it was sealed to (deleting in the sense of Section 3.1: from every copy the app keeps), which happens at the first feed read after the app's next rotation; with fresh random receive keys, a leaked receive key stops reading new messages at the app's next rotation. A leaked signing key, which a full state copy or backup contains, can register its own receive keys and read new messages until the app is revoked (Section 3.6). Rotation follows reads, so an app that opens nothing new keeps its current key (Section 3.6). This covers captured envelopes; plaintext kept by senders, and re-sent by them on request (Section 11), in shared records and in backups is outside it, and shared records stay readable to every app holding their scope keys (Section 15). It doesn't hold against an operator that holds a receive key of the app, stolen or leaked: the operator can open what was sealed to that key and seal it again to the app's current key, which recipients don't notice, since the message signature covers neither the kid nor the envelope header. Nor does it cover text the push extension showed, which the operating system keeps in its notification store (Section 9).
- **Integrity:** every message, operation and document is signed by its writer, and apps check the writer, its standing and the item's place in the chain for every operation they read (Section 10.3). Apps detect conflicting history while they can verify continuity: the chain and batch IDs expose a rollback of history an app has seen. If a restore or long absence predates retained history, the app enters explicit recovery; reconciliation does not prove the missing chain's continuity (Section 8.3). An app that may write a collection can still replace or omit records in it: signatures inside a record prove who sent each message, not that the record is complete. It can't change what a stored message says, because apps verify every stored message on use (Section 8.2).
- **Isolation:** an app acts and reads only within its scopes, and can be revoked on its own. Departed apps lose access at once through the service, and cryptographically at the next key rotation.
- **Idempotent processing:** every message's lasting effect is applied once per identity, through the messages and `msg_id`s that shared records keep and each app's processed pairs; deduplication and the conflict check hold per reading app (Section 11). A pair a protocol forgets leaves that message to the protocol (Section 11). Backup rollback and external effects are handled by reconcile mode, claims and the journal.
- **Availability** depends on the switch and, for acting on public app records, on the Homeserver from which `identity.json` must be revalidated (Section 4.3). Delivery ends at acceptance. The service keeps entries for an offline app within its retention rules (Section 6.3); entries an app missed while marked lagging, and those a lost service held that no app had read yet, come back only through re-sends on request, best effort (Sections 8.2 and 12.6). Moving to another provider and a provider loss (Sections 12.5 and 12.6) bound the damage. The switch is one logical, replaceable coordinator for each identity, trusted for coordination: ordering, time, availability and delivery, not for content. Operators are expected to run it on synchronous replicas, so a failure of one machine loses nothing; what is forbidden is losing a write it acknowledged and serving on, which makes it non-compliant (Section 6.5): the account must move to a new generation instead.

A protocol states what these give it.

## 17. Left to apps, protocols or later

- **Up to each app:**
  - local storage (the protocol is storage-agnostic), and its backups: whether to keep them, where, and the backup key;
  - keeping its devices consistent: cursor, receive keys, journal and local state.
- **Decided later:**
  - detecting a split view, a service that shows different own apps different histories after any shared prefix, for example through witness files on the Homeserver or own apps exchanging signed heads: two service-signed heads at one `seq` with different hashes prove it. Witness files are defeated when one operator runs both;
  - read status for messages;
  - a state commitment in signed heads, covering claims, tombstones and record versions, so that an import, and every read by an app, can be checked for completeness against the chain (Section 12.5, residual risk);
  - a Merkle log as chain version 2, so a phone on a busy identity verifies a new head with a few dozen hashes instead of a stub for every operation since its last head. Version 1 works without it; the cost of waiting is that download, which matters only for very busy identities;
  - browser and WASM support;
  - strangers messaging without an invite (open mode);
  - filters for connect requests, such as identities on trusted Homeservers or in a social graph; later options, not in this version, are a proof of work or a payment stamp with each request, and a social graph of trust drawn from public data: who else approved the identity, and which Homeserver it uses;
  - accepting attestations in Pubky grants as app certificates;
  - a private identity file, written by the signer and encrypted for the identity, with opt-in details about each app for the user's own convenience, such as a device name and when and where it was added, to help with reinstalls and managing sessions;

## 18. What the Pubky stack needs

- **Pubky Switch:** open-source, run as a separate service, self-hostable, documented API.
- **A reference push relay.**
- **Signer support in Ring and Bitkit:**
  - app requests signed by the app and bound to the auth request, checked as Section 3.2 says, and certificates with scopes, switch permissions, bundle keys and a lifetime of at most 2 years, renewed before they expire, delivered in an approval of public material only as the grant approval's companion claim;
  - `identity.json` with versions, generations and the app list, delivered to the switch before it is published (Section 4.3);
  - Shared Data Keys and the naming key, derived from a Switch root as in Section 3.5 and delivered as a key bundle sealed to the app's bundle key, in the approval and after rotation on revoke and leave;
  - the generation, version and hash of the newest `identity.json` a service accepted from it, kept so it never adopts a lower copy, and the App IDs it revoked, kept for good;
  - listing apps by last-seen time;
  - enrollment, revoke, freeze, recovery and erasure (Section 12.7);
  - sub-scopes, with their keys in key bundles, such as `tasks_assign:team1` (Section 3.5);
  - the hand-over to another signer, sending and receiving (Section 12.8).
- **Pubky grants** covering exactly each app's paths and never `identity.json`, issued by the signer and revoked by its host on the signer's alert (Section 3.4).
- **Pubky client:** HTTP/2 and a persistent pkarr cache.
- **Homeserver event stream keep-alives,** so that an open subscription proves it is live. That would let the stream replace the check before each attempt (Section 4.3).

## 19. Decisions and open questions

Questions 1 to 6, 8 and 9 are deliberate trade-offs of the switch; the numbers this section skips aren't the switch's. Each has a default, which this spec describes and the reference prototype implements and tests. Every one is decided as its default, with the metadata of 3 and 6 disclosed to users and push optional for each app.

1. **No unsolicited first contact.** A sender needs to be a saved contact, invited, or answering someone who wrote to it first; a stranger can at most ask to connect, where the user allows it (Section 7). Decided: kept for v0.2.
2. **Forward secrecy by rotation, not a ratchet.** Receive keys are replaced by fresh random keys after reads, about once a day by default and configurable down to once an hour (Section 3.6). An app that opens nothing new doesn't rotate, so there is no hard one-day bound for an app that doesn't read. Receive-key deletion protects older captured envelopes. Stored shared data remains readable to apps holding its scope keys, so a seized device exposes the history its scopes cover, as well as its unread messages and captured envelopes sealed to keys it hasn't deleted yet (Section 15). A stolen receive key reads new incoming messages until the next rotation. A copied signing key, which a full state copy or backup contains, can register receive keys and read them until the app is revoked, which the app detects and answers by leaving (Section 3.6); rotation alone doesn't end that, and on iOS the push extension holds that key in storage readable after the first unlock, so a forensic extraction gets it and can send forged messages as the app until it is revoked (Section 9). A copy of a current app's state also reads its scopes' shared data, past and future, until the app is revoked: later key bundles are sealed to the app's static bundle key, kept by decision. An operator holding any receive key of an app can re-seal what was sealed to it to the app's current key, unnoticed (Section 14). Admitted senders see roughly how often each app reads its inbox, and when it rotates, so roughly when it is online (Section 15). A Double Ratchet would give per-message forward secrecy and heal within one round trip, at the cost of per-pair state and message loss on restore. Sealed messages, Noise IK, a Double Ratchet and MLS were compared, and sealed messages with rotation after reads were chosen: they keep no state per pair of apps and lose no message on a restore. Decided: rotation after reads.
3. **Server-visible metadata.** The switch sees target apps, and from them the class of each message's kind, policy scope names, record size buckets (values are padded, Section 13.4), contact Pubky IDs, whom the identity writes to (conversation entries), invite code contexts, each app's push relay URL, network addresses and timing (Section 15). Blinding hides counterparties in stored state and exports, not from a live operator, which links records and claims to senders through batches and timing. Decided: acceptable, disclosed to users.
4. **Rollback detection, no fork detection.** Apps detect conflicting history while they can verify continuity (Section 10.1). If a restore or long absence predates retained history, they enter explicit recovery; reconciliation does not prove the missing chain's continuity (Section 8.3). Apps don't detect a split view: a service that shows different apps different histories after any shared prefix, from the start or later, or one that loses an acknowledged write and serves on, which is non-compliant (Section 6.5). On a split, each branch can carry out an obligation once (Section 10.1). Witness files on the Homeserver, or own apps comparing signed heads, could detect it, but witness files not when one operator runs both. Decided: accepted for v0.2. The switch is trusted for coordination, including ordering (Section 14), and detecting a split view stays later work (Section 17).
5. **Delivery ends at acceptance.** There are no acknowledgements: a message is done when the recipient's inbox accepts it, and the protocol's own replies show progress. Offline delivery is retained within the service's retention rules (Section 6.3). Entries an app missed while marked lagging, and messages a lost provider held, are recovered only by re-sends on request, which are best effort (Sections 8.2 and 12.6). Decided: enough, without read status.
6. **Push metadata.** A switch operator and a relay operator together can link senders to devices, and a relay alone may link a handle to an identity from the webhook's source and timing (Sections 9 and 15). Decided: acceptable, disclosed to users; push stays optional for each app.
8. **Signer availability.** Rotation after a leave waits until the signer is online; until then, only the service blocks the departed app. Decided: acceptable.
9. **Signed messages.** Every message is signed by its sender app, so a counterparty can prove to anyone what you sent (Section 15). Signing only the messages a protocol acts on would make the rest deniable, but someone with an app's stolen keys could then forge those messages to it from its contacts. Should any kinds be deniable? Decided: every message stays signed.

**Open questions on the switch.** Four questions are open. Each default is the rule this spec describes.

25. **An authenticated sign of erasure.** An app can't check that its identity's account was erased: the erased account answers like one the service doesn't host, signed with a key no client knows, and a failing Homeserver can show a missing `identity.json` too. So an app takes the two together as an erasure only after they have held for 24 hours (Section 12.7), which leaves it idle for a day after a real erasure and still rests on answers no key vouches for. A marker the signer publishes on the Homeserver before it erases, signed by the identity key and naming the service and its key, would let apps stop at once and on evidence. It would cost one more public record, which shows anyone that the identity left that service and when, a format for it, and a rule for a marker that no erasure follows. Open: until it is decided, the 24-hour rule applies.
26. **Bounding `renewed`.** Each renewal adds an entry for the earlier certificate to `identity.json`, and a closed entry stays until its app is removed. At renewal every half lifetime, an entry about every six months per app, `POST /enroll`'s 256 KiB cap is reached in about 1.9 years at the 255-app limit and 17.5 years at 32 apps; `PUT /identity`'s in about 2.6 and 24. The signer stops at the cap with an alert at three quarters of it, renewals stop for an app that stays away and keep a lifetime the user chose short (Section 3.1), and only a removal shrinks the list. A purge by time, of a closed entry once its certificate expired longer ago than some bound, isn't sound. A shared record stays current until it is written again, and a reader that fetches it later accepts its write under an earlier certificate only while that entry is in `renewed` (`spec/wire-format.md` Section 6.2), so the entry is needed for as long as such a write is current, which no time bounds. An inbox entry is checked against the sender's newest `identity.json` when the recipient processes it, and entries don't expire, so a time bound there is a trade-off, as for purging `removed` (Section 4.3). The candidate answer bounds the purge from the records' side, as `service_keys` are: the service reports the certificate hashes that current records' kept writes name, the signer keeps those entries, the switch refuses an `identity.json` that drops one, and an app frees one by writing such a record again under its newer certificate. Open: until it is decided, nothing purges `renewed`.

29. **Uploads from a dishonest app after a provider loss.** After a provider loss, any app of the identity can upload the lost generation's operations of the kinds its certificate allows, a record write under any write scope it holds, not only the record's (`spec/wire-format.md` Section 7.4.14), and an operation without the lost service's proof is compared at a lower bound its signer chose: the version it claims to build on, plus one. Today the rule decides between two versions silently whenever one is newer, a bound counting as its value. So a dishonest app of the identity can, after a provider loss, replace a record held from an honest proved upload with an operation built on an inflated version, which keeps the proved one nowhere; later honest uploads below the bound then change nothing and are counted nowhere, and honest readers may adopt the replacement when they read the record back. At a key the service lacks, the first upload fills the record with whatever collection and policy it names, and an operation that isn't a create carries no key derivation that binds them, so honest proved uploads that follow are only divergent and a live write with the real policy is refused, which holds the key with the uploader's policy. A proofless `unknown` applies to a live attempt that isn't orphaned yet, which a live `unknown` couldn't; and a proofless `attempt` beside an honest open one makes the claim divergent, no automatic attempt, until every attempt that isn't final is resolved by its owner, evidence or the user, the uploader owning its own: a live `attempt` beside an open one is refused. An app needs a certificate of the identity to do any of this, so it is a compromised or malicious app of the identity, not a stranger. The candidate rule: decide silently only between two proved versions, or when a bound builds exactly on the other's proved version, and keep everything else divergent; and let a proved upload replace a record taken from a proofless one. Open: until it is decided, the rule is the one `spec/wire-format.md` Section 7.4.14 states.

32. **Two identities against a third at the total bound.** The total bound on entries an app stores while they wait, for their sender's check or for a scope key, drops from the identity holding the most, and of identities holding as many, from the one whose newest entry is newest (Section 8.2). Two admitted identities acting together can so drop a third's entries: one holds as many as the third, accepted earlier, the other takes the total one over. One identity alone can't. The default is that rule, with every drop told to the protocol, which may ask the sender again (Section 11). Alternatives: on a tie, drop from the identity whose entries were accepted latest in all, or refuse to store the entry that takes the total over, which the cursor then can't pass until the bound frees.

**Team decisions on the switch.** The numbers this section skips aren't the switch's. All three are decided.

15. **Who runs the default switch.** Decided: Synonym runs it, for users who don't choose one; any user can still choose another operator or host their own. Its availability target, cost per identity and runbook (Section 6.5) are set before launch. Recommended: a separate service with its own database, never inside a protocol's app server. A user whose Homeserver Synonym also runs has one operator for both, so witness files wouldn't detect a split view for that user (Section 17).
23. **Anchoring `identity.json` in PKARR** (Sections 4.3 and 14). Decided: no anchor for v0.2. The switch's copy bounds what a stale Homeserver copy can do, and after a cooperative move the old switch points to the new one, but not after a provider loss. An anchor would cost PKARR space and couple every update to it. If one is wanted later, the smallest is the generation and switch origin.
24. **Who manages the identity when a user starts with a third-party app.** Decided: the signer core ships in the SDK, so any app can be its identity's signer; handing the identity to a dedicated signer such as Bitkit or Ring is recommended, not required. An identity has one signer at a time, the install `identity.json` names (`signer`): a hand-over, which travels through the switch, moves the identity key and the signer's records (the newest `identity.json` it accepted, the App IDs it revoked, the certificates that document references, the key bundle parts it stored) to the new signer, and the old one deletes the key and becomes an ordinary app. Keeping the key safe and backed up is the signing app's job; the signer also backs its records up on the Homeserver, sealed to a key from the identity key, and restoring is taking over from that backup. Section 12.8 specifies the hand-over and the backup.

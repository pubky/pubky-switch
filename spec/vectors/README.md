# Pubky Switch test vectors

Test vectors for the Pubky Switch's wire format in `spec/wire-format.md`. Every file is computed by the
reference prototype's own code, shared separately, from fixed keys and fixed randomness, so any
implementation of the switch, a signer or an app can check its encodings, signatures, derivations, envelopes
and state rules against them byte for byte.

The scopes, message kinds, collections and app record member in these files are those of Paykit, the first protocol on the Switch, which the switch treats as opaque. Paykit's own vectors, a set that builds on this one, are [with Paykit's spec](https://github.com/pubky/paykit-rs/tree/master/specs/v0.2/vectors): it uses the fixed keys of `keys.json` and the documents of `documents.json`. This set depends on no other.

## Conventions
- **Seeds.** Every fixed secret and random value is `BLAKE3("paykit/v1/test-vectors/" + label)`, cut to the length needed (16 or 24 bytes take the first bytes). Labels appear in the files where they help, for example `alice/identity` or `alice/wallet/receive/0`. X25519 secrets are clamped (RFC 7748) after that. UUIDs are UUID v4 built from the first 16 bytes of a seed.
- **Encodings.** `*_hex` fields are lower-case hex; other binary values are base64url without padding, as on the wire. JSON that is signed or hashed appears as a string holding its exact bytes (`body`, `json`, `envelope_json`); parse it, but compare and hash the string's bytes.
- **Times.** Static vectors start at `2026-01-01T00:00:00.000Z`. `claims.json` runs on a test clock starting at its `start_time`.
- **Sections.** Descriptions and the table above cite sections of `spec/wire-format.md` as "wire N"; "spec N" is the Pubky Switch spec. Paykit's documents are "Paykit wire N" and "Paykit spec N".
- **HPKE randomness.** An envelope fixes, per recipient, the 32 bytes of keying material `ikmE` from which HPKE derives its ephemeral key (RFC 9180 `DeriveKeyPair`). An implementation whose HPKE library can't take `ikmE` can take `sk_e_hex` instead, or check only that it opens every envelope to the given plaintext.
- **Scope keys and blinding.** Scope keys and naming keys are derived from each identity's Switch root (wire 1.5); `keys.json` lists them, and `sealed.json` and the key bundle use them. Record keys and obligations are blinded with the naming key of the identity whose switch holds them: alice's for her payer records, Allowance records and claims, bob's for his payee records.
- **Record versions** are the (generation, `seq`) of the write that produced them (wire 6.2): `operations.json` and `chain.json` follow one record from its create at `seq` 6 to its delete, each write naming the version it read in `expected_version`. After `chain.json`'s revoke at `seq` 9, the paid batch takes `seq`s 10 and 11, so the delete names (1, 11).
- **Claims.** Each `write` step sends one batch with one claim operation, built from the step's `op`. Its `expect` is `GET /claims/{claim_key}` as app A sees it after the write, or the error's status, code and `current`. Owners and attempts are named in `apps` (with their switch permissions and the seed label of the signing key their App ID comes from) and `attempts`.
- **Export.** Service keys are fixed only in these vectors; a real service draws each account's key at random (spec 4.3). `export.json` is alice's account frozen right after `chain.json`'s last item: its chain ends at the freeze transition (`seq` 10), while `operations.json` continues the account past `seq` 9 instead. It is a complete export, which a next service enrolled with alice's version 3, at the freeze's time, activates; the reference prototype tests this. Only the wallet registers in that chain, so the phone's and the executor's `app` parts hold no record or receive key; the inbox entry at `seq` 5 isn't exported, since the wallet moved its cursor past it. A record's `size` is its `ct` decoded (wire 9.1). Completing it changed `export.json`, and, through the manifest hash, the export transfer in `documents.json`, its signature and the transfer request's in `signatures.json`, and the chunk fetch and answer in `http.json`; nothing else.
- **First document:** alice enrolled without a document, so her account's first `identity.json` is version 1 at generation 1 and data epoch 1 (wire 3.3): `http.json`'s delivery and `chain.json` seq 1. Her version 3, at data epoch 2, follows at seq 2; versions need only increase. The generator replays the enrollment and that delivery on the prototype service, which chains it as seq 1 and refuses version 3 as a first document.
- **Erasure** (wire 7.4.16). `http.json`'s erasure names the fixed service key of alice's account. The generator replays it on the prototype service after that enrollment and first delivery, where the account's key is drawn at random: the vector's request is refused (`409 conflict`), the same request naming the drawn key gets exactly the vector's answer body, without a head, and a repeat is an operator-signed `404`.
- **Certificate lifetimes** (wire 3.1). Every certificate expires, within 730 days of its `issued_at`. The fixture certificates are issued 31 days before the start time and expire 365 days after issue, except `phone`'s (one year after the start) and the renewed `wallet` certificate (90 days after the start). Bringing in these lifetimes changed every value built on a certificate: the certificates' signatures and hashes, the `identity.json` documents and app records that carry them, the sealed record values holding stored messages with their sender's certificate, and so the chain, the proofs, the heads, the export and the HTTP signatures; `messages.json`, `envelopes.json`, `keys.json`, `identifiers.json`, `claims.json`, `periods.json` and `allowance_usage.json` didn't change.
- **Sealed value padding** (wire 6.2). Every sealed shared record value is `u32_be(len) || JSON || zeros`, padded to its size bucket, except a delete, which stays empty. Bringing in the padding changed every value built on a sealed value: the `ct` of each `record.put` in `operations.json`, `chain.json`, `http.json` and `export.json`, and the signatures, item hashes, chain hashes, stubs, proofs, heads, chunk and manifest built on them; checked against the files before the change, nothing else differs.
- **Key bundle certificates** (wire 3.5). Every key bundle part names, in `cert`, the document hash of the certificate it was made for: `envelopes.json` `key_bundle` names the executor's certificate and `documents.json` `approval` the wallet's. The parts' envelopes and signatures, the key-bundle case of `signatures.json` and `operations.json` `key_bundle.put` carry it.
- **Reconciliation window** (wire 6.8). A tombstone, and a claim whose every attempt failed, are kept until the service clock reaches the pinned deadline plus 30 days. In `claims.json` O7's tombstone is still there at its deadline (steps 41 and 42), and a 30-day advance at the end shows it deleted. O10 is a failed claim that a late receipt settles after its deadline.
- **No-op batches** (wire 6.4). `claims.json` `noop_batch` steps send an unchanged `app.put`, by app A conditioned on claim O11's step, and by the revoked app C: without `cursor.set` a failing condition is answered as a no-op; with it the condition is checked (`409`), a condition that holds moves the cursor with no proof, and C is refused at authentication (`403 not_current`). Each step gives the exact request body. `claims.json` gives the account (`identity`, from the seed label `identity_seed_label`) and per app its certificate and the app record and receive key record it registered (`apps`); its `identity.json` names a service key drawn at random, so only its contents are described.
- **Kept record proofs** (wire 7.4.9, 10.3). The service keeps the transition proof of a record's current write with the record, so `export.json`'s record part carries `chain.json`'s proof for `seq` 8. That changed the chunk, the manifest, and through the manifest hash the export transfer in `documents.json`, its signature and the transfer request's in `signatures.json`, and the chunk fetch and answer in `http.json`; nothing else.
- **Key retention conflict** (wire 7.4.2). The generator replays `http.json`'s key change on the prototype service, whose account keys are drawn at random: an identity writes a record at generation 1, enrolls again for the pending key and delivers a document naming it without generation 1's key, and the service's answer body is the vector's. It then checks the generations come ascending: kept at generation 2, a write there, and both left out at generation 3 give `[1, 2]`.
- **A reduction rotates** (wire 3.8). The `wallet` renewal drops `manage_contacts`, which has keys, so `documents.json`'s versions 4 and 5 carry `data_epoch` 3 where version 3 has 2; their `until` is the renewing delivery's time plus the tolerance. Only those two documents changed.
- **Separate export parts** (wire 10.3). `export.json`'s live claim carries no entries: its one entry follows it as a `claim_entry` part, and the claim names its `creator` and `last_entry_ms`; `app` parts carry no key bundle parts (none are stored in this chain). That changed the chunk, the manifest, and through the manifest hash the export transfer in `documents.json`, its signature and the transfer request's in `signatures.json`, and the chunk fetch and answer in `http.json`.
- **Reachable apps only** (wire 10.3). `export.json`'s meta part gives `app_added_at` for the reachable apps alone, as the service keeps it: the wallet, current with a receive key. The phone is revoked and the executor has no receive key, so neither has an entry. That changed the chunk, the manifest, and through the manifest hash the same documents, signatures and answers as above.
- **The version held again** (wire 7.4.5). bob's switch, in `http.json`, holds alice's version 3. Its answers to her wallet's two deliveries of version 3 are built as the switch builds them: the refusal of the other body by the switch's own constructor, whose body the prototype's tests compare with the switch's answer. The other body is her version 3 with connect requests on, signed with her key; the two bodies at one version are equivocation (wire 3.3).
- **The switch's names** (wire 1.5, 2.3, 4.1, 7.1). The formats of the Pubky Switch sign and derive under `pubky-switch/v1/` labels, its headers are `Switch-*` (sent in lower case), its Homeserver paths lie under `/pub/pubky-switch/v1/` and its envelopes start with `PSW1`; Paykit's executor grant and obligation IDs keep `paykit/v1/`. Moving to these names changed nearly every value: every signature but the executor grant's, kids, key commitments, envelopes, scope keys, naming keys, blinded inputs, record keys, policy hashes, sealed values, the chain, proofs and heads, and the export. The seeds keep their prefix, so the fixed keys, Pubky IDs and App IDs are as before.
- **Signer IDs** (wire 3.3). Every `identity.json` names its signing install in `signer`: alice's documents `b64(seed alice/signer)`, bob's `b64(seed bob/signer)`, and the phone's take-over delivery in `http.json` `b64(seed alice/phone/signer)`.
- **Executor batch.** An Allowance pays only requests in its own asset (Paykit wire 4.15, 5.5; Paykit spec, Section 17, decision 14), so the executor batch in `operations.json` pays the btc one-time request under the btc Allowance: after the wallet's attempt failed (`claim failed`), at step 2, before the request's deadline. Its ledger entry's `value` and `asset` are the request's own amount (`0.00025` btc).
- **Attempt deadlines** (Paykit wire 4.5). An attempt carries `d + 1 ms`, `d` taken at millisecond precision. The wallet's attempt on the btc one-time request, which expires at `2026-01-02T00:00:00.000Z`, pins `2026-01-02T00:00:00.001Z`, and the executor's attempt names the same. That deadline is in the claim attempt of `operations.json` and in `chain.json` `seq` 7, so the chain hashes from `seq` 7 on, the proofs and heads built on them, `export.json`, the export transfer in `documents.json`, its signature and the transfer request's in `signatures.json`, and the feed page, `POST /ops` answer and chunk of `http.json` carry it too.
- **Labelled selling scopes** (Paykit wire 3.1, 4.3, 5.1). bob's `hosted` app holds only `request:shop1`; it isn't among `keys.json`'s first apps or bob's `identity.json`, so the earlier vectors keep their places. Its label keys are the sub-scope keys of `request:shop1`, bob's `request` keys derived once more (`sub_scope_keys`).
- **Permissions** (wire 3.1). A certificate's switch permissions are its `permissions` member, signed with the rest; the switch checks their form and enforces them as signed.
- **Protocols' members** (wire 3.2). An app record carries what its protocols add under `protocols`. The records of `documents.json`, all of Paykit's apps, hold Paykit's member, `protocols.paykit` (Paykit wire 3.2): the identifiers each app can pay to and, for `shop`, its public endpoint. The apps of `claims.json` belong to no protocol, and their records carry an empty `protocols`. `documents.json` `app_record_protocols` checks the form of `protocols`. The member is part of every value built on an app record: the record's signature, the `app.put` operation, the chain items, proofs and heads that follow it, the export and the HTTP bodies that carry them.
- **Rejections.** Where a file lists inputs to refuse (the `rejections` of `chain.json`, `envelopes.json` and `signatures.json`, the refused case of `chain.json` `batch_id_window`, `documents.json` `permission_rejections` and the `refused` cases of `scope_rule` and `app_record_protocols`, `envelopes.json` `key_bundle_rejections` and `signer_handover_rejections`, `export.json` `record_rejections` and `claim_rejections`, `operations.json` `unknown_members` and its `batch_entries` and `integer_bounds`, the errors of `claims.json`), what is normative is that the input is refused, and the HTTP status and `code` where the wire document fixes one. An `error`, `message` or `reason` text is the prototype's, and only informative; an `error` or `reason` text is quoted without the section number it starts with there.

## How the files were generated
The reference prototype, shared separately, generated every file. Its tests recompute every file of both sets and fail on any difference. While computing, the builder also checks each vector with the implementation: every signature verifies, every envelope opens for each recipient, every message passes the recipient checks and decodes by kind, the chain verifies, and the rejection cases fail.

After an intended wire change, the vectors are generated again from the prototype and the diff is reviewed.

The JSON examples in `spec/wire-format.md` are taken from these files, except the `429 quota_exceeded` body of wire 9.3, which is the prototype's answer and says so, and the acceptance example of wire 5.1, which is the Paykit set's; update them with the vectors.
